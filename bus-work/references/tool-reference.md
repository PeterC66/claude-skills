# Tool reference — the detail behind `bus-work/SKILL.md`

**For:** a session about to change one of these tools, or one that needs to know exactly what a tool asks, refuses or writes.

`SKILL.md` keeps a rule sentence and the command for each tool and points here; this page holds the per-tool reference. The split was made on 21 October 2026 by buses-data OA-646, when `SKILL.md` had grown from 9,571 words on 18 September to 16,073, and every interactive `/bus-work` session loaded all of it. **Nothing below was rewritten in the move** apart from relative links re-based to this folder: the paragraphs are the ones that stood in `SKILL.md`, so `git log -S` on a sentence still finds its history. The incidents behind the rules are in [why-these-rules.md](why-these-rules.md), and the procedures in [playbooks.md](playbooks.md).

## `loop_health.mjs`: the deeper readings

**It also answers "could a tick take any work, by its own prompt?"** (buses-data OA-560), in a section headed `CAN A TICK DO WORK?` with one word: CAN WORK, NOTHING TO DO (a NOTE, and the normal day for a loop that does map upkeep only) or BARRED (a BLOCKING finding). It checks the prompt's prerequisites (the stored task against `loop/README.md`; every script the block names exists), the resources a unit needs (a tick's own live lock is a run in progress, not a bar), and the one feed: bus-work rows by step 4D's rules (`--deep`, which reads the live portal and takes about a minute). The ad-hoc queue is not a tick's feed since buses-data OA-610, because it has its own loop, so without `--deep` the verdict is BARRED or *not measured*, never a guess. It ends with **What you can do, most rows first**: each lever says how many rows it releases and the move. Add `--deep` for the bus-work feed and `--no-probes` to skip the spawned commands.

**With `--deep` it also asks whether the ticks can clear the refreshes in time** (2026-10-08). Each finishable refresh row owes a rebuild and a staging, less what the scan's `_gtfs/ink-review_<scan>.json` shows done, and the rows are projected earliest date first against the ticks a day read from the cron in `loop/README.md` (3 if it cannot be read, and the finding says it assumed). A shortfall is AT RISK, and its move is `/ticks N`, where N is the number of extra ticks that, run now, put every row in time. A row with no date is counted apart and never projected.

## `commit_paths.mjs`: refusals, the read-back and `--index`

**It refuses, and commits nothing, when** the token no longer matches (a path, the branch, HEAD or the message changed since you read the diff), a path is a folder, a pattern or outside the repository, somebody else has already staged a named path, or the checkout is not on `<branch>` at the start or just before the commit. It commits through `spawnSync` with the output captured, so a backtick in the message is text and no pipe can kill a hook mid-refusal, and it never pushes. **It then reads the commit back:** subject, parent, the changed-file list equal to the paths, a clean `git status` for them, and each path's committed blob equal to the reviewed one, or every reviewed added line present where the pre-commit hook rewrote it. The two document-stamp lines are the only tolerated difference. If the commit lands and the read-back fails, the first line is `COMMITTED <sha> - READ-BACK FAILED` and `--json` carries `committed: true`: the commit is in the history, so repair it with a new commit and never commit again.

**A restamp leaves git's index one stamp behind, and the script repairs it.** A pathspec commit builds git's real index before the pre-commit hook runs, so when the hook restamps a document the commit and the working tree carry the new stamp and the index keeps the old one (`MM`); a later bare commit would put the old stamp back. Measured on 9 October 2026 against buses-data's own hook. buses-data's post-commit hook already resets those entries; where a named path is still staged after the commit and its working tree already equals HEAD (a repository without that hook), the script resets the entry itself and says so. **The script must not pass `--literal-pathspecs` to `git commit`**: git exports the option to hooks as `GIT_LITERAL_PATHSPECS`, which turned the `'*.md'` glob in that post-commit hook into a literal and silently stopped its repair, so the commit names each path as `:(literal)<path>` instead.

**An untrack or a file-mode change is committed with `--index`**, because it has no working-tree content a pathspec could carry. Run `git rm --cached "<path>"` or `git update-index --chmod=+x "<path>"` first; `--index` then requires the staged set to be exactly the named paths, refuses a staged change of content, commits bare and reads back that the index is clean and the path is gone from HEAD, or has the reviewed mode. Exit 0: reported, or committed and read back. 1: a hook refused, or the read-back failed. 2: refused before any commit. 3: git's index is locked, try again.

## `preflight.mjs` and `push_main.mjs` in full

**It asks what the push CONTAINS first, and the answer decides how much of the rest to run.** `origin/main..HEAD` gives the paths; a push touching only the documentation folders `gates.yml` already treats that way runs the cheap tier, and anything reaching `Areas/`, `Places/`, `.github/` or a root dotfile earns the full one, which includes the unsuppressed board. That is not thrift for its own sake: hand-run before a docs-only push the cheap version yielded zero true findings and one false alarm, and a preflight whose false positives outnumber its true ones is one somebody stops running. `--all` forces the full tier, `--json` prints the machine-readable form, `--repo <path>` names a repository other than the one you are standing in.

**Four properties are load-bearing and each of them is a thing that went wrong.** It never stops at the first failure, because CI's job ordering is what hid three of the four blockers — the named shape *the blocker behind the blocker*. It suppresses nothing: no `--no-live`, no `--register-only`, because the deployment row is exactly what `--no-live` hides. A check whose tool is missing is UNANSWERED and takes the exit code with it, never a pass. And the report always ends with **what it did not ask** — whether the portal suite is green, anything needing the network, and, when the engine checkout is not clean and level with its own `origin/main`, the fact that any arm not run at the pin was measured against an engine CI will not check out.

**The board runs at the pin, as `gates.yml` runs it** (buses-data OA-540). CI checks claude-skills out at `engine.lock.json`'s commit and runs `status.js` from there, so the `board` arm, like the two harnesses below, runs from a detached worktree at that commit, and its portal is pruned and caught up first. Run from the local checkout, a `main` that lagged its `origin/main` measured the portal's vendoring against an engine CI never uses. An at-pin arm names its script by a path RELATIVE to `make-bus-leaflet`, because `atPin` re-roots the working folder and nothing else; the harness fails if a path is absolute.

**A chore on the board can still be a red push, so preflight asks that join itself rather than reading the board's exit code** (buses-data OA-445). The board keeps a portal vendored fixture that differs from buses-data out of its exit code, because the artwork is right and only a push is blocked. But `gates.yml` runs the portal's `fixtures:vendor` against the portal's `origin/main` on every buses-data push, and on 2026-09-23 preflight printed `0 would go red` for a push that step would have failed. The `portal-fixtures` arm runs `portal_fixtures.js` on its own, in the cheap tier, against the portal's `origin/main` rather than its disk. A check may declare exit codes as `cannotTell`, and this one declares `2` (no portal ref or no fixture folder), so a refusal is reported as UNANSWERED and never as a finding.

**A push that moves the engine pin, or any map's `ci-reference/`, also runs the two estate harnesses a pin bump fails on** (buses-data OA-462). On 2026-09-24 a push moving `engine.lock.json` passed the preflight with the board green, then failed `gates.yml` at *Prove the byte gates can go red*, because one harness's own control no longer reproduced under the new engine, and a harness control is not a board row. The `prove-red-gates` and `prove-red-status` arms run as `gates.yml` runs them, from `make-bus-leaflet` with `--buses` and `--portal`. Together they take about a minute and a quarter. A check may carry `when`, a list of path patterns, so these two are asked only when a pushed path matches. An unreadable scope or `--all` asks them anyway, and the report names every check it did not trigger under *what it did not ask*.

**Exit codes are this repository's: `0` nothing would go red, `1` something would, `2` it cannot tell you** — an undeclared repository, a branch with no upstream, or a check it could not run — **and `3`, DEFERRED: not yet.** A manifest may declare `pushInterval`, and `buses-data`'s built-in does (buses-data OA-525: about 65 billed `gates.yml` runs a day against an allowance a third of that). The preflight then asks FIRST when the last push-triggered run of that workflow started — of `gh run list` and of the checkout's reflog of the upstream, taking the later — and inside the interval exits 3 having run no check. Since buses-data OA-533 the interval is **paced to the month's Actions budget**: the allowance left, less a 10% reserve for PR and urgent runs, spread over the days left at the mean billed length of the last twenty runs, rounded up to a carrier step — 55, 115, 175 or 235 minutes, whole hours less five for the hourly tick's jitter. A spent month waits 235. When the budget cannot be read it is 175, and the report's `pace` line says why; the usage report needs the `user` scope on the `gh` token, granted once with `gh auth refresh -h github.com -s user`, from any folder. Do not push: the commits wait on local `main`, and the loop's hourly tick, which pushes whenever `main` is ahead of `origin/main`, carries them. Neither witness answering is not a deferral, and the report says the interval was not asked. `--urgent "<why>"` pushes inside the interval, for a red `main` or a cross-repository pairing only; a bare `--urgent` exits 2. A repository declares its own checks in a `.preflight.json` at its root, exactly as it declares its documentation scope; `buses-data` and `claude-skills` have built-in manifests, and a repository matching neither is a refusal rather than a clean bill of health. `npm run test:prove-red-preflight --prefix "C:/Buses/claude-skills/bus-work"` is the harness.

**`push_main.mjs` carries a deferred `main` to origin with no model in the loop** (the 6 October simplification review, B1/B2). Step 8 of the loop's tick has been the only thing that pushes a DEFERRED `main`, which made the hourly tick the push scheduler by accident; a loop cut to a few ticks a day would turn a wait of one interval into a wait of one tick, with local `main` the only copy of the commits. The script does step 8's sequence and stops at the first refusal: nothing ahead of `origin/main` is exit 0 with no lock taken; it takes `loop/LOCK.d` as `sched-push-HHMM` (a later tick may steal it once its 40-minute lease runs out, a person's lock past its lease is never stolen); it fetches and, only when `main` is behind, rebases (a conflict aborts the rebase and writes `loop/your-move/push-job-rebase-conflict.md`; tracked edits a person has not committed make it wait rather than rebase over them); it runs `docstamp.py` because a rebase runs no hook and commits what it wrote by pathspec, `[expected-red]` carried; then the preflight, and `git push origin main` on exit 0 ONLY, read back with `ls-remote`. It never passes `--urgent` and never force-pushes. Exits are this repository's: `0` pushed or nothing to push, `1` the answer is no, `2` cannot tell, `3` not now. `--repo` is required and is never defaulted, and without `--apply` it only reports. From anywhere; the repository is the one placeholder, the buses-data checkout whose local `main` is to be carried:

```bash
node "C:/Buses/claude-skills/bus-work/assets/push_main.mjs" --repo "C:/Buses/buses-data" --apply
```

**The same job keeps the engine checkout current** (buses-data, 2026-10-19). Nothing moved `C:\Buses\claude-skills` after a pull request merged, a tick may not move it, and on 2026-10-19 that had kept #383 away from the loop for over a day. So every `--apply` run, whatever the push did, fast-forwards the checkout the script runs from, which is the engine checkout because the scheduled task runs the engine's own copy (`--engine "<claude-skills checkout>"` overrides it, for a test). Its one write is `git merge --ff-only origin/main`, and it makes it only when the checkout is on `main`, nothing is mid-operation, no tracked file is modified, local `main` has nothing origin lacks and `loop/LOCK.d` is free, taking that lock for the moment of the merge so no tick's engine changes under it; it reads `HEAD` back against `origin/main`. A diverged `main` writes `loop/your-move/engine-checkout-behind-origin.md` at once; any other refusal writes it after six runs in a row (`STUCK_RUNS_FOR_HOLD`, streak in `loop/engine-ff.state.json`; a lock-held run neither counts nor ends it). Every run is an `engine` block in `loop/push-main.log`, and the step never changes the exit code. Cases 16a to 16q of `npm run test:prove-red-push-main --prefix "C:/Buses/claude-skills/bus-work"` hold it.

`npm run test:prove-red-push-main --prefix "C:/Buses/claude-skills/bus-work"` is the harness: real git against throwaway bare repositories, and each guard has been seen to fail when its one line is broken.

**A refresh row you have answered can be cleared without rebuilding the map (buses-data OA-205)**, because a `refresh` row is a JOIN against the newest scan report and otherwise comes back unchanged after every item on it has been worked to a *no rebuild* conclusion ([why](why-these-rules.md#a-refresh-row-that-could-not-be-cleared-oa-205-2026-08-31)). If you adjudicate a scan and the sheet does not need to change, **record it**, from the `bus-work` assets folder (`C:\Buses\claude-skills\bus-work\assets`); `--map` is the map's OWN folder, the one holding `manifest.json`, and `--scan` must name a report that exists under `_gtfs/upcoming/` or the command refuses:

```bash
node refresh_review.mjs --map "C:/Buses/buses-data/Areas/High Wycombe" --scan 2026-08-31 --verdict no-rebuild --by <this session's name> --note "what you found, in one sentence"
```

The row disappears and the worklist header says how many it suppressed and why — it is never silently dropped. **A newer scan brings it straight back**, because the match is on the scan date and nothing else, and `--verdict rebuild-needed` records the reading without silencing anything. **Adjudicating a town does NOT adjudicate a place inside it**: a place's frame draws a different set of services, so it keeps its own row and its own file.

**Re-adjudicating a scan you have already adjudicated REPLACES that scan's entry and keeps the one it replaced (buses-data OA-290).** Replacing is deliberate — `worklist.mjs` suppresses on one review per scan, and two entries for the same scan with opposite verdicts would leave the board's behaviour decided by whichever a `.find()` reached first. The displaced entry moves into `superseded[]` **on the entry that displaced it** — oldest first, flat rather than nested, so a three-step reversal keeps its middle — which leaves the board's join untouched; the tool prints what it displaced, and `--list` shows a superseded entry indented under the one that replaced it. An adjudication note is the evidence somebody assembled, not a status field ([what dropping one cost](why-these-rules.md#re-adjudicating-a-scan-oa-290-2026-09-09)). Falsified in both directions by `assets/prove-red-refresh-review.mjs`, whose control asserts that a FIRST review of a scan carries no `superseded` key at all — without it, a tool stamping an empty array on every entry would pass.

**The last three sources are read from THIS LAPTOP and are identical in every mode.** Only the portal queues change between `--local` and `--url`: a stale render, an upcoming BODS change and an unsent letter are facts about this disk, not about a portal. So the same correspondence row appearing in a dev run and again in a live run is **correct, and not duplication** — there is one draft on one disk, and it belongs to neither portal. If it ever appeared twice inside a single run, that would be a bug.

**Ranks 0 and 8 also reach the portal itself** (item 3, 2026-08-08): `push-status.mjs` POSTs the same `status.js --json` output to `POST /api/admin/status`, the portal stores the latest snapshot, and `src/worklist/index.js` folds it into ranks 0/8 there too — so a failing gate or a stale engine shows on the admin console's To-do tab and to a remote reader, not only to whoever last ran `--gates` on this laptop. It is a snapshot, not a stream: stale until the next push. Rank 7 (a BODS-flagged town with no portal map) is not pushed — it still only comes from this tool reading `_gtfs/upcoming` directly.

**Commitments are a source because nothing on disk changes when the answer is no.** Correspondence answers *is a real person waiting*; `Development Docs/commitments.json` answers *did we do the thing we said we would* — a letter we chose to write, a credential nearing expiry. `status.js` fails the board once a date passes, but a red CI run is a reminder only if somebody reads the email, so the same rows go on the list you actually work from. **It is deliberately silent until the date is close**, because a worklist that prints an obligation eighty days out is one nobody finishes. Retire an entry by DELETING it from the JSON, exactly as a finished OA file is deleted. Falsified by `node assets/prove-red-commitments.mjs`, which pairs every case: make the state and see the row, clear it and see the row go. ([why](why-these-rules.md#why-commitments-are-in-here-too-2026-08-31))

**Correspondence is a source because the human step is the only one nothing else watches.** Everything Claude can do is picked up by the next session; a drafted reply waiting for Peter to send it is not, and it is the step a person on the other end is actually waiting on. So rank 3 — an unsent draft — sits in *someone is blocked* rather than *your move*, because they are. ([why](why-these-rules.md#why-correspondence-is-in-here-at-all-2026-08-31))

**A thread may declare itself finished, and rank 2 then says nothing** — the declaration is read rather than inferred from the direction of the last message, because a courtesy acknowledgement is inbound like any other. A `CORR-nnn/README.md` silences its rank-2 row when **both** hold: its `**Status:**` begins with `dormant`, `closed` or `settled`, and the record's **docstamp is dated on or after that last inbound message**. The closed vocabulary means unrecognised prose keeps nagging, and the stamp brings the row back by itself when the correspondent writes again. **It suppresses rank 2 only.** An unsent draft at rank 3 is the one step nobody else can do, so no wording in a record we write ourselves can take it off the list — `prove-red-correspondence.mjs` asserts that directly, alongside the three refusals (stamped too early, unstamped, and a status reading `open`). ([why](why-these-rules.md#a-thread-may-declare-itself-finished-2026-09-07))

**One thing MAY move an unsent letter off rank 3, and it is a declaration rather than a wording.** A message whose header carries both `**Held:**` and `**Revisit when:**` demotes to **rank 9, WAITING ON OTHERS** — which is what a letter waiting on a condition outside this project is. **The condition is the load-bearing half**: a `**Held:**` with no `**Revisit when:**` leaves the row exactly where it was and says why, because a hold with no route back is how a letter is quietly abandoned. It demotes rather than disappearing, deleting the two lines puts it back the same minute, and a leftover hold on a letter that has **gone** raises nothing at all, because the rule is read inside the unsent branch. The convention is `Correspondence/README.md` in `buses-data`, deliberately not linked here because a relative link out of this repository resolves on one laptop only. Suppressed threads are named in `meta.correspondenceSettled` and printed to the console, because a suppression nobody can see is how a board starts lying. ([why](why-these-rules.md#a-held-letter-2026-09-17))

**A message's outbound state is read from its H1 as well as its `**Status:**` field, and either one saying it has not gone raises the row** — a contradiction nags rather than going quiet, and `\b` is what stops "redrafted" inside a title saying it was sent nagging for ever. **An inbound message answered in another thread carries `**Answered by:** <path>`, and the pointer must RESOLVE**, so a typo or a rename silences nobody; the suppressed thread is named in `meta.correspondenceSettled`, and the letter appears exactly once, in the folder it lives in. The convention for both is in `Correspondence/README.md` in `buses-data`, deliberately not linked. ([why](why-these-rules.md#both-ends-of-one-letter-were-wrong-2026-09-08))

**`loop_your_move.mjs` reads `loop/your-move/` in `buses-data`, the scheduled loop's whole outbound channel to a person** — a tick never asks a question; one that needs a decision writes a file there and stops, and nothing else enumerates the folder ([why](why-these-rules.md#the-scheduled-loop-had-a-channel-to-peter-oa-283-2026-09-08)). **one row per hold at rank 3**, in `SOMEONE IS BLOCKED` beside an unsent reply and for the same reason — only a person moves it, and every tick that fires meanwhile does nothing about it. Its title is the file's H1, its reason is the file's own *What is needed* paragraph, and its age is the date the file states, falling back to mtime. **A hold that has been decided carries `**Decided:**` and `**Revisit when:**` fields above its ask**, and then its row is titled *Decided, nothing to answer* and its reason is the decision and not the ask (10 October 2026: the ask is written first and goes on describing what is already done); the banner over a row it blocks reads `ON HOLD, DECIDED`. Neither field makes a file a hold or removes it from rank 3, and the `/triage` command in `buses-data` skips a file that has them. A hold may also name the rows it contradicts in a **`**Blocks:** <key>`** field (write a key that contains a space, such as `engine-rebuild-High Wycombe`, in backticks, or it is split into two words that match no row), and each named row is then **annotated, never dropped**: the warning prints above the row's commands and gates them behind *Only once that is settled*, so the row keeps its place, its age and its link but cannot be read as an instruction. **One exception folds rather than annotates** (buses-data OA-574, 11 October 2026): an `engine-rebuild-*` row whose map the weekly shadow rebuild, on the pinned or live engine and after the build, found **regressed** is the hold's own question, so `foldHeldRows()` takes it off the board into the hold row's `folded[]` and prints it under the hold as *carries …*; `meta.folded` lists each one. A held row with no such regression keeps its annotation. A `Blocks:` naming a key that is not on the board today is reported as a warning rather than ignored, for the reason `adjudicated` is printed — a stale hold is how a convention quietly stops working. Both halves also ride in `--json`, on the item as `onHold` and in `meta.warnings`.

**The DRAFTS in the same folder have a row too**, because nothing in the loop will ever action one and without a row nothing enumerates them ([why](why-these-rules.md#the-drafts-row-2026-09-10)): **one row for all of them at rank 7**, the bottom of `YOUR MOVE`, with the count, the oldest age and each draft's H1, date and tick. The three dispositions are on the row: promote (a `**Promoted:**` line under the H1, then move to `adhoc/ready/`, where the ad-hoc loop takes it), file (an OA, then move to `loop/retired/` saying where it went), decline (a `## DECLINED` section, then `loop/retired/`). An answered hold also moves into `adhoc/ready/`, and a hold a tick or `adopt.mjs` retires goes to `loop/retired/` (buses-data OA-610; `loop/adhoc/` before that). Never delete one; the reason is the record.

**Holds and drafts share one folder, and the FILE says which it is rather than the folder** (OA-401): a *What is needed* section or a `**Blocks:**` field makes it a hold, and neither makes it a draft. A misfiled hold is read as a draft, which is a lower place and never a silent one, and a draft that grows an ask is promoted at the next run. `adhoc/ready/`, `doing/` and `done/` are a different channel — Peter's in-tray INTO the ad-hoc loop, its crash rule, and nobody — and `prove-red-loop-your-move.mjs` holds that line with a file in each, alongside a case that the partition is total and disjoint so nothing can be counted twice or lost between the two readers. ([why](why-these-rules.md#one-folder-for-holds-and-drafts-oa-401-2026-09-18))

**`adopt.mjs` is the one way a tick commits a file it did not write** (buses-data OA-542). It covers two cases. Under rule (a) it commits a modified tracked file that a live hold names in its `**File:**` field, when `git diff HEAD` is exactly the hold's ```` ```diff ```` block, and then retires the hold. Under rule (b) it commits a modified `.md` under `Documentation/`, `Development Docs/` or `BusMapsUK/` that has been untouched for 30 minutes, with check-tables, check-doc-links and check-file-hygiene green. It never commits under `Correspondence/`, `Areas/` or `Places/`, and never anything untracked, staged or deleted. Each path gets its own pathspec commit, subject `adopt: Peter's edit to <path>`, and the commit is read back afterwards. So **a hold that asks Peter to edit a tracked file spells the edit out as a `diff` block**, or the tick cannot adopt it. `prove-red-adopt.mjs` breaks every guard in a copy of the module and requires a case to go red. ([why](why-these-rules.md#a-tick-commits-the-edit-peter-finished-as-asked-oa-542-2026-10-01))

**A branch that was never pushed has to be looked for, because `countUnpushed` cannot see it.** That count, in the conditions block above, takes `<basis>..HEAD` in the three main checkouts, so it answers only for the branch each checkout happens to have out; a branch held in a git **worktree** — or checked out nowhere at all, the normal end state once a worktree is removed — is invisible to it. A tick pushes at the end of its unit behind the push preflight (buses-data OA-394), so a row here means a push that did not happen rather than one that could not. ([why](why-these-rules.md#stranded-branches-and-the-channel-that-was-missing-oa-326-2026-09-12))

`unpushed_branches.mjs` asks the question of every local branch instead: **one row per stranded branch at rank 3**, in `SOMEONE IS BLOCKED`, carrying the branch, its age, its insertion count, its last commit subject and a self-contained `git -C "<repo>" push -u origin <branch>`. **Computed rather than declared**, which is the point: extending `loop/README.md` to tell every tick to declare its own residue would have been the cheaper change and it is the wrong one, because a declaration can be forgotten and on the day this was found it had been. A branch that a `loop/your-move/` hold **also** names still raises its row — the computed half must be loud exactly where somebody remembered, or it could not be told from the half that is silent where nobody did.

**The trap is that it must be computed from PATCH IDENTITY, never from ahead-count.** The portal squash-merges with `delete_branch_on_merge` on, so every branch it has ever merged stays ahead of `main` for ever: measured there on 2026-09-12, **34 local branches, 27 ahead of `origin/main`, 8 unmerged by `git cherry`, 6 raised**. A row built on ahead-count would have raised 27 items of which 24 were finished work, and it would have been muted inside a week. **And `git cherry` is not enough on its own, which was measured rather than reasoned**: a squash of a *single* commit keeps that commit's diff, so its patch-id still matches and `cherry` correctly says merged — but a squash of *two* produces one diff matching neither, so `cherry` calls it unmerged for ever. Both of the portal's two-commit strays are exactly that, `schema-note-token-column` (landed as `a12d247`, #127) and `tabs-read-as-buttons` (`709a9b5`, #125). The discriminator that rescues them was already on the disk: their upstream is **recorded and gone**, which in a repository that deletes a branch on merge is the remote saying the work landed.

**What it does not ask, said at the point of the narrowing — and the half that WAS built on 2026-09-21.** OA-326 specified `gh pr list --head <branch>` as the second half of the test, and this source still does not make that call: `worklist.mjs` touches the network only in `--url` mode, and a board opening a socket per branch would fail on a train. So a branch that **has** been pushed raises nothing here, whether or not a pull request is open for it, and the pushed-but-unmerged count is printed as a warning so the half not being asked is visible rather than silently absent. What has changed is that the question now has an instrument of its own, in the directory sweep's shape: `pr_sweep.mjs` below.

**Its first real run named six branches, three of which nothing in the estate knew about** — `oa059-pinned-dp`, `oa322/place-page-size-literal` and `oa323/tier-4-1-for-the-place-skill` in `claude-skills`, 574 insertions between them, none of them mentioned in any hold. `prove-red-unpushed-branches.mjs` builds a bare origin, a clone, a worktree and a squash-merge history under the temp dir, and **five of its assertions are controls asserting silence**, because the way this source realistically fails is by being right too often. A six-mutation sweep watched all six go red, and two of its results are worth carrying: replacing patch identity with ahead-count reddens **exactly one** assertion, the single-squash control, so that control is the whole defence against the change the module argues hardest against; and *each says how much work is sitting there* was first written as `/insertion/` over the row's own sentence, where it could not fail — the word is there whatever the number is — so it asserts the count now.

**The pull-request half, and why the guarantee above turned out to be too weak (OA-326 item 1, 2026-09-21).** The narrowing rested on *a pushed branch is on GitHub for anyone who looks*, and the measurement is that nobody looks: portal [#170](https://github.com/PeterC66/community-bus-maps/pull/170) was open **21 days** and named on no list until the day it merged, dependabot [#64](https://github.com/PeterC66/community-bus-maps/pull/64) has been open **31 days**, and #284 and #285 eight days each. `pr_sweep.mjs` closes it without putting a socket in the board: `node pr_sweep.mjs` asks GitHub and writes `loop/pr-sweep.json`, and the board only ever reads that record — the writer sits behind an entry-point guard, the reader is pure and takes its clock as an argument, and `worklist.mjs` imports the reader alone. The record is gitignored by `loop/*`, which is required rather than convenient: it is dated, and **a generated file under byte comparison must not read the clock**.

**A protected repository's own `main` is asked too (OA-326 item 2, 2026-09-23).** The branch rows skip the trunk by design, and the conditions block reports commits on `main` as a bare count — the right answer for buses-data, where a push is the remedy and the loop makes it. In the two PR-per-change repositories a direct push of `main` is refused, so those commits have no route to the remote but a branch and a pull request, and until now nothing said so. `trunkAhead()` in `unpushed_branches.mjs` raises `unpushed-branch-<repo>--trunk` at rank 3 when the local trunk holds commits that **no other ref, local or remote, carries by patch identity** — a cherry-pick onto a worktree branch changes the SHA and keeps the patch, so `--contains` would have raised a finished hand-off. A pushed carrier is `pr_sweep.mjs`'s to judge and an unpushed local one gets its own stranded row, so in both cases the trunk row stays silent and a warning names the carrier. `prove-red-unpushed-branches.mjs` section 6 walks one clone through level, one commit, branched and pushed, cherry-picked, partly carried and locally carried, with a direct-push control; three mutations — ancestry-only, patch-only and no protected-repository guard — each went red.

**Finished worktrees are swept, not remembered (2026-09-23).** Every session was told to remove its worktree when the PR merged, and on 2026-09-23 the three repositories held 34 worktrees of which 25 were merged, plus two empty folders git had forgotten. `node worktree_sweep.mjs` (from this skill's `assets/`, no placeholders) reports what it would remove; `--apply` removes it, and Windows Task Scheduler runs `--apply` weekly as the task *BusMaps worktree sweep*. A worktree goes only when its HEAD is on `origin/main` or is inside a MERGED pull request's head (the public repositories squash-merge, so ancestry alone reads every merged branch as unmerged — and a PR state alone would delete a commit made after the merge), it is clean, unlocked, holds no symlink or junction, and nothing git records for it has moved for 24 hours. Removal is `git worktree remove` without `--force`, and the local branch goes with it. **The no-link refusal is load-bearing, not a second layer** (2026-10-13): a plain non-forced remove of a clean buses-data worktree still carrying `stage.js attach`'s junctions exited 0 and emptied a map's S4–S6 runs in the main checkout. A person clearing a row the sweep raised for a link — or removing any worktree by hand — runs `node remove_worktree.mjs "<worktree path>" --apply` from this skill's `assets/`, where `<worktree path>` is the worktree's root as `git worktree list` prints it: it unlinks a link only when it points at the main checkout's own folder at the same path (what `attach` and the push preflight make), restores the tracked files that leaves missing, refuses any other link untouched, and then removes without `--force`. Without `--apply` it only reports. **Branches are swept too (2026-09-28)**: claude-skills had no "delete head branch on merge", and it held 113 remote branches, 107 of them merged, plus 46 merged local branches that had never had a worktree. After the worktrees, every local branch not checked out anywhere and every `origin/*` branch is deleted when the same MERGED proof holds for its tip, no pull request from it is OPEN and its tip has not moved for 24 hours: a local branch with `git branch -D`, a remote one with `git push origin --delete` (a pull request's "Restore branch" undoes it). `main` is never a candidate. An empty folder under a `.claude/worktrees/` or the old `claude-skills-wt/` sibling that no worktree is registered at is deleted; one with files is not. The record is `loop/worktree-sweep.json` in the pr-sweep shape, and the board raises a row only for a merged worktree the sweep refused to touch, a forgotten folder with files in it, a kept worktree that is outside its repository's `.claude/worktrees/` (2026-10-20; a tool's scratch under the temp folder excepted — the first read found two claude-skills worktrees under `C:\u3a St Ives\.claude\`, made there by docs that still named a pre-move sibling folder), or a sweep more than eight days old. `prove-red-worktree-sweep.mjs` runs the writer against throwaway repositories, and a six-mutation sweep watched each refusal go red.

**The same weekly sweep also clears the portal tests' scratch from the temp folder (2026-10-14).** On 2026-10-14 `%TEMP%` held 62,823 entries, 36,858 of them folders the portal's test scripts had made with `mkdtemp` and never removed (2.3 GB, the oldest from 31 August; 118 scripts make one and 77 mention a removal, on the success path only). `temp_sweep.mjs` (from this skill's `assets/`, no placeholders; `--apply` to remove, `--temp "<folder>"` to sweep another folder in place of the user's temp folder) removes a directory whose name starts `cbm-`, `portal-deps-`, `prove-red-status-` or `sheets-` and whose own modified time is 24 hours old or more, and nothing else in that folder. A scratch folder holding a junction into a live worktree is not refused, because it would then pile up: each link entry is unlinked first, checked gone, and only then is the rest deleted; `prove-red-temp-sweep.mjs` holds the control, a junction whose target must keep its file. A folder a program holds open is left for next week and is not a failure; the result is written into `loop/worktree-sweep.json` under `temp`.

**Two questions, each asked with the instrument that can answer it, and neither derived from the other.** `gh pr list --state open` once per repository finds a stall and cannot miss one; `gh pr list --state all --head <branch>`, asked **per branch and over every state**, answers *has this branch ever had a pull request*. The second form is not a preference. On 2026-09-19 a tick scanned the branches this board prints and inferred absence from a list it had already filtered to OPEN, and reported that `worklist-demo-applications` had never had a pull request at all — #170 had been open on it for nineteen days, and the claim was repeated to Peter two days later before anybody checked it. **Inference from a filtered list answers ABSENT, and absent reads as a finding**; a branch with no pull request and a branch with a stalled one are different faults wanting different fixes, and no amount of branch-scanning would ever have surfaced the second.

**Four rows, and the silence is again the common case.** `pr-sweep-stalled-<repo>-<n>` and `pr-sweep-no-pr-<repo>-<branch>` at **rank 3**, `pr-sweep-due` and `pr-sweep-record` at rank 8; `needsOf` answers `[]` for the first two on the same load-bearing argument as `ci-red-` and `unpushed-branch-`, because `--safe-only` must never hide the row saying finished work has been sitting open for three weeks. A **DRAFT raises nothing** and is carried in a warning — `claude-skills` #3 and #4 forbid their own merge in their titles, and a row nagging about those two daily would be muted inside a week and would take the other rows with it. Staleness is measured from `createdAt`, **not** `updatedAt`, and that was measured too: #64 read 31 days open and 10 days quiet, so an activity test is reset by a bot comment and a pull request nobody means to merge evades it for ever while looking busy. The last-activity age is in the row's detail and is never the trigger. **The threshold is two days and the sweep's cadence 24 hours** (seven days and 48 until 2026-10-14, Peter): of the last hundred closed pull requests in each public repository not one had stayed open a day, so two days is already stuck and the lower figure raised no row on that history; the bus loop refreshes the record at 20 hours so the cadence row seldom shows.

**`prove-red-pr-sweep.mjs` is fourteen sections and a nine-mutation sweep put all nine red.** Section 11 is the one holding the shape in place: it asserts that the half `worklist.mjs` imports runs no `execFileSync` and no `gh` call, so nobody can "tidy" the sweep into the board. Section 8 is the one it was written for, asserting against a stubbed GitHub that the per-branch query carries `--state all`, that a MERGED pull request answers it, and that a **refusal is not an absence** — `gh` failing leaves the branch unmentioned rather than inventing a finding out of a network error. Two results are worth carrying. The entry-point guard cannot be written as `new URL(import.meta.url).pathname`: on Windows that is `/C:/…`, the comparison silently fails, and the sweep becomes unrunnable with no error to read. And a **missing row must fail the assertion that names it, not throw on the line after it** — widening `STALE_DAYS` first killed the harness with a stack trace instead of naming the control it had broken, so every indexed read goes through `one()`.

**A check that runs by hand runs once, unless something asks — so the national bus-map directory gets a MONTHLY row (OA-308, 2026-09-11).** `BusMapsUK/bus-map-directory/` records, for every English local transport authority, whether it publishes a bus map and where; it is a hundred-odd URLs belonging to seventy-six councils, and it rots without anybody here touching a file. `directory.mjs --links` is the check, and OA-308 ruled it **out of CI on purpose**: a council page dying on a Tuesday would turn `main` red with nobody having committed anything — the calendar-red shape OA-289 took out of the backlog index — and `buses-data` is the one repository in the estate whose Actions minutes are billed. That reasoning is sound and it leaves the check with no reader, which is what this row is. **It opens no socket.** The sweep WRITES `link-check.json`; `directory_links.mjs` only ever reads it, because a source that fetched 109 council URLs would turn a half-second board into a minute-long one and fail on a train.

**DEAD outranks DUE, and BLOCKED raises nothing at all.** Running the sweep is housekeeping; a dead link is a row of the directory pointing a member of the public at a 404 while the `/maps` panel tells them their council publishes a map, so it sits at rank 7 and names every URL with the directory rows citing it. A **BLOCKED** result is a bot wall refusing an automated reader — on the checker's first run 12 of the 14 "dead" links were HTTP 403 on pages the survey agents had opened in a browser that same morning, which is *the refusal read as an absence* — so blocked URLs are recorded, counted in the row's prose where a reader can see them, and are never a reason to act. The trigger for the whole source is `directory.json`, not the record: a tree with no directory is silent, a tree with a directory and no record has **never been swept**, and collapsing those two would make "never run" indistinguishable from "not applicable".

### The weekly document triage — `doc_triage.mjs`

**Two of `buses-data`'s document checks can never run in CI**, because their subjects do not survive `actions/checkout`: `list-archive-candidates.mjs` asks whether a dated document still has live work behind it, and `check-memory-paths.mjs` asks whether Claude's memory stores still point at files that have moved. `Development Docs/README.md` said since 2026-09-21 that the loop's weekly triage runs the first of them. **Nothing did** — grepped on 2026-09-22, the only things naming that script were four documents inside `buses-data`. The sentence described an intention and no move executed it, which is *a rule that is consulted is not a rule that is executed* with a whole recurring job as its subject.

**`doc_triage.mjs` is that move.** It runs both with `--json` — nothing here greps a report — writes `loop/doc-triage.json` as the stamp the loop prompt's `find -mmin 10080` test reads, and writes ONE draft, `loop/your-move/doc-triage.md`, when there is something to say. The draft carries no *What is needed from you* and no `**Blocks:**`, which is what makes it a draft rather than a hold: an archive candidate is a question and a stale memory path is a chore, and neither blocks anybody. It needs no worklist row of its own, because `loop_your_move.mjs` already counts every draft in that folder at rank 7.

**It is READ-ONLY on the memory store, deliberately.** `check-memory-paths.mjs --apply` is mechanical and harness-backed, and running it here would save a step. It is not run, because that store is in **no repository**: an unattended write to it leaves no diff anybody can review and nothing to revert to. The draft carries the exact command and a person runs it — the same line the estate already draws, that a tick may write where the history is readable.

**Since 2026-09-23 it runs a third, `list-not-filed.mjs` (buses-data OA-446).** Asked that day what reminds Peter that a plan in `Development Docs/` holds a step nobody filed, the answer was nothing: `check-doc-coverage.mjs` asks whether a DOCUMENT is held by a live row, never whether every ITEM in it is, so a plan with five steps and one row passes. An item a document deliberately leaves is now a line beginning `**Not filed:**`, and the draft lists each one with its document and line. Its subject does survive `actions/checkout`, unlike the other two; it lives here anyway because it exits 0 whatever it finds, and a question in a CI log has no reader. **Prose saying "not filed" is deliberately NOT searched for** — two such sentences in the 2026-09-17 process review were false by the day this was built, both halves having been filed later, so a grep that trusted prose would list finished work every week.

**A half it cannot run is exit 2, never a clean report**, and that is what `prove-red-doc-triage.mjs` spends its refusal cases on: a checker missing from disk, a checker that refuses, a checker whose output stops being JSON, and a buses tree older than the third checker. A triage that silently drops one half and prints *nothing to do* about a question it never asked would be the original fault wearing the fix's clothes. The controls hold the other half — that a run finding nothing **still stamps**, so the tick does not redo the work every tick, and that a draft already in `loop/your-move/` is **left exactly as it was**, because a draft is Peter's to move and a tick that tidied one away would delete the record of the finding with it.

**The limit, stated rather than hidden: a stopped loop runs no triage.** If `loop/STOP` is up for a fortnight these two questions go unasked again, exactly as before. That is visible — the board prints the loop's idle age — but it is not the same as a guarantee.

**Absent is the normal state, and that is what makes this hard to falsify.** `loop/` is gitignored in `buses-data` apart from its README, so the folder does not exist in a clone, a worktree, any other harness's fixture, or CI — the named shape *the subject that does not survive `actions/checkout`*, where a check is green for ever because its subject was never there. `prove-red-loop-your-move.mjs` therefore builds **real folders on disk** rather than injecting a fake reader, which is also why `readYourMoveDir` does its own I/O. A mutation sweep watched all eight mutations go red, and **two of them survived the first draft of the harness** and are worth knowing: an `existsSync` precondition in front of the `try/catch` could be deleted with everything still green, because `readdirSync` already throws for all three cases — *the check that could not go red*, so the redundant guard was removed rather than the assertion added; and `src.includes('for (const it of loopHolds.items) add(it);')` passed with the wire **commented out**, because a commented line still contains the string, so every source assertion now asks whether the line RUNS.

Every case there is a pair: make the state and see the row, clear the state and see it gone. Appearing is only half of it — a row still nagging about a letter that went out last week is a row that gets ignored, and then so is every row beside it. **The third is the same argument turned round and is the more dangerous half**: a refresh row suppressed by a review that never lifts has been silently deleted, and nobody would find out — so its cases prove a NEWER scan brings the row back with the old review still sitting in the file, and that an unreadable review file fails safe rather than quiet.

### The weekly shadow rebuild — `shadow_rebuild.mjs`

**Every map is gated against the engine commit that drew it (buses-data OA-430), which proves it reproduces, not that today's engine still draws it acceptably** — so the first customer change to an old map inherits every engine change since, all at once, and nobody has looked at any of them. `rollout.js` and `rollout_places.js` have written a verdict per map with `--json` since claude-skills #242 (`clean`, `regressed` or `unmeasured`, the rules in `make-bus-leaflet/assets/rollout_report.js`). **`shadow_rebuild.mjs` is the job that asks every week** (buses-data OA-485 item 1): both rollouts `--all`, dry run, into a scratch folder, and both reports whole in `loop/shadow-rebuild.json`, the stamp a loop tick's `find -mmin` test is to read, as `doc-triage.json` is — the loop prompt does not run it yet; that is OA-485's next step. On the estate at `83a53865e1` it took under a minute.

**It never applies, and it checks that rather than trusting it.** Neither rollout is ever passed `--apply` or `--force`; a report that says it applied is refused; and `git status -- Areas Places` in the buses tree is read before and after, so a dry run that wrote into a map folder is refused however clean its report. It commits nothing and touches no tracked file — not `ci-reference/`, not a manifest.

**A regressed map is an answer, not a failure.** `rollout.js` exits 1 when a map would lose a label or raise a blocking warning, which is exactly what this job counts, so it exits 0, names every regressed map and stamps. `regressed` means LOOK: the lost-label rule cannot tell a deliberate change (OA-437's three-bullet *How to use*) from damage.

**So a regressed map comes with a picture** (OA-485 item 2, the visual diff). Both rollouts run with `--keep`, which keeps each map's built sheets past the dry run. For every REGRESSED map, each built sheet is compared with the shipped one, with the footer's build stamp neutralised on both sides as `ink_review.mjs` does. A sheet whose only change is that stamp is `unchanged`. Any other sheet goes through `crop_compare.js --diff 3`, which gives the three places its ink moved most as shipped/built pairs in `loop/shadow-rebuild-crops/`. That folder is emptied on each stamped run and left alone by a refused one. Each map in the stamp carries `visual`, naming its pair files per sheet. A clean map is never cropped. A crop that fails is a note on that sheet and never a refusal.

**A half it cannot run is exit 2 and NO stamp**, so the next tick asks again: a rollout missing from disk, one that refused or died, one that wrote no report, or JSON that is not a rollout report. A shadow rebuild that dropped the place maps and stamped the towns would call half an estate the estate. `prove-red-shadow-rebuild.mjs` holds each of those, and that each rollout was called `--all --json` and nothing else. The board count read from the stamp, the quality metrics and the hard-collision count are OA-485's later items; nothing here writes a board row.

From `C:\Buses\claude-skills\bus-work\assets`, with no placeholders:

```bash
node shadow_rebuild.mjs
```
