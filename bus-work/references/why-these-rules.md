# Why these rules — the incidents behind `bus-work/SKILL.md`

**For:** anyone who has read a rule in the skill and wants to know what earned it, or who is about to argue it away.

`SKILL.md` states each rule and points here; this holds the incident, the measurement and the argument. The split was made on 18 September 2026 by buses-data OA-399, R6 of the 2026-09-17 process review, on the finding that a scheduled tick read about fifty thousand words before acting, and that volume was the cause of the thing Peter reports as *Claude does not follow my instructions*. `bus-work/SKILL.md` was 13,560 words of it.

**Nothing below was rewritten in the move.** The sections are the sections that stood in `SKILL.md`, carried across byte for byte, so the argument survives the shrink and the diff stays readable. Read the section a rule names; read further only when a rule does not fit what you find.

**A companion, not a second skill.** If you are adding a rule here rather than to `SKILL.md`, you are writing a rule nobody will read. Put the rule there, in a sentence, and the reason here.

### Is it safe to do this right now? — the concurrency verdict (OA-221, 2026-09-01)

**Peter can run this at any hour and be told, rather than having to work it out.** Printing the list is read-only; *carrying an item through* writes into a working tree several sessions share, sometimes sweeps the whole estate, and sometimes deploys. So every row carries `SAFE NOW`, `CHECK FIRST` or `BETTER TO DELAY`, and a `CONDITIONS` block above the bands states each contended fact **once** — the three working trees (this one, the engine repo, the portal), which open actions other sessions have claimed — with any claim older than today marked stale — and what that means. The rows then name what is contended instead of repeating the sentence; an early version printed the full reason on all nineteen rows and buried the titles it was meant to help you read.

**Answer "can I do anything at all right now?" without gathering a single queue** with `node "%BW%\worklist.mjs" --conditions` — it reads three working trees on this disk, never asks a portal anything (so it works with no token configured), and classifies the standing commands that are *not* worklist rows: `--gates`, `push-status.mjs`, `rollout.js --apply`, `quality_gate.js --accept`, `npm run deliver`, `npm run deploy`. `--safe-only` filters the list itself, strictly — a `CHECK FIRST` row is workable and is still hidden by it.

**What the three verdicts mean, and why only two things ever earn a delay.** `git status` cannot say *whose* uncommitted files those are — yours and a neighbour's look identical — so a dirty tree is `CHECK FIRST`, meaning read what is actually there — **with one subtraction, since OA-301 (2026-09-10): a modified `Correspondence/**/*.md` that a live `loop/your-move/` hold names in its `**File:**` field is accounted for and left out of the `buses-tree` and `estate-sweep` counts.** A hold is the one thing on this disk that CAN say whose file it is, and a letter with Peter's salutation typed into it is the normal state of that folder, so before the subtraction the loop idled twelve of eighteen ticks in a day behind one such file. The conditions block still lists the file as uncommitted and prints an `accounted` line beneath naming the hold, so the subtraction is shown rather than trusted; the scope is that folder and `.md` only, because a hold naming residue under `Areas/` describes something the next commit could sweep and the tree is right to stop on it; and only a hold that is in the folder NOW counts, so retiring the hold puts the file straight back into the verdict. `BETTER TO DELAY` is reserved for two recorded faults: an estate-wide sweep while `Areas/`, `Places/` or `ci-reference/` has uncommitted files (the `quality_gate.js --accept` case, which has happened), and a deliver or deploy whose SCRIPT in the portal checkout differs from `origin/main`. **Not whose branch differs — corrected by buses-data OA-375 (2026-09-24).** This page used to say `npm run deploy` ships the checked-out commit, and it does not: every step of `scripts/deploy.mjs` is an `ssh`, and the commit that goes live is whatever the host's own `git pull` brings; `deliver-map.mjs` likewise `scp`s renders up from buses-data. The laptop supplies only the script and the local modules it imports, so `readRecipes()` compares those, and the npm script line, as the working tree against `origin/main`. A feature branch whose recipe matches is `SAFE NOW` for both commands — the state of 2026-09-15, when the old reason stood in front of the one deploy that cleared the estate's only red — and a recipe it could not compare is the stricter answer and says so. A DETACHED portal checkout is still judged by OA-387's residue rule, unchanged.

**Dirt in one town's folder is that town's business** (buses-data OA-434, 2026-09-22). One uncommitted path anywhere used to make `buses-tree` `CHECK FIRST`, and since nearly every unit needs `buses-tree`, one stray file stopped the whole loop. On 2026-09-22 four ticks in a row did nothing: three stopped on Peter's half-edited letter in `Correspondence/CORR-010/`, and one on an untracked `disagreements.docx` under `Areas/Chatteris/` that was byte-identical to a committed copy. None of them meant to write into either folder, and a tick commits by pathspec. So unstaged dirt inside one `Areas/<X>/`, `Places/<X>/` or `Correspondence/CORR-nnn/` folder is **fenced**: it leaves `buses-tree` and is counted by `buses-maps`, which map builds, S6, the byte gate, rollouts and correspondence rows need. A staged path, anything under `ci-reference/`, and a file directly under one of those roots are never fenced, and a mutant for each is caught by `prove-red-concurrency.mjs`. `buses-maps` is deliberately coarse: any fenced file stops every map or letter unit, because no row can name its folder reliably.

**The unpushed count says what it counted against, and a count it could not take is not a count of zero** (buses-data OA-313, 2026-09-11). `@{u}..HEAD` answers only where the branch has an upstream, and a branch created locally has none until its first push — so the portal, which is PR-per-change and therefore begins every piece of work on a fresh local branch, was the one repository where *is there finished work nobody has pushed?* could not be answered. It read `unpushed: None` over twenty committed files and a thousand lines of OA-308 while counting `buses-data`'s single commit correctly. The count now falls back to the remote's own default branch — `origin/HEAD`, then `origin/main`, then `origin/master`, each verified to exist before it is counted against — and the conditions line says `ahead of origin/main; this branch has no upstream` whenever the basis is not the branch's own upstream, because *3 commits ahead of origin/main* and *3 commits your upstream has not seen* are different sentences. Where neither basis exists the reason is printed as `unpushed UNKNOWN — …` and `portal-write` reads `CHECK FIRST` rather than staying silent: a null there was the shape this estate names *the refusal read as an absence*, and the silent direction is the one that ships a deliver against fixtures GitHub has never seen. The case the harness guards is the empty one — a freshly cut branch with no commits on it must report **0**, not the base branch's own history.

**A claim older than today is MARKED, and the marker is about AGE rather than liveness (2026-09-13).** The block listed every claim with its age in days and said nothing about any of them, so on the day this was written six claims printed alike — five held by sessions that had ended days earlier, one being worked at that moment — and a session reading the board asked the obvious question: does this tell me which to release? It did not. `assemble.mjs --who` is the only thing in the estate that says STALE and prints the `--release` command, nothing runs it for you, and meanwhile each dead claim went on refusing `--claim` to everybody, the scheduled loop included. Every claim made **before today** now carries `<< STALE, n day(s) old`, and one summary line beneath the list names the count and the command that can clear them. **The threshold and the wording are `assemble.mjs`'s own** — the two are read side by side and two thresholds that disagreed would be worse than either. **It is an AGE, and the line says so in those words**: this board cannot tell a dead session from an idle one, and its own `activity` line two rows below is explicit that *an idle prompt looks the same as gone*, so a marker phrased as liveness would be a claim nothing here has evidence for; what it does know is the date somebody wrote down and the estate's rule that a session does not live overnight. **A computed age is safe here and was removed from `open-actions.md` for good reason** (buses-data OA-289): that file is generated and byte-compared, so an age in it turned `main` red on the calendar once a day for as long as a claim was held, whereas this is a report recomputed on every run and compared to nothing. A `selected:` date that will not parse is **not** marked — *could not look* is a third answer and never a finding. `now` was made injectable into `readClaims` so the harness can set the date; without that, a case about an age can only assert it against the day it happens to run. **Since buses-data OA-400 (R7, 2026-09-18) such a claim EXPIRES**: `--claim` takes it without `--force`, so the marker reads `EXPIRED` and the summary prints that `--claim` rather than telling anyone to release it — the board said *release it* for three days after the rule changed, beside an `assemble.mjs --who` that said *nothing needs releasing*.

**A decision is never held back, and that is the most useful thing on the list.** A publish review, an organisation application, a map-request decision, a chase, and a drafted reply Peter has to send touch no working tree at all, so nothing happening on this machine can spoil them. When everything else says wait, those are what to offer.

**It is falsified**, from this folder, no placeholders: `node prove-red-concurrency.mjs`. It builds throwaway git repositories to prove the reading is real, drives the rules over synthetic conditions to prove each verdict both appears and clears, and asserts a clean machine says go — which is the control that stops a rule returning `CHECK FIRST` for ever and passing every red case. It found a real fault on the day it was written: the estate-sweep rule was reading a flag stored beside the paths instead of the paths themselves.

**The `activity` line counts TURNS now, not file writes, and the thing it used to count was bookkeeping (2026-09-10).** It read each session transcript's mtime, and on 2026-09-10 `sched-1715` was shown `2 session transcript(s) written in the last 20 min` while deciding whether the obstruction in front of it would clear itself: one was the tick itself, and the other was a tick that had stopped at 10:23Z, whose file carried an mtime of 16:14Z because something had appended a `last-prompt` and a `custom-title` record to it — **neither of which carries a timestamp at all**. So the reader now takes the greatest `"timestamp"` in the tail of each candidate file, capped at the mtime, and the mtime survives only as the prefilter that keeps it cheap: an append moves an mtime forward and never back, so mtime-in-window is a strict superset of turn-in-window and the tail read happens for a handful of files rather than the 298 that get statted. Where the content cannot answer — no timestamp, an unreadable file — **the mtime is still used**, because the floor for this signal is what the proxy already gave. A file demoted this way is named in the line rather than quietly dropped. **It is still context and still never scored**: this closes the third way it was wrong, and the two the tool's header names — an idle session sitting at a prompt, a crashed one with a fresh transcript — are properties of what a transcript *is*, which no amount of reading it more carefully touches. The function had no falsification case at all until this fix, which is the standing hazard of a signal that is never scored: nothing goes red when it lies.

### The scheduled loop holds a lock, and this is where you see it (OA-287, 2026-09-08)

**The loop takes `loop/LOCK.d` before it does a unit of work, and until now nothing you run could see it.** A tick takes the lock at step 3 of its stored prompt, writes its name and a lease into `holder`, and a later tick refuses to steal from any holder whose first line is not a `sched-` name. That half was written, falsified and deployed. The other half did not exist: this skill never mentioned the lock, `concurrency.mjs` never read it, and an ad-hoc manual prompt was told nothing — so a session started at 20:05 walked straight into a tick that took the lock at 20:00 and was forty minutes into an S6 red team. **A mutex taught to one party is not a mutex, it is a log.**

**And it could not have been fixed by reading `git status` harder.** `loop/` is gitignored, so the lock directory can never appear as an uncommitted file in the `buses-tree` verdict; the one signal a manual session already consulted was blind to the loop's existence by construction. It is now the `loop-lock` resource, so a live tick shows up as `BETTER TO DELAY` on every row that touches the shared trees, named in the same `CONDITIONS` block as everything else.

**Take the lock yourself before heavy work, and release it afterwards.** Not for ordinary document or backlog work — several sessions run here at once and must keep doing so, and a lock meaning *I am working in this repository* would serialise sessions that coexist fine on the stage-by-name and pathspec discipline, which is how it would come to be routed around. Take it for the work that cannot tolerate a second writer: **an S1–S6 map build, an estate sweep or rollout, `quality_gate.js --accept`, or an engine change.** From the buses repository root, `C:\u3a St Ives\Using AI\Buses`, with no placeholders:

```bash
mkdir "loop/LOCK.d"
```

A non-zero exit means somebody already holds it. Then write `loop/LOCK.d/holder` with **your session name first** — the name `ListAgents` gives this session — then the time, and a second line `expires:` at most ninety minutes ahead. Release with this exact string, from the same folder, **relative and not absolute**, because both allow rules are written relative and the absolute form is a fresh permission prompt at the worst possible moment:

```bash
rm -rf loop/LOCK.d
```

**Releasing is the part you owe.** A tick never steals from a name that is not a tick's — a session sitting idle is indistinguishable from an abandoned one, and idle is the normal case — so your lock cannot expire under you, and the price of that safety is that an abandoned one stalls the loop until Peter deletes the directory by hand.

**What each verdict means when it names `loop-lock`.** A live tick, or another session, is `BETTER TO DELAY` with the holder and its age. A lock held by **you** is `SAFE NOW`, which is the control the harness exists to protect: without it the rule would block its own holder for ever while passing every red case. A **tick's** lock past its lease is also `SAFE NOW`, deliberately — the loop runs its conditions check at step 2 and takes the lock at step 3, and step 3 is where the steal rule lives, so a `CHECK FIRST` here would stop the next tick before it reached the line entitled to recover a crashed run. A **person's** lock past its lease is `CHECK FIRST`: nothing will clear it for you, so go and read it. Held with an unreadable `holder` is `CHECK FIRST` too — the directory is the lock and the file is only the courtesy.

**The portal deploy row carries it since 2026-09-17, and the delivery row does not**, and both are facts about the loop rather than judgements. Until that day a tick never pushed — a deny rule in buses-data's settings, observed refusing — so it could neither deliver a map nor deploy the portal, and contended for neither. buses-data OA-394 (R1 of the 2026-09-17 process review, Peter's decision) gave the tick the push, the pull request, the merge and the deploy; the harness assertion the old sentence promised would go red did, and was flipped. Delivery stayed outside the grant, and the harness holds that boundary with a second assertion.

**It is falsified**, from this folder, no placeholders: `node prove-red-loop-lock.mjs`. It builds throwaway lock directories to prove the reading is real, then drives the rule over synthetic conditions. Watched go red before the rule existed — fifteen cases, with all four greens already passing, which is the shape that matters: the greens are the ways this rule could quietly break something that already works.

Against a **remote** portal, add `--url https://busmaps.uk --token <OPERATOR_TOKEN>` (or set `BUSMAPS_URL` / `BUSMAPS_TOKEN`). See "Remote portals" below — both reading and delivery work against the live site from this laptop (delivery proven end to end across all 13 sample maps on 2026-08-18). What has **no** laptop path is the operator half: accepting a staged refresh, withdrawing a publish request and changing a map’s outputs are HTTP endpoints needing a signed-in admin session, so they are browser work.

**Which portal you are looking at — it will not guess, since 2026-08-31.** `BUSMAPS_URL` and `BUSMAPS_TOKEN` live in `C:\Claude\community-bus-maps\.env`, which `worklist.mjs` loads for itself, so the bare command reads the **live site** and there is no flag to remember. With neither set and no `--local`, the tool prints the two lines to add and exits 2 rather than opening the dev SQLite. The dev checkout is `--local`, which **beats a configured `BUSMAPS_URL`** — otherwise the flag would do nothing on precisely the machine it exists for. `--local --url` together is a refusal, not a precedence rule. Either credential is live: it belongs in that gitignored `.env`, never in a chat message or a command line that lands in shell history.

**Send the TOKEN, not a cookie — `OPERATOR_TOKEN`, since OA-203 (2026-08-31).** `BUSMAPS_TOKEN` carries the portal's `OPERATOR_TOKEN` in an `Authorization: Bearer` header, and that credential is **read-only**: it admits `GET /api/admin/worklist`, `GET /api/maps` and, since 2026-09-05 (OA-233), `GET /api/maps/:id/poi-tiers` at admin scope and nothing else anywhere — GET only, those three routes only, refused everywhere else, and the portal's own test suite asserts the exact set of places it is consulted. `BUSMAPS_COOKIE` still works and is the fallback for a portal deployed before that change. **Prefer the token, because a `cbm_session` value is a PERSON's live admin login.** Only four portal routes sit behind step-up, so the same string that let this tool print a list could also approve an organisation, invite an admin, revoke anybody's sessions and mail every customer — and it was being kept in a file, renewed indefinitely by its own use. The portal's 2026-08-20 security round had explicitly retired *"the standing admin cookie kept in a file on the laptop"*; this skill put the practice back eleven days later, in the change that stopped it guessing which portal, because nothing in either repository named the other.

**Rotating that token breaks this skill until its copy is updated, and the rotation lives in the other repository.** Run `npm run rotate:secret -- OPERATOR_TOKEN` from `C:\Claude\community-bus-maps` (added 2026-09-01; `docs/DEPLOY.md` §2 *Rotating a token* is the write-up). It generates the replacement on the **host** and deliberately never prints it, so read the new value once out of the host's `.env` and put it into `BUSMAPS_TOKEN` in `C:\Claude\community-bus-maps\.env`. `STATUS_TOKEN` and `push-status.mjs` below are the same story. The rotation script names both of these tools in its preflight, **before** it changes anything, for exactly the reason the paragraph above ends on: this is the class of remedy that goes wrong by living in one repository while the thing it breaks lives in another, and nothing but a written pointer ever catches it.

**And the cookie was never actually short-lived, which is worth knowing before blaming an expiry.** The portal's session window is seven days and **slides on use**, so every live run here renewed it by a week. What kills it is signing out in the browser — the value in `.env` is the very session row that click deletes.

**Demo rows are hidden unless `--demo`, and never share a band with real work.** The seeded customers are all named `... (demo)`; anything carrying that in its title, reason or customer sorts below every real row under its own `DEMO DATA` heading. **A rollup row — one item standing for several records, like the applications queue — is classified by the portal instead**, in `src/worklist/index.js`, which sets `demo` on the item; this tool honours that flag rather than guessing from a sentence that cannot carry the evidence.

**The test for a seeded record is the address, never the name.** RFC 2606 and RFC 6761 reserve `example.com/.net/.org` and the `.example`, `.test`, `.invalid` and `.localhost` TLDs so that they resolve nowhere and accept no mail — so an applicant who cannot be emailed is, by construction, nobody waiting. That rule replaced a guess on 2026-08-31: the eight pending applications on the dev checkout are seven obvious `Test <sector>` rows and one *"Ramsey Town Council"*, and this skill reported that last one to Peter as a real council waiting on him because it lacked a `(demo)` suffix. It is seeded as well, at `clerk@ramsey-tc.example`. **Absence of a demo label is not evidence of realness** — and on a system that also holds genuine correspondence from a real Ramsey adviser (CORR-001), a seeded council of the same town is precisely the row that will be believed. When a queue looks real, check the address before you say so.

Both guards exist because of one run on 2026-08-31: a session asked for "the worklist", got the dev checkout, and presented a demo customer's publish review as the top item in **SOMEONE IS BLOCKED** while the one real item — a member of the public owed a reply — sat fourth. The banner said `LOCAL — dev checkout` throughout, in a box, three lines above. **A header you have to read is not a guard**; the fix had to change which rows exist, not how loudly the mode is announced.

### And whether the loop is DOING anything, which is a different question from whether it is running (OA-288, 2026-09-09)

**The lock row above answers *is a tick in progress right now*. When the loop is HALTED there is no lock at all** — so `loop_lock.mjs` reports `present: false`, which is exactly what it reports when everything is fine. The one state you most need to be told about was the one indistinguishable from health, and that is not a hypothetical: on 2026-09-09 the loop stopped at 08:15, 09:15, 10:15 and 11:15, three of them on a still tree that `sched-0815` described in its own headline as *"a finished experiment nobody has committed yet"*. Six of the first 36 ticks were gate-stops. Nothing on this board said so on any of them — the `buses-tree CHECK FIRST` line was there, but it says a tree is dirty, not that four hours of loop time went nowhere.

**`loop_runs.mjs` raises one row, `loop-idle`, and the measurement opens no file.** `loop/runs/` is one file per tick named `YYYY-MM-DD_HHMM-<feed>.md`, and `<feed>` is `none` exactly when the run stopped before dispatch, or `around` when it dispatched and did a real unit of work but never reached `buses-data` at all — so the date, the time and the verdict are all in the NAME, and a directory listing is the whole instrument. That matters beyond speed: run files are prose written afresh each hour, and a reader that depended on their wording would break the first time a tick phrased something differently.

**`around` exists because the counter measured the wrong thing, and the fix is the one place in this module where two predicates are deliberately not each other's complement** (buses-data OA-303, Peter's option 3, 2026-09-11). The row counted **idleness**; the subject anybody cares about is whether the loop can **reach its own queue**, and the two came apart on 2026-09-10 — `0815-none`, `0915-none` (row raised), then `1015-bus-work`, a tick that found and fixed a defect in `claude-skills`, the one tree the bar left open. The row vanished while one modified `Correspondence/` letter went on barring `buses-data` for another four hours: a better tick made the board quieter about a problem that was getting older. So an `-around` tick **continues** the run the row counts, because the bar did not move, **and** is in `working` and sets `lastWorkingAt`, because it genuinely did something. Only a `none` tick is in neither. When any tick in the run is an `around` the row's title says *without reaching its own queue* and names how many, rather than *done nothing*, which would be false of a tick that committed a fix. **`missed` is the third state** (buses-data OA-408, decided by Peter 2026-09-21): a scheduled run that died before reading its prompt leaves no file, so a later tick joins the scheduler's run list against the folder and writes `<stamp>-missed.md` for it. It continues the run like `none` and is never `working`; until this module knew the name, such a file would have parsed as an ordinary feed and reset the count as though the run had worked. **`busy` is the fourth, and it is in neither the run nor `working`** (buses-data ad-hoc `tick-counts`, 2026-09-26): a scheduled run that finds `loop/LOCK.d` held by another TICK under a live lease stands down and names itself `-busy`, because the queue was being worked the whole time by the tick holding the lock. The idle walk skips it without stopping, and `routine_numbers.mjs` takes it out of the idle ratio's denominator and prints the count beside it. On 2026-09-26 a 20-tick `/ticks` run was fired into twice by the hourly schedule, and both stand-downs were written `-none` and read as idle. A stand-down to a PERSON's session stays `-none`, because that is loop time the queue really lost.

**The row says WHY, and the causes come from `conditions`** — the same block printed above the bands, so the row can never contradict it. A `loop/STOP` somebody forgot, or a dirty shared tree, is rank 3 in `SOMEONE IS BLOCKED`, because clearing it is Peter's move and nothing else will. A lock held by a name that is not a tick is named as a cause but stays at rank 8: the loop is deferring to a session at the keyboard, which is correct and clears itself. Where nothing visible explains it, the row **says that** and points at the newest run file rather than inventing a cause.

**Two silences are deliberate and both are load-bearing.** A merely OLD newest run raises **nothing** — the scheduler only fires while the desktop app is open, so *"nothing since 01:15"* is the normal state of every morning, and a row for it would cry wolf daily and be muted inside a week; the age is reported inside a row, never a trigger of one. And one idle tick is below the threshold, which is **two consecutive** — derived, not chosen: the interval is the MEDIAN GAP between run files, the schedule's own output measuring itself, because the cron lives in the desktop app's task store where a node script cannot reach it. Measured over the first 36 ticks, 14 of 21 gaps were exactly 60 minutes and the median shrugs off the rest, including a four-hour hole where the app was shut.

Falsified by `node prove-red-loop-runs.mjs` from this folder, whose GREEN cases are the ones to read — a working tick clears the row, one stop is below the threshold, an old newest run raises nothing, and (case 3b) a tick that DID reach the queue resets the count even when an `around` precedes it, so `around` has not been made a synonym for *any work at all*. **Read the mutation count off the run rather than from here.** One mutation mattered more than the others: counting the idle run from the wrong end of the list, which would have reported a loop that recovered hours ago as still stopped. Case 3b's two halves are falsified **separately** — dropping `around` from `UNREACHED` reddens eight assertions and leaves the `working` one green, while making `working` the complement of `UNREACHED` reddens **only** that one, which is how you know the non-complement property is pinned by something rather than merely commented.

**Occasionally, push the gate results to the portal too:** `node "%BW%\push-status.mjs"` runs `status.js` (the full regenerate-and-diff — a minute or two) and sends the result to `POST /api/admin/status`, so the failing-gate and engine/S6-stale items show at ranks 0/8 of the portal's own To-do tab and `GET /api/admin/worklist`, not only in this terminal. Worth doing after an engine change or before a batch of deliveries — it's a separate, occasional step, not part of the routine "print the worklist" above. Add `--url` + `--token <STATUS_TOKEN>` for a remote portal. **The token travels in an `Authorization: Bearer` header and nowhere else** — the portal stopped accepting `?token=` on 2026-08-25, because Caddy's access log records the full request URI and every use of the query form wrote a live credential in clear into a file that is in no backup and under no retention rule.

**Since 2026-08-25 `status.js` also answers "is any of this actually live?"** Its closing **Deployment** row reads the `X-App-Version` header off busmaps.uk and compares it with `main` in the portal checkout — added because the deployed commit had become unreadable from outside and the site sat a commit behind `main` with nothing able to say so. Three things to know before reacting to it: it is **amber for twelve hours** after the oldest undeployed commit, because a merge is not a deploy; an **unreachable site is never red**, since that is the uptime monitor's question and this row will say `unreachable` and pass; and a **`no-header` row means the live build predates the change**, which is a fact rather than a fault. If it says `BEHIND`, the remedy is `npm run deploy` run from `C:\Claude\community-bus-maps`, not an edit — **and since 2026-09-17 a dated `BEHIND` is not red either** (buses-data OA-396, R3 of the process review): it is a chore, printed by the board and carried by this worklist as the `deploy-pending` row (rank 8 inside the grace, rank 5 after), and the only red left on the row is an *undateable* one, a live sha nothing can find. Skip the row entirely with `--no-live`, on the board and on the worklist alike. **And there is a fourth thing to know, because it is the one that has produced a false row on this very worklist (buses-data OA-392, 2026-09-17): a `BEHIND … undateable` verdict used to be the row's answer for two states with opposite remedies** — the live site running something older that cannot be dated, which needs a deploy, and the live site running something *newer* than this laptop's `origin/main`, which needs a `git fetch` and says nothing about the deployment. The second is what happened on 17 September: the board read `BEHIND live 7c1297d != main f0d511f` about a site that was running `origin/main` exactly, a hold was raised asking Peter to deploy, and it stood at the top of `SOMEONE IS BLOCKED` for four hours. The row now fetches once — and only when the live sha resolves to nothing in the checkout — and then answers `current` (noting that this clone was the stale one) or `live ahead`, both of which pass.

**And since 2026-09-18 the board asks whether the monthly BODS scan RAN, which nothing had ever asked** (buses-data OA-402, R9 of the process review). Every `refresh` row on this worklist is a JOIN on the newest `_gtfs/upcoming/upcoming-report_<date>.md`, so a report that stops being written produces a board with no refresh rows — which is exactly the board a genuinely quiet month produces. `bods_scan.mjs` raises a rank-4 chore when the newest report is older than a month plus a three-day grace, and a differently-worded one when no report exists at all, because *the scan has never run* and *the scan is stale* are different sentences with the same remedy. It reads the report FILENAMES and opens nothing, for the reason `loop_runs.mjs` gives about `loop/runs/`; a tree with no `_gtfs` — every CI runner, every fresh clone — gets a warning and never a row. **The threshold is a constant and the measured-cadence technique was tried first and is wrong here**: the reports on disk are dated 07-14, 07-27, 08-01, 08-31 and 09-01, gaps of 13, 5, 30 and 1, median 9, because four of those five were run by hand — a cadence inferred from a population that mixes a schedule with ad-hoc runs measures neither.

**The same round found the human touch that made the row necessary.** `_gtfs/refresh-bus-data.ps1`, the monthly scheduled task, ended by calling `[MessageBox]::Show`, which is **modal**: the first step of the whole refresh waited for somebody to click, and its `catch` path pops the same dialog on a machine where a failed overnight run is precisely the case nobody is watching. Measured in the script's own log, the 2026-09-01 run has twenty-nine seconds between the line before the dialog and the line after it. It now takes `-Unattended`, which logs what the dialog would have said and names the reports rather than opening them. The switch defaults OFF, because that dialog was also the only signal the monthly job had happened — so the row above was built before the signal it replaces was removed.

**And since 2026-09-22 a refresh row says whether moving the sheet needs a PERSON** (buses-data OA-426, item 2 of the same R9). `gtfs_refresh_report.py` has graded every town SAFE, ESCALATE or NOTHING since 2026-09-18 — SAFE meaning every actionable change is an operator NAME or a set of DAYS, fields that decide no colour and move no line — but the grade was written only into the report's own heading, so the only way to ask the question was to parse generated prose. It now has a file: `_gtfs/refresh-grades_<date>.json`, written beside the report by the same run, out of the same record the heading is built from, so the two cannot drift. `refresh_grades.mjs` reads it and adds one sentence to the row. **The rule worth knowing is that the dates must MATCH**: a grade is a fact about the run that produced it, a refresh row is a join on the newest upcoming report, and when those are different runs no row carries a grade and the mismatch is printed as a warning — because a stale grade attached to today's row is a machine saying *no person needed* about changes it has not seen. A town the scan could not check is NAMED in the row rather than left silently ungraded, for the same reason the report names it loudly: an absence that reads as *no changes* is the shape a month of clean, confident, empty reports already cost this project once.

**`routine_numbers.mjs` prints the five numbers R9 is judged on**, from this folder: `node routine_numbers.mjs --buses "C:/u3a St Ives/Using AI/Buses"`. Three are measured — CI red rate per repository, idle ticks off the run filenames, and words a tick loads before acting. **Two refuse to be computed and say what would make them real**, which is the point of the file as much as the three that are: nothing on disk distinguishes a commit Peter made from one a session made in his name, so *human touches per map-month* would be invented, and *relayed commands* is a grep of prose and is reported as a **floor** with a control beside it. The control is what makes it readable: *only Peter can send an email* is a decision, not a relay, and a relay count that moved with the decision count would be measuring how often Peter is mentioned. **Its harness has caught two faults in it already and both produced a plausible number rather than an error** — a re-implemented run-name regex that dropped every uppercase `-OA.md` tick from the denominator and reported 36.4% idle against a 15% baseline, and a relay pattern set so narrow it matched one file in 267, which reads as success.

Present the result to Peter as a short numbered list — title, who's waiting, age. Do not paste the raw output wholesale; it is written for a terminal, and he wants the decision, not the dump. Lead with the bands in order: **BROKEN → SOMEONE IS BLOCKED → YOUR MOVE → HOUSEKEEPING → WAITING ON OTHERS**. **Say which portal it was in the first line of your answer** — "live portal" or "dev checkout" — because he cannot see the banner and every item below it means something different depending on the answer.

**Say the conditions in that same first line**, in his register and in one clause — "nothing else is running, everything below is workable" or "another session has the portal on a branch, so the two delivery rows can wait". Then carry each row's verdict onto the row you present. He cannot see the terminal, so a verdict you leave in the tool's output is a verdict he does not have.

## Remote portals — the honest state

**Reading a remote portal works, and since OA-203 it has its own credential.** This tool only ever GETs, so `--url` + `--token <OPERATOR_TOKEN>` gives the same worklist from anywhere, with a read-only token instead of a borrowed sign-in session. `--cookie <cbm_session value>` from a signed-in admin browser remains the fallback for a portal older than that change — see [Step 1 — Print the worklist](../SKILL.md#step-1--print-the-board-and-the-worklist-and-show-peter-both-always-start-here) above for why the token is the right one to reach for.

**Delivery works too**, via `scripts/deliver-map.mjs` in `community-bus-maps` (`npm run deliver`), not an HTTP endpoint. This is item 4 of `Buses\Development Docs\_archive\foolproofing-plan_2026-08-07.md`, built 2026-08-10 — originally scoped there as `POST /api/admin/ingest`, built instead by extending the SSH-based delivery script that already existed for brand-new maps (GO-LIVE.md §2.1 Phase 1, shipped 2026-08-09): scp the render to the VPS, verify it byte-identical *before the live service is touched*, stop the portal, run the real script (`import-map.mjs` or, new, `propose-update.mjs` when `--map <slug>` is given) inside a throwaway container, restart, `/health?deep=1`. Needs `DEPLOY_HOST`/`DEPLOY_SSH_KEY`/`DEPLOY_APP_DIR` in `community-bus-maps/.env`.

`worklist.mjs` itself already knows this: when it's reading the **live** worklist (`--url`/`BUSMAPS_URL` set), a `refresh` item's printed command is the `npm run deliver -- --map …` form; reading the **local** worklist, it's still the bare `propose-update.mjs` form (no SSH round-trip needed for local dev). If you ever see a bare `propose-update.mjs`/`import-map.mjs` command printed while the worklist is in remote mode, that's a regression — it would silently write to a local `DATA_DIR` and do nothing to the live site.

An admin can also accept/decline a staged refresh straight from the admin console now (2026-08-10) — the **Refreshes** tab (`/app/admin`) carries a link to the map and Accept/Decline buttons, rather than requiring a trip to `/app/maps/:id` or signing in as the customer (unnecessary — an admin already has permission). This is frontend code, so it needs a VPS deploy to reach the live site; it isn't automatic the way `deliver-map.mjs` (laptop-only, no deploy needed) is.
