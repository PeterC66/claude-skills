# Gotchas / fixes

Reactive troubleshooting reference for the `make-bus-leaflet` workflow — read when
something misbehaves. `%SK%` = the skill's `assets` folder.

- **Converting a busway town's `external[]` to radial: drop the leading town-name stop.** The busway `leftBranch()` loop draws `stops[1..n-1]` (skips index 0), so busway-shaped data conventionally starts each arm's `stops` with the town's own name as a throwaway index-0 placeholder. `gen_external_radial.js`'s spoke loop draws **all** of `stops[0..n-1]` as ticks — it has no such skip — so copying busway `stops` arrays straight into a radial config draws a spurious "St Ives" (etc.) tick right next to the hub on every spoke, badly cluttering a multi-spoke town. Strip the leading town-name entry first (confirmed against March's radial config, which never carries one). **Real-corridor spokes will still look crowded even after that fix** if several services share a real corridor before diverging (St Ives's A/B/5A busway trio all run Fenstanton→Swavesey→Longstanton→Oakington→Histon before splitting to three different termini) — that's the same congestion the busway generator's shared "spine" was built to absorb, so expect to spread those spokes' bearings **20–30°+** apart (not the true ~10° geographic gap) and set `side` on each to steer their intermediate labels onto different sides of the line, same remedy as any crowded radial town.
- **A radial `bearing` near 270–300° can swing the hub-ward end of a long town name straight into the top-left operators legend / arm-note text**, because at those bearings `dx,dy` both go negative (up-and-left) and the terminus townNode has no collision awareness of the legend block. Nudge the bearing back toward due-west (~275–285°) rather than pushing it further round; the legend's own position (`legendAt`) is the other lever if a town genuinely needs a spoke through that quadrant.
- **bustimes locality page is padded** with expired and non-serving routes — verify every one (this is the whole point of S1, and feeds the disagreement audit). It can also **omit** services that do serve the town — so a route absent from the locality list isn't proof it doesn't run; cross-check the operator.
- **Operator PDFs via `WebFetch` → save → Read** (see S1 step 3): `WebFetch` can't parse a PDF but saves it and prints the path; Read that path (no `pages` param here). Read every page — don't trust the front-page day-type heading.
- **`gen_disagreements.py` and `gen_verification.py` need `python-docx`** (`pip install python-docx`; installed on this box). Pure python-docx, nothing that needs Word.
- **`icons.js` require** — the current template **self-resolves** it (`__dirname/icons.js` when run from `%SK%`, else the skill path / `$SKILL_ASSETS`), so a verbatim copy works in any run dir with no edit. (Old town copies that hardcoded `__dirname+'/icons.js'` break once copied out of `assets/` — rewrite to the absolute skill path, or just re-copy the current self-resolving template.)
- **sharp + `density`** mis-scales `mm` SVGs; instead set the SVG's `width/height` to the pixel target (3508×2480) and render natively — `render.js` already assumes this.
- **Label overlap (internal):** the de-collision placer drops a label rather than overlap; if important places lose labels, nudge the icon, shorten the name (the name-tidy block), or raise the candidate-position count. Tight retail clusters may need a manual offset.
- **Road-name label silently missing under `internalRoads`, even though it's in the "chosen" set** (2026-07-03) → road labels use a multi-candidate search (whole-road weighted centroid first, then points spread along the road's used length) and only give up if **every** candidate collides or falls off-frame — set `DBG_LABELS=1` to print each road's outcome (`placed` / `SKIP(overlap)` / `SKIP(off-frame)`). A genuinely busy road (e.g. St Ives Constable Road, boxed in by a POI + badges) can still lose after all candidates; that's expected, not a bug — same "give up rather than overlap" philosophy as `placeLabel()`.
- **A rotated road-name label visually overlaps a badge/icon even though `DBG_LABELS` says it "placed" cleanly** (found + fixed 2026-07-04, item 5 work) → the road-label collision box (`gen_internal.js`, road-label block, `if(IR&&SKEL)`) used to be **axis-aligned regardless of the label's own rotation angle** (`[cx-w/2-1,cy-2,cx+w/2+1,cy+2]`, ignoring `ang` entirely). A steeply-rotated name (e.g. -35°/77°) is drawn correctly rotated but its *reservation* was still the un-rotated box, so the visual glyph could swing well outside what the collision check thought was reserved — caught two live cases in shipped v6.1: "Hemingford Road" ran straight through the 5A badge, "Constable Road" ran through the doctors'-surgery icon. **Fixed:** the reservation is now the axis-aligned bounding box of the label's own rotated rectangle (rotate the 4 corners by `ang`, then min/max) — reduces to the exact old box when `ang=0`, so unrotated labels are unaffected; verified via the byte-identical gates (all three gate towns still PASS) and by DBG_LABELS before/after (the two previously-mis-placed roads now correctly `SKIP(overlap)`; Constable Road was already a "no space" case per the note above, just previously overlapping silently rather than honestly dropping). Re-check `DBG_LABELS` output any time you touch this block — a `placed` result only means "the (correct) box didn't overlap," not "eyeballed clean," so always spot-check a rendered crop for any road at a steep angle. To force a named road to draw at full **skeleton weight** even when no bus route uses it today (e.g. a real corridor continuation whose nearest-junction stretch is currently unused, so it fades to the 0.45 mm context line and breaks visual continuity), add it to `internalRoads.keyRoads` — it also folds into the label-eligible set for free (no need to *also* list it in `roadLabelInclude`). Diagnose with a `roads_geo.json` closest-point scan between two road names to confirm they actually share a node before assuming a "gap" is real.
- **"to X" continuation arrow lands at an INTERIOR junction instead of the frame edge** (internalRoads) → the tail is *truncated*, not mis-rendered. `pull_roads.js` sizes its OSM bbox from the **drawn** stops (`routes_intown_atco.json`) + a flat margin, so a route whose next real stop sits beyond that box has no road geometry past its last in-box stop; `match_routes.js` stops there and `gen_internal.js`'s continuation fallback (correctly) draws the arrow at the last point it has. The arrow/frameCut code is fine — the fix is upstream: add `match_cfg.json` `reachExtend:{ "<route>":{ "start":N, "end":N } }`, which makes `pull_roads.js` union a few more of that route's real full-chain stops into the pull bbox so the matcher reaches out to where the fisheye+frame actually cut the tail (St Ives item-3, 2026-07-04). **The projection is unaffected** — under internalRoads the fit set is town-core stops only (locality prefix + `fitExtra`), so extending the pull only lengthens tails; the town core, frame, scale and stop positions don't move. `start`/`end` = which chain end continues (match `contStart`/`contEnd`); use `DBG_TRIM=1` to read each cut point and check it lands on the MX0/MX1/MY0/MY1 boundary (St Ives used `N:2` on all five affected ends — the fisheye pushes the first out-of-town stop way past the frame, so 1–2 stops is plenty; don't over-extend or you balloon `roads_geo.json`). **Traps:** (1) `reachExtend` candidates are filtered through the SAME `viaPrefixes`/`viaExclude` as the matcher, so an excluded variant-loop is never reintroduced — BUT if a route's onward main journey needs a prefix the current `viaPrefixes` excludes (St Ives 9's Hemingford→Godmanchester continuation is the `0500HHEMA` prefix, previously dropped along with the Hilton/Elsworth village loop), you must **add that main-journey prefix to `viaPrefixes`** or the extension is filtered out and nothing changes. Verify the extended route traces the intended corridor (dump its edge road-names) — the village loop must stay absent. (2) Extending the bbox changes `match_routes.js`'s `k0` projection constant slightly, so **every** route's `stopT` bytes change — this is sub-pixel and moves no tick visibly (a couple of loop-stop ticks that project onto a re-traced line can shift a few mm along it — sensible, still on the line). (3) A bigger, denser road graph can only make Dijkstra paths **shorter or equal**; if an unaffected route's *drawn* line shifts ~one `gap`, that's **corridor bundling** re-offsetting because the newly-reached route now co-runs a corridor (its matched `pts` in `routes_paths.json` are unchanged — check those, not the rendered path). `roads_geo.json` grew 465→821 KB (1.76×) for St Ives; report before/after size + pull time.
- **Measuring how much a bundled corridor family really co-runs: the two obvious measures are both WRONG** (found while building rung 1, 2026-07-28) → `internalCorridors` needs a health check ("do these services actually run together, or have I just painted two different routes the same colour?"), and the first two attempts each *confirmed a deliberately absurd bundle* before the third one caught it. (1) **The lane-bundling test** (`corridor.dist`, 2.4 mm ≈ 65 m at map scale) is the right tolerance for "should these share a grey casing" and far too generous for "would a reader see one line" — in a dense core it makes nearly every route a neighbour of every other. (2) **Page-space coincidence of the DRAWN lines is circular**, and this is the subtle one: bundling is *precisely* the operation that removes the lane offset between members, so measuring after it inflates every family towards 1.0. Two unrelated High Wycombe routes (`1`, `33`) read **0.70 shared at a 0.3 mm tolerance** — the coincidence was real, it was just an artefact of the thing being measured. **Use the same measure the gate proposes families with:** mutual ~111 m-cell overlap of the raw matched lat/lon paths (`complexity_score.js --overlap`, default 0.6). It is independent of the fisheye, the page scale and the bundling decision, and it scored `1/33` at 0.17/0.13 and `1/1A/1B` at 1.00. General lesson: **never health-check a transformation with a metric the transformation itself moves**, and sanity-check any new metric against a case you know is bad before trusting one you hope is good.
- **`coreBox` comes out far bigger than its radius suggests — because the fisheye magnifies the core** (2026-07-28, P3) → the box's page rectangle is derived by projecting a real geographic circle of `radius` metres and taking its bounding box, which is exactly right (it stays true under any fisheye or `lenses[]`, with no scale assumption) — and that is *why* it looks large: `internalRoads.focus` deliberately magnifies the centre, so 600 m of real ground occupies a lot of page. **`coreBox` and `focus` are two answers to the same problem**; a town wanting the box should usually cut `focus` right back or drop the extra `lenses[]` over the centre. Check the S5 JPG, don't reason about it.
- **A `features[]` label can print INSIDE the `coreBox`** (2026-07-28) → feature labels are hand-positioned via `labelPos` and have no collision logic of their own, so a river label sited on the town centre lands on the box ("River Wye" did, on the High Wycombe proof). The generator now **drops such a label and warns on stderr** rather than printing it. The fix is to move `labelPos` (or `overrides.json` `internal.features[key].label.pos`) — not to hide the feature, whose line is legitimately covered by the box.
- **`corridorPalette` does not reduce a town's colour count — and expecting it to is the whole misunderstanding** (2026-07-28) → High Wycombe v1.0 already drew only 12 distinct hues; the defect was that they were spread over 31 routes **at random**, so two unrelated lines read as one corridor. Rung 3 makes the sharing *structured*: you re-assign `palette` so each corridor gets one hue and no two corridors share one. The generator's payoff is the **clash check** — it names every hue still used by unrelated groups (nine of them on the first High Wycombe pass), which is the actual defect. Related: with `corridorPalette` set, `complexity_score.js` reports **R as distinct colour groups** and adds `linesDrawn` — R exists to police the ~12-hue palette, not to count ink, and K5/D5 still measure every line.
- **A same-coloured line that loses all its badges is unidentifiable, and the normal badge pass will happily let that happen** (2026-07-28) → badge placement drops a badge rather than overlap something, which is right while colour still says which route a line is, and fatal once `corridorPalette` (or a diverged `internalCorridors` branch) means it doesn't. So for those lines only, the generator now places one badge **regardless of collision**. If you add a future remedy that makes colours ambiguous, add it to that guarantee too — a crowded sheet beats an unreadable one.
- **A "family" whose members share the same streets *inside the town* is a good bundle even when their full routes differ** → High Wycombe's `1/1A/1B`, `32/32A` and `102/103/104/105` all score 1.00 on in-town geometry; the variation is entirely outside the frame, which the internal map never draws. Conversely a pair that looks like a family by number can fail: the plan's hand-picked `31 / 41` measured 0.40 / 0.46 and the generator warned on it. Trust the measurement over the numbering.
- **Bundling a family internally without merging it externally breaks the internal/external colour correspondence** → `internalCorridors` gives every member the lead's colour on the internal sheet only. If the same family also shares a spoke via `external[].routes`, **use the same lead in both** and the two sheets agree; otherwise that family is one colour on one sheet and several on the other. Decide per family, don't discover it at print.
- **PCA rotation** can flip north left/right; that's fine for legibility (add a small north arrow if asked). It keys off the in-town stop spread.
- **Overpass 406** → missing User-Agent header. `curl` sets one automatically; **Node `fetch` and bare requests do not** → pass `headers:{'User-Agent':'make-bus-leaflet/1.0','Accept':'application/json'}` (every mirror — overpass-api.de / kumi / lz4 — 406s without it). Observed here: the `bbox` MCP exposed only `list_osm_tags` + `generate_share_url` (**no `search_overpass`**), so raw Overpass-with-UA stays the working geometry path. **bustimes 404** on a guessed locality slug → use the search page to find the real slug.
- **Editor renders blank / `Cannot find module icons.js`** → the editor runs the S4/S3 generator copy; its `icons.js` require must be the absolute skill path (the template's `__dirname` form only works when run from the skill's own `assets/`). **Editor port 5179** in use → stop the old `node edit-server.js`. Start template `assets/overrides.example.json` for the schema.
- **Editor straighten distorts OTHER routes, or the Active-route / colour / per-route options are missing** → the town's S3/S4 generator copy **predates the per-route editor** (no `routeStops`/`OVERRIDES_FILE`). A town stays on whatever generator it was built against. **Fix:** re-sync that town's `gen_internal.js`/`gen_external.js` from the *current* template (re-apply only that town's small customizations) and run the byte-identical gate before trusting it. Quick gate: copy the town's S4 `*.json` + the candidate generator + `icons.js` into a temp dir, `node gen_*.js`, `diff` the output SVG against the committed one — must be **identical** with no `overrides.json`. (Reusable harness: **`%SK%\gate.sh <gen> <S4dir> internal|external <committed.svg>`** — it lives in the skill's `assets/` now, not the old `C:\Claude\bus-editor-work\` scratch folder. Full procedure, current gate set, and the portal re-vendor step: [changing-the-engine.md](changing-the-engine.md).)
- **The map prints the WRONG version number** (folders say v1.1, the sheet says v1.0) → the printed stamp comes from `routes.json` `"version"`, not the `v<N.N>_<ts>` folder name, and branching a build from an older `routes.json` used to carry the old value across. **Fixed at source 2026-07-25:** `stage.js pull` now rewrites the field to match the run dir and `stage.js commit S4|S5` refuses a mismatch (`--force-version` to override; `stage.js stampver <runDir>` to repair by hand). The guard fires at *commit*, by which point the SVGs are drawn — so a mismatch means **re-run the generators**, not just edit the field. Don't reach for the `LEAFLET_VERSION` env var instead: it only reaches `gen_internal.js`, so the external sheet keeps the old number and the two disagree (this is what happened to the place build `St Neots Tesco Extra v1.1`).
- **A bad saved `overrides.json` (e.g. a distorted straighten)** → open the editor and press **Clear all** (or just delete `overrides.json` and regenerate). The editor no longer auto-saves, so new mistakes only persist if you press Save; Ctrl+Z undoes within a session.
- **Overrides not taking effect** → confirm `overrides.json` sits in the generator's working dir, the top-level key is `internal`/`external`, and ATCOs/keys match (stops by ATCO, POIs by `cat:name`, branches by route). Absent/`{}` is *expected* to change nothing.
- **Linear features draw nothing / wrong place** → a feature's `key` in `routes.json` `features[]` must match a key in S2's `features_geo.json`; a missing/empty geometry array draws an empty (invisible) feature rather than erroring. Recolour a feature that clashes with a route via `features[].style.stroke` or `overrides.json internal.features[key].style`. Omitting `features[]` entirely is valid (legacy single-river fallback) — don't add an empty `features:[]`, leave the key out.
- **bustimes per-direction parsing (`pull_routes_full.js`):** direction headers are `<h2>A - B</h2>` **or** `<h2>A to B</h2>` (both separators occur, even within one town). EXCLUDE the operator `<h2 itemprop="name">` and the "Possibly similar services" `<h2>`, and **stop collecting `/stops/` links at the first such non-direction heading** — otherwise links to *other* services leak into the last direction (B once parsed 107 "stops" instead of 54/56 from this). A merged direction list interleaves all journey patterns of that direction (a two-arm route shows both arms concatenated) — that's expected; it's the full record.
- **A route's in-town stop count looks wildly too high** → you merged a minor sub-service's town loop. e.g. St Ives 301S (Saturday) does a 31-stop town circuit while base 301/301X/301V hit 2 stops; merging all four made "301" appear to circle the whole town. `derive_intown.js` draws the **canonical** (first-slug) pattern only, so it shows 301's real 2–3 in-town stops; the loop still lives in `routes_full_atco.json`. List the canonical/primary slug **first** in `route_slugs.json`.
- **Long "tentacle" spokes on the internal map** → a buffer (out-of-town) stop is kilometres away because that route has no intermediate stop near town (express 302→Pidley 6.8 km, VL14→Huntingdon 7.8 km, 69→Papworth 8.7 km). Set `intown_cfg.json` `maxEdgeKm` (with `anchor`) to drop buffer stops beyond the real town edge (~3.5 km), and/or tune `routes.json` `internalZoom` to compress what remains. Without `internalZoom`, far edge stops blow the map fit out and shrink the town — St Ives went compact→needs `{corePct:0.9, comp:0.18}` once edge buffers were added.
- **`backfill_coords.js` curl note:** `--data-urlencode` is normally fine here, but `backfill_coords.js` POSTs Overpass with a `Content-Type` header from Node `fetch` (UA required, else 406). The bbox must cover **every** terminus, not just the town — under-sizing it leaves out-of-town stops uncovered (they then fall to the slower bustimes per-stop fallback, or go missing and get silently dropped by the generator's `atco2ll` filter).
- **Generator drops a stop silently** → it only draws ATCO with a coord in `atco2ll`; a stop missing from `atco2ll` vanishes with no error. After S2, confirm `backfill_coords.js` reports 100 % coverage of `_all_atco.json`.
- Keep fonts ≥ the reference; if a panel is cramped, drop content, don't shrink below ~2.5 mm.
- **S6 `verify_report.js` exits non-zero / prints "BLOCKED"** → that is **by design** on a HARD finding (it's the build gate), not a script crash. Read `verification.json`, fix the upstream stage, re-verify. A clean run exits 0 / "PASS".
- **Red-team JSON won't parse, or spurious day/terminus SOFTs** → the agent often emits HTML entities (`&amp;`, `P&amp;R`, `Mon &amp; Fri`); `verify_report.js` unescapes the common ones on load, but if the agent wraps the JSON in prose or emits other entities, strip to the bare `{...}` object before saving it as `redteam.json`. Spurious `days` diffs are almost always an un-unescaped `&amp;`.
- **Borderline direction SOFTs (55–90°) are expected, not bugs** → a route that leaves town on a different bearing than the straight line to its terminus throws a soft `direction` flag (St Ives 301 goes east via Needingworth/Morrisons then curves north to Ramsey; 5A heads southwest before swinging to Bar Hill). Only **>90°** (genuinely drawn the wrong way) is HARD. Likewise terminus SOFTs from locality coding (Cambridge/Trumpington stops are coded `CITY`) are naming, not errors.
- **S6 on a pre-S6 town** → `stage.js` lazily backfills the missing `S6` slot (and any other absent stage) in canonical order on first touch, so old manifests (March, early St Ives) just work; no migration step needed.
- **Gating the config-driven `gen_internal.js` against an OLD (pre-2026-06-07) S4 dir DIFFs** (route order, POI tidy, road-label rotation) — not a regression: that dir's `routes.json` predates the config keys (`routeOrder`/`panelOrder`/`orientationRoute`/`internalDesc`/`poi`), so the template falls back to defaults. Gate against an **augmented** `routes.json` (the town's re-homed S4, e.g. St Ives v4.1 / March v1.2, or a prep dir with the keys added). An existing town only builds byte-identical on the generic template once its `routes.json` carries those keys — that's what "re-homing" adds.
- **A new town's external hub / title shows the WRONG town** (e.g. "March" on a Huntingdon map) → a generator still has a **town literal**. The generators are meant to be fully config-driven; the radial/busway hub label was the last holdout (fixed 2026-06-07 to use `routes.json` `town`). If you find another literal, replace it with a `routes.json` key and re-gate St Ives + March byte-identical — never leave a town name baked in. The **radial hub box auto-widens** for long names (`w=max(22, town.length*2.6+6)`); if a long town name overflows a fixed box the white text spills onto white background and the overhang vanishes.
- **Overpass POI query rejected / `overpass failed`** → the verbose per-key selector form (one `node[...]`/`way[...]` line per amenity) can be refused or time out. Use the **compact regex selector** form from `%SK%\overpass-pois.txt` (`["amenity"~"^(pharmacy|doctors|…)$"]`) in a single bbox, and retry across mirrors (`overpass-api.de` / `kumi` / `lz4`) with a UA header. Add `way["landuse"="industrial"]` if you want estates. POIs go in `osm.json`; `osm2.json` can be `{"elements":[]}` (the generator reads both).
- **`bootstrap_town.py` anchor lands on the wrong stop** → it prefers an in-town stop **named** like a bus station/interchange (with ≥½ the max route count); if a town's bus station isn't named that way in NaPTAN it falls back to the most-routes stop — fix `anchor`/`anchorLabel` in the draft by hand. The bootstrap `--radius-km` (default 1.6) may also pull in an adjacent locality's prefix (Huntingdon picked up `0500HGODM` Godmanchester) — keep only the town's own prefix as `atcoPrefix`.
- **Console `UnicodeEncodeError` (`≈`, `·`) on Windows** → the cp1252 console can't print the report's `≈`/`·`; the helper files are written UTF-8 *before* the print, so the output is fine — `bootstrap_town.py`/`scaffold_town.py` now `sys.stdout.reconfigure(encoding="utf-8")` to avoid it.
- **A shared road looks "fat" — bare grey casing shows beside the colour, so a route reads as running *alongside* the road rather than on it** (internalRoads) → the grey road casing width is `(cnt-1)*gap + stroke + skeletonPad` (`gen_internal.js` ~L496) where `cnt` is that segment's **geometric-bundle membership** — i.e. *every* route that shares the corridor, even where only some of those colour lines are actually **drawn in-frame** (the others have turned off onto another road or continue out past the frame). So a corridor used by N routes always draws an N-lane casing, but where fewer than N colours occupy it the extra lanes are bare grey. Example: St Ives Somersham Road (B1040, used by 300+301+302) draws an 8.6 mm 3-lane casing its whole length, while much of the in-frame stretch shows only 1–2 colours; St Audrey's Lane (route 300 only) is a 3.0 mm one-lane casing where the green sits centred. Not a matching bug — the routes really are on that road — and it also drives the interchange knot (casing hits 17–22 mm where 6–8 routes converge on the bus station). **DONE (St Ives item 4c, shipped v6.1 2026-07-04):** the casing loop now runs *after* the TRIM pass and sizes each segment by the routes whose **trimmed in-frame line actually spans it** — of the bundle `MEM[r][i]`, keep only routes whose `TRIM[s].draw` range covers the segment midpoint (within `corridor.dist`), take the span from the lowest to the highest **drawn** lane offset, and **centre the casing on the drawn lanes' midpoint** (offset perpendicular by `mid` along `refDir(bundle[0])`'s normal). Centring matters: a corridor showing only its outer lane would otherwise overrun a centreline-anchored casing (or leave bare grey on the empty side). When every bundle route is drawn, `mid=0` and `span=(nb-1)*gap`, i.e. the old formula exactly, so all-drawn corridors (incl. the interchange knot itself, still ~22 mm — that's honest, all colours fill it) stay byte-identical; only under-occupied corridors slim (St Ives Somersham/Needingworth 5.8→3.0 mm). `TRIM[r].draw={s0,e}` was added for this. `DBG_CASE=2` prints per-segment `name bundle drawn w mid`; `DBG_CASE=1` prints the max casing width. All inside `if(IR)` — gated towns unaffected. (4c did NOT declutter the interchange itself — the converging edge is genuinely all-lanes; that needs 4a's fisheye retune below.)
- **Two "to X" terminus labels sit right on top of each other / jitter apart untidily** (internalRoads, e.g. two routes leaving via the same corridor a few mm apart on the frame edge) → **DONE (St Ives item 5, shipped v6.2 2026-07-04):** the terminus-arrow block (`gen_internal.js`, `if(IR&&TRIM)`) now **single-link-clusters** every non-suppressed frame-cut point within `internalRoads.terminiClusterDist` mm (default 7, the old jitter threshold) and draws **one arrow + one badge/label box per cluster** instead of one per route: same-destination members (e.g. St Ives A+B both "to Cambridge") share one row and ONE "to X" text side-by-side; different destinations at the same exit stack as separate rows. A cluster of one route reduces to the exact old per-route arrow+badge+label (same maths, same draw order) — byte-identical for any route whose cut has no neighbour in range, and the 3 gate towns (no `internalRoads`) still PASS untouched. **Badge pitch matters:** badges are drawn at 3.0 mm radius (6 mm diameter) — the side-by-side/stacked pitch constants (`BS`/`RH`) must clear that or adjacent badges overlap and the later one hides the earlier one (caught this the first time through: `BS=3.3` let a 2nd badge vanish under the 1st; fixed to `BS=RH=6.6/7.0`). Always visually crop-check a multi-member cluster, not just diff the SVG — an overlap like this doesn't show up as a missing element, just a hidden one.
- **The bus-station interchange is too crowded / lines pile onto the anchor** (internalRoads) → the `internalRoads.focus` fisheye keeps everything within `coreKm` at true scale and compresses beyond by `comp`; the map then **fits-to-frame**, so to give the interchange more page space you must shrink the *compressed extent* → **lower `comp`** (compress the outer town harder), which raises the fit scale and magnifies the true-scale core. Counter-intuitively, **raising `coreKm` makes the interchange SMALLER** (bigger extent → lower fit scale). St Ives went `comp 0.42→0.34` (item 4a, v6.1) for ~+8 % core spread. Trade-off: magnifying the core enlarges the whole map, so **peripheral POIs near the frame can push off-frame** (St Ives lost only *Copley Scout Park* at 0.34; 0.30 also dropped *Wheatfields Primary*) — stop ticks are unaffected (the fit set is town-core stops; check `r="0.8"` circle count is unchanged).
