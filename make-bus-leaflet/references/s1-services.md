# Stage 1 — Services (+ the disagreement audit)

Detailed steps for S1 of the `make-bus-leaflet` workflow. See SKILL.md for the stage model, the manifest, and `stage.js`. `%SK%` = the skill's `assets` folder. `$S1` = the S1 run folder created by `stage.js new S1`.

1. `stage.js init` the town folder if it doesn't exist; `S1=stage.js new S1`.
   - **Pre-print gate — check what's changing *soon* before you build.** Run `python "%SK%\gtfs_upcoming.py" --root "…\Buses" --town "<Town>"` (ad-hoc, writes nothing). It mines the BODS feed for changes registered to take effect in the near future ([NEW]/[CHANGE]/[ENDS?]) plus a month-over-month diff — because operators must publish ≥42 days ahead, this is genuine advance notice. Use it to decide, **per town, this build** (there is no fixed rule):
     - *Nothing upcoming* → build today's network normally.
     - *A firm dated change within the leaflet's useful life* → either **(a)** build today's network and add a dated call-out via `routes.json` `stamp.notes` (see [s3-config.md](s3-config.md)); or **(b) hold and build the post-change network** by passing `--asof <YYYY-MM-DD>` to `gtfs_query.py` in step 2 so the facts reflect the network as it will be on the change date; or **(c)** do both (render future, stamp "valid from <date>"). `[ENDS?]` items are low-confidence — verify on bustimes before dropping a route.
2. **GTFS facts pull (primary, deterministic).** Get the town's NaPTAN ATCO locality prefix (e.g. `0500HSTIV` St Ives, `0500FMARC` March — from the bustimes locality page's `/stops/<ATCO>` links, or the town's existing S2 data). Then:
   ```
   python "%SK%\gtfs_query.py" <ATCO_PREFIX> --town "<Town>" --out "$S1\gtfs-services.json"
   ```
   (Don't know the prefix? Use `--near "lat,lon,km"` for a geographic radius around the town centre instead.) To build the leaflet for a **future** date (option (b) from the pre-print gate), add **`--asof YYYY-MM-DD`**: only services in effect on that date are returned, so a route starting/ending then appears/disappears and re-registered timetables show their new pattern (it also reads `calendar_dates`, so new calendar-only routes like Wisbech 52 get their days). Omit `--asof` for today's live network — the default output is unchanged. This reads the shared county dataset `…\Buses\_gtfs\cambridgeshire.sqlite` (BODS open data) and returns, **per route that calls at the town**: `operator`, `days` (computed only from trips that stop in the town — never region-wide), `validFrom`/`validTo`, `headsigns` + `termini`, `possibleVariantOf` (e.g. 301S/V/X → 301), and `hasGtfsShape` (whether road-following geometry exists — true mostly for big operators like Stagecoach). This is the **candidate service set**; it reproduced St Ives' hand-verified facts exactly. If the dataset is stale/missing, rebuild it (`gtfs_build.py`, see its header) or fall back to the bustimes-only flow below.
   - **Collapse the variant suffixes** (301S/V/X → 301) into the base route per `possibleVariantOf`, but **record the variants** (the pipeline already supports `variants[].subServices`) so S6 doesn't re-flag them.
3. **bustimes pass — catch what BODS omits, and cross-check.** GTFS covers **registered local services only**; **community / demand-responsive / pre-book minibus** services are missing (e.g. St Ives **VL14** Villager, March **33A** FACT). `WebFetch https://bustimes.org/search?q=<Town>+<County>` → locality slug; `WebFetch`/`curl` the locality page and **(a) merge in any serving service the GTFS pull didn't list** (these are usually the community/DRT ones — verify they actually serve the town), and **(b) cross-check** the GTFS facts (operator, days, status, whether the route really enters town — the locality page is **padded** with expired and non-serving routes). Save the raw `locality_*.html` into `$S1`. If it resists curl/WebFetch (JS-rendered, consent/cookie wall, interactive widget), load it with **Claude in Chrome**. The result of this pass is the **per-route worklist** for step 3a: one row per candidate route with its GTFS facts (operator, days, headsigns, termini) attached.

   3a. **Fan out one sub-agent per route (or small batch) — this is the slow, human-time-heavy part and it's embarrassingly parallel.** For each route in the worklist, launch an `Agent` (`subagent_type: general-purpose`, run in background, all launched in one message so they run concurrently) with a **self-contained prompt** containing: the town, the route number, the GTFS facts already known for it (operator/days/headsigns/termini/status), and the exact task —
      - Open `https://bustimes.org/services/<slug>` (or search from the locality page) and record operator, days, ordered stops/towns, status.
      - Find the operator's own timetable — usually a PDF (`curl -sA UA "<operator page>" | grep -oiE 'href="[^"]+\.pdf"'`, URL-encode spaces) — and **read the whole PDF, not just the front-page heading** (multi-page timetables put each day-type on its own page; e.g. Stagecoach 56's cover read "Monday to Friday" but a later page held the **Saturday** timetable, so it's really Mon–Sat — concluding from page 1 alone produces a false disagreement). Use the `pdf` skill to read it (OCRs scanned tables); if `WebFetch` can't parse the PDF it still saves the binary and prints a path — Read that path directly (no `pages` param on this box).
      - Watch for **day-dependent renumbering and variants** (Dews **ZIP2** weekdays → **ZIP3** Saturdays is the same link, not a withdrawal; **301/301S/301V/301X** are variants, not separate routes) and combine bustimes' separate Mon–Fri + Sat columns into one days string.
      - Compare bustimes vs operator per field (status, operating days, route number/branding, terminus/destination, stop sequence; fares only if both publish them) and return **strict JSON only**, one object per field checked (agree rows included, not just conflicts), matching the `disagreements.json` row schema documented at the top of `assets/gen_disagreements.py`:
        ```json
        {"route":"32","operator":"Dews Coaches","field":"operating days",
         "bustimes":"Mon-Sat","operator_says":"Mon-Sat","agree":true,
         "resolution":"-","sources":{"bustimes":"https://...","operator":"https://..."}}
        ```
      - Also ask it to flag **(a) whether the route genuinely serves the town** at all (catches locality-page padding) and **(b) any conflict between the *existing* leaflet's panel text and what it found** if you pass in the current panel wording (e.g. St Ives 301 said "market days only" while both live sources say Mon–Sat).
      - **Batch size:** for towns with only 3–4 routes the fan-out overhead isn't worth it — just do it inline as before. For 5+ routes, one agent per route; for towns with 15+ routes, group 2–3 low-complexity routes (same operator, obviously-agreeing GTFS facts) per agent to keep the fan-out from ballooning. 3b. **Merge.** Collect each sub-agent's JSON rows into a single `disagreements.json` rows array (step 4 below) and fold the "genuinely serves the town" / "panel text conflict" flags into that same file (inline note in `operator_says`/`resolution`, per the existing convention) rather than a separate document — nothing about the *output* changes, only how step 3's legwork gets done.
4. Build **`disagreements.json`** in `$S1` from the merged sub-agent rows (or, for small towns done inline, written directly) — one row **per route per field checked**, each with `bustimes`, `operator_says`, `agree` (true/false), `resolution` (when they differ — operator wins), and `sources` URLs. Include **agree rows too** (full audit trail). Schema is documented at the top of `assets/gen_disagreements.py`.
5. Build the doc: `python "%SK%\gen_disagreements.py" "$S1\disagreements.json"` → `disagreements.docx` (+ `disagreements.pdf`, converted via LibreOffice headless automatically — the docx stays the internal editable source, the PDF is what the BusMaps.uk portal shows customers; see `convert_to_pdf()` at the top of `gen_disagreements.py`. If `soffice` isn't found the script still writes the docx and just skips the PDF — never a hard failure).
6. Write **`verified-services.json`** (the final route set + per-route operator/days/status) into `$S1`. Note each service's source where it matters: `"source":"gtfs"` for the BODS-derived majority, `"source":"bustimes-community"` for the DRT/pre-book additions GTFS missed (so a refresh knows to re-check them on bustimes, not expect them in the dataset).
   - **Register the town for refresh-diffing (new towns):** add it to `…\Buses\_gtfs\town_prefixes.json` as `"<Town>": {"prefixes":["<ATCO_PREFIX>"]}` (or `{"near":[lat,lon,km]}`). That's what lets `gtfs_refresh_report.py` later tell you this town's leaflet has gone stale and why.
     - **Add `"region": "<key>"` unless the town is in the default region** (`cambridgeshire`) — the key comes from `_gtfs/regions.json`. `scaffold_town.py` sets this for you from `--db`; set it by hand if you register a town manually. Omitting it means the town is diffed against the wrong dataset, so the tooling now refuses and reports it **NOT CHECKED** with the reason. (Before that guard existed, Beaconsfield was diffed against the Cambridgeshire dataset and every one of its 7 routes came back `[WITHDRAWN?]` every month.)
     - **Prefer `near` when the NaPTAN block is over-broad.** Beaconsfield's `040000001` covers 326 stops across a wide swathe of Bucks; on prefix it reported 35 unrelated routes as `[ADD?]`, on `near:[51.601601,-0.637726,2.5]` it reports only the 4 school services genuinely awaiting curation. Same over-broad-block problem `coreMaxKm` solves for the drawn map.
7. `stage.js commit S1 "$S1" --outputs gtfs-services.json,verified-services.json,disagreements.json,disagreements.docx,disagreements.pdf`.
