# Stage 1 — Services (+ the disagreement audit)

Detailed steps for S1 of the `make-bus-leaflet` workflow. See SKILL.md for the stage model, the manifest, and `stage.js`. `%SK%` = the skill's `assets` folder. `$S1` = the S1 run folder created by `stage.js new S1`.

1. `stage.js init` the town folder if it doesn't exist; `S1=stage.js new S1`.
   - **Pre-print gate — check what's changing *soon* before you build.** Run `python3 "%SK%\gtfs_upcoming.py" --root "…\Buses" --town "<Town>"` (ad-hoc, writes nothing). It mines the BODS feed for changes registered to take effect in the near future ([NEW]/[CHANGE]/[ENDS?]) plus a month-over-month diff — because operators must publish ≥42 days ahead, this is genuine advance notice. Use it to decide, **per town, this build** (there is no fixed rule):
     - *Nothing upcoming* → build today's network normally.
     - *A firm dated change within the leaflet's useful life* → either **(a)** build today's network and add a dated call-out via `routes.json` `stamp.notes` (see [s3-config.md](s3-config.md)); or **(b) hold and build the post-change network** by passing `--asof <YYYY-MM-DD>` to `gtfs_query.py` in step 2 so the facts reflect the network as it will be on the change date; or **(c)** do both (render future, stamp "valid from <date>"). `[ENDS?]` items are low-confidence — verify on bustimes before dropping a route.
2. **GTFS facts pull (primary, deterministic).** Get the town's NaPTAN ATCO locality prefix (e.g. `0500HSTIV` St Ives, `0500FMARC` March — from the bustimes locality page's `/stops/<ATCO>` links, or the town's existing S2 data). Then:
   ```
   python3 "%SK%\gtfs_query.py" <ATCO_PREFIX> --town "<Town>" --out "$S1\gtfs-services.json"
   ```
   (Don't know the prefix? Use `--near "lat,lon,km"` for a geographic radius around the town centre instead.) To build the leaflet for a **future** date (option (b) from the pre-print gate), add **`--asof YYYY-MM-DD`**: only services in effect on that date are returned, so a route starting/ending then appears/disappears and re-registered timetables show their new pattern (it also reads `calendar_dates`, so new calendar-only routes like Wisbech 52 get their days). Omit `--asof` for today's live network — the default output is unchanged. This reads the shared county dataset `…\Buses\_gtfs\cambridgeshire.sqlite` (BODS open data) and returns, **per route that calls at the town**: `operator`, `days` (computed only from trips that stop in the town — never region-wide), `validFrom`/`validTo`, `headsigns` + `termini`, `possibleVariantOf` (e.g. 301S/V/X → 301), and `hasGtfsShape` (whether road-following geometry exists — true mostly for big operators like Stagecoach). This is the **candidate service set**; it reproduced St Ives' hand-verified facts exactly. If the dataset is stale/missing, rebuild it (`gtfs_build.py`, see its header) or fall back to the bustimes-only flow below.
   - **Collapse the variant suffixes** (301S/V/X → 301) into the base route per `possibleVariantOf`, but **record the variants** (the pipeline already supports `variants[].subServices`) so S6 doesn't re-flag them.
   - **`days` is what RUNS, and `daysBasis` says how we know** (OA-204, fixed 2026-08-31). GTFS lets `calendar` and `calendar_dates` both define the answer, and until this was fixed the days came from the `calendar` row alone — so a service filed Mon–Fri that added every weekend as an exception read **Mon-Fri**. High Wycombe route 300 is that shape, and applying it would have printed *no Sunday bus* onto a sheet where twelve Sunday journeys run. Days are now the weekdays the route actually carries a journey at the town across the sampled window. `daysBasis` normally says `resolved …`; when it says `declared …` the sampled window held no journey at all (a seasonal route sampled out of season) and you are reading the operator's declaration rather than an observation — treat it as the weaker claim it is.
   - **"Operator wins" names a source, not a page — and a service LIST is the wrong page.** BODS carried a Thames Valley Buses route 20 at High Wycombe from the town's first build. It was excluded on 2026-07-27 as a stale registration because *"the operator's own website lists no route 20"*, and the rule invoked was the right one. What had been read was the operator's service-list page, which does not show the 20 to this day; the operator's own **announcement** ("New service 20 to connect Maidenhead to High Wycombe") and its own `/services/CTNY/20` page both carry it, and it had been running since 3 November 2025 — nine months before that reading was made. The same list page, and both terminal stop pages on bustimes, still show nothing, so re-running the same check re-confirms the same wrong answer for ever. **Before excluding a route the feed asserts, SEARCH for the number and the two town names**, not just the operator's index; and where the two disagree, say in `disagreements.json` which page you read, so the next session can tell a checked claim from an unchecked one. Cost: five weeks of a published map missing an hourly Mon-Sat service, on both artefacts we ship for that town disagreeing with each other about whether the bus existed.
   - **A days change on a route you already draw is a disagreement to resolve, not a fact to apply.** Take it to the operator's own timetable first; that is what settled 130 and 300 at High Wycombe, and the panel turned out to be right and BODS incomplete. Record the outcome as a `disagreements.json` row so the next refresh does not reopen it.
   - **How often each route runs comes back too, and which field you use matters.** `journeysPerWeek` (with `journeysPerWeekRange`, `busiestDayJourneys`, `journeysOutBack`, `firstDeparture`/`lastDeparture`) is the real rate, expanded over 12 consecutive weeks from today's Monday — `frequencyBasis` records the window. Every count is of distinct **journeys**, not of trip records: some operators file the same journey several times under overlapping `service_id`s (High Wycombe's M40 up to four), and `typicalDayDuplicates` reports how many were collapsed on the profiled day. **`tripPatternsAtTown` is NOT a rate**: it counts rows in `trips.txt`, understates by ×2.0–×5.7 depending on how many `service_id`s the operator split their timetable into, and gets the *ranking* wrong — never sort, rank or draw from it. **And to tier a line weight, do not use `journeysPerWeek` either**: a weekly total is a volume, not availability, and tiering on it misplaces 11 of the 78 drawn lanes on the board. Use **`coreHeadwayMinutes`** (median gap 09:00–15:00, busier direction) and **`longestDaytimeGap`** (largest gap 07:00–19:00, both directions), with a **`weeksActive`** floor — a service running under half the sampled weeks cannot hold a weekly rate at all, which is how High Wycombe's bank-holiday-only 130, 300 and WW1 read as 24, 24 and 8 journeys a week. `typicalDayJourneys`/`typicalDayWindow` describe the busiest weekday of the sample. Model, evidence and proposed thresholds: Buses repo, `Development Docs/frequency-tier-model_2026-08-17.md`.
3. **bustimes pass — catch what BODS omits, and cross-check.** GTFS covers **registered local services only**; **community / demand-responsive / pre-book minibus** services are missing (e.g. St Ives **VL14** Villager, March **33A** FACT). `WebFetch https://bustimes.org/search?q=<Town>+<County>` → locality slug; `WebFetch`/`curl` the locality page and **(a) merge in any serving service the GTFS pull didn't list** (these are usually the community/DRT ones — verify they actually serve the town), and **(b) cross-check** the GTFS facts (operator, days, status, whether the route really enters town — the locality page is **padded** with expired and non-serving routes). Save the raw `locality_*.html` into `$S1`. If it resists curl/WebFetch (JS-rendered, consent/cookie wall, interactive widget), load it with **Claude in Chrome**. **Moovit (`moovitapp.com`) may be read as a further cross-check where an operator's own timetable is hard to find** — Huntingdon's AW1 was checked against it on 2026-09-06 — **but agreement with Moovit is NOT independent confirmation.** It reads the same BODS feed `gtfs_query.py` reads, so it is a second reading of the same source, and its generated line pages are unverified: on 2026-09-06 its St Neots 61 page said "once a day at 16:30" against seven journeys Mon–Sat in the feed and on bustimes (buses-data OA-260). The operator's own page still wins, and when you cite Moovit in `verified-services.json`, say what it is. Do not link to it from anything a customer sees. The result of this pass is the **per-route worklist** for step 3a: one row per candidate route with its GTFS facts (operator, days, headsigns, termini) attached.

   3a. **Fan out one sub-agent per route (or small batch) — this is the slow, human-time-heavy part and it's embarrassingly parallel.** For each route in the worklist, launch an `Agent` (`subagent_type: general-purpose`, run in background, all launched in one message so they run concurrently) with a **self-contained prompt** containing: the town, the route number, the GTFS facts already known for it (operator/days/headsigns/termini/status), and the exact task —
      - Open `https://bustimes.org/services/<slug>` (or search from the locality page) and record operator, days, ordered stops/towns, status.
      - Find the operator's own timetable — usually a PDF (`curl -sA UA "<operator page>" | grep -oiE 'href="[^"]+\.pdf"'`, URL-encode spaces) — and **read the whole PDF, not just the front-page heading** (multi-page timetables put each day-type on its own page; e.g. Stagecoach 56's cover read "Monday to Friday" but a later page held the **Saturday** timetable, so it's really Mon–Sat — concluding from page 1 alone produces a false disagreement). Use the `pdf` skill to read it (OCRs scanned tables); if `WebFetch` can't parse the PDF it still saves the binary and prints a path — Read that path directly (no `pages` param on this box).
      - Watch for **day-dependent renumbering and variants** (Dews **ZIP2** weekdays → **ZIP3** Saturdays is the same link, not a withdrawal; **301/301S/301V/301X** are variants, not separate routes) and combine bustimes' separate Mon–Fri + Sat columns into one days string.
      - Compare bustimes vs operator per field (status, operating days, route number/branding, terminus/destination, stop sequence; fares only if both publish them) and return **strict JSON only**, one object per field checked (agree rows included, not just conflicts), matching the `disagreements.json` row schema documented at the top of `assets/gen_disagreements.py`:
        ```json
        {"route":"32","operator":"Dews Coaches","field":"operating days",
         "bustimes":"Mon-Sat","operator_says":"Mon-Sat","agree":true,
         "resolution":"-","sources":{"bustimes":"https://...","operator":"https://..."}}
        ```
      - Also ask it to flag **(a) whether the route genuinely serves the town** at all (catches locality-page padding) and **(b) any conflict between the *existing* leaflet's panel text and what it found** if you pass in the current panel wording (e.g. St Ives 301 said "market days only" while both live sources say Mon–Sat).
      - **Batch size:** for towns with only 3–4 routes the fan-out overhead isn't worth it — just do it inline as before. For 5+ routes, one agent per route; for towns with 15+ routes, group 2–3 low-complexity routes (same operator, obviously-agreeing GTFS facts) per agent to keep the fan-out from ballooning. 3b. **Merge.** Collect each sub-agent's JSON rows into a single `disagreements.json` rows array (step 4 below) and fold the "genuinely serves the town" / "panel text conflict" flags into that same file (inline note in `operator_says`/`resolution`, per the existing convention) rather than a separate document — nothing about the *output* changes, only how step 3's legwork gets done.
4. Build **`disagreements.json`** in `$S1` from the merged sub-agent rows (or, for small towns done inline, written directly) — one row **per route per field checked**, each with `bustimes`, `operator_says`, `agree` (true/false), `resolution` (when they differ — operator wins), and `sources` URLs. Include **agree rows too** (full audit trail). Schema is documented at the top of `assets/gen_disagreements.py`.
5. Build the doc: `python3 "%SK%\gen_disagreements.py" "$S1\disagreements.json"` → `disagreements.docx` (+ `disagreements.pdf`, converted via LibreOffice headless automatically — the docx stays the internal editable source, the PDF is what the BusMaps.uk portal shows customers; see `convert_to_pdf()` at the top of `gen_disagreements.py`. If `soffice` isn't found the script still writes the docx and just skips the PDF — never a hard failure).
6. Write **`verified-services.json`** (the final route set + per-route operator/days/status) into `$S1`. Note each service's source where it matters: `"source":"gtfs"` for the BODS-derived majority, `"source":"bustimes-community"` for the DRT/pre-book additions GTFS missed (so a refresh knows to re-check them on bustimes, not expect them in the dataset).
   - **A route you know about and deliberately do not draw goes in `notOnLeaflet[]`, and nowhere else** (OA-259, 2026-09-06). Three older spellings — `verifiedNotDisplayed[]`, `notDisplayed[]` and `excluded[]` — mean exactly the same thing and are **read for ever**, so every S1 run this estate has ever built stays readable; they may no longer be **written**, and `check-exclusion-fields.mjs` fails a repository whose latest S1 runs still use one. The five town files that did were migrated on 2026-09-06, each proved to give an identical reader answer before and after. Give every entry a `route` and a `reason` — `note` is accepted too, and High Wycombe's one-word `reason` plus a `detail` is joined into one sentence. **There is no longer a field to pick**, and that is the point of the second half: making four spellings behave identically removed the bug — until OA-259, `verify_report.js` read `notOnLeaflet` alone and only where `servesTown` was `false`, so an exclusion written truthfully in any of the other three was invisible and its route came back a `missing-service` inclusion candidate on every S6 run — but it did not remove the question, and four spellings that behave identically are four chances to write the one nobody greps for. Huntingdon's blind red team named the same seven routes twice at 89k–137k tokens an answer for exactly that reason. The rule lives in `assets/known_off.js` and in `known_off_routes()` in `assets/gtfs_refresh_report.py`, and the two are held together by `npm run test:prove-known-off-parity`.
     - **`servesTown: false` in `notOnLeaflet` still means something different and louder**, so use it only when the route genuinely does not serve the town: it raises a `serves-town-conflict` if the red team disagrees, and a `RE-EVAL` if BODS starts showing the route at the town. A route that DOES serve the town and that we simply do not carry takes a plain entry with a reason.
     - **An entry with no `route` is reported, not counted.** Beaconsfield's `notDisplayed` carries a `{"group": "Dedicated school services"}` block; nothing can match a route against a class, so S6 says so rather than letting a whole fleet look adjudicated.
   - **A service that is legitimately NOT IN BODS must say so, rather than be guessed at from the operator's name** (OA-259). Add `"notInBods": {"why": "…", "since": "YYYY-MM-DD", "recheckBy": "YYYY-MM-DD"}` to the service entry; `why` is required, `recheckBy` optional. The monthly refresh then reports `[NOT-IN-BODS]` carrying your words instead of `[WITHDRAWN?]`. **The `source: "bustimes-community"` / operator-name inference still works and is still the fallback** — but it is an inference from a brand, and it fails on the first commercial counterexample. Whippet's **X1 "Blue Arrow"** (Cambridge – Huntingdon – Peterborough, Mon–Sat, five journeys each way since 26 January 2026) is absent from the ITM East Anglia extract while nine other Whippet routes are in it, so it read `[WITHDRAWN?]` every month about a bus that runs. **An unexplained declaration silences nothing**, and a `recheckBy` that has passed stops silencing and names the date — same rule as `redteamRejected`. Give a community service no `recheckBy` (its absence is structural); give an anomalous one a date.
   - **Register the town for refresh-diffing (new towns):** add it to `…\Buses\_gtfs\town_prefixes.json` as `"<Town>": {"prefixes":["<ATCO_PREFIX>"]}` (or `{"near":[lat,lon,km]}`). That's what lets `gtfs_refresh_report.py` later tell you this town's leaflet has gone stale and why.
     - **Add `"region": "<key>"` — ALWAYS, for every town including Cambridgeshire ones.** There has been **no default region since 2026-08-21**; the key comes from `_gtfs/regions.json`. `scaffold_town.py` sets this for you from `--db`; set it by hand if you register a town manually. Omitting it means the town would be diffed against the wrong dataset, so the tooling refuses and reports it **NOT CHECKED** with the reason. (Before that guard existed, Beaconsfield was diffed against the Cambridgeshire dataset and every one of its 7 routes came back `[WITHDRAWN?]` every month.)
     - **One region per town, and nothing unions two.** `"region"` is a single string and `gtfs_regions.resolve_db()` returns a single sqlite path, so a town whose services genuinely straddle two BODS regions would silently lose the half in the neighbour's dataset — there is no supported way to read both. Nothing built needs it (checked for St Neots on 2026-08-22: Cambridgeshire holds all 8 of its BODS services; Bedfordshire adds only route 905, which Cambridgeshire already carries), but do not assume a cross-border town will just work. Registering the neighbouring region does **not** make an existing town read from it.
     - **Prefer `near` when the NaPTAN block is over-broad.** Beaconsfield's `040000001` covers 326 stops across a wide swathe of Bucks; on prefix it reported 35 unrelated routes as `[ADD?]`, on `near:[51.601601,-0.637726,2.5]` it reports only the 4 school services genuinely awaiting curation. Same over-broad-block problem `coreMaxKm` solves for the drawn map.
7. `stage.js commit S1 "$S1" --outputs gtfs-services.json,verified-services.json,disagreements.json,disagreements.docx,disagreements.pdf`.


## A service that is in NO feed at all — the hand-authored chain (2026-09-11, buses-data OA-286)

**Before you conclude a community service cannot be drawn, download whatever the operator publishes.** OA-286 was filed saying Wisbech's route 68 had *"eight or nine place NAMES, from prose"* and was therefore undrawable. It does not: `fact-cambs.co.uk/Route-68.html` links a PNG headed *Route 68 Timetable / Wisbech town circular / Times updated 1st June 2026*, with all 38 calling points in order and five hourly journeys. Nobody had looked. The premise was an inference from the sources that happened to be to hand — two newspaper reports and a council listing — rather than a fact about the world. A community operator that runs a fixed route usually publishes a timetable somewhere, often as an image a text fetch will not show you; fetch the page, list its links, and read the PNG or PDF.

**`source: "operator"` is the third provenance value, alongside `gtfs` and `bustimes-community`,** and it means *neither feed has this; a person read the operator's own publication*. Pair it with `notInBods{}` as usual, and say in `why` that bustimes lacks it too, because that is the unusual half — a community service missing from BODS is structural, one missing from bustimes as well is worth stating.

### Resolving a printed timetable into an ATCO chain

Route 68 is the estate's first drawn service whose geometry came from no feed. What made it defensible was not care; it was **a second field that had to agree**.

- **Resolve row by row, in the timetable's printed order, and write the audit down.** Wisbech's S2 run carries `manual-chain-68.json`: every printed row with its `printedStop` / `printedLocation` verbatim, the ATCO it resolved to, a `confidence` and a `why`. Its own header says what it is for — *disagree with a row by reading it, not by re-deriving it*. Without that file the next session re-does the afternoon.
- **Use NaPTAN's `Bearing` as the check, and it is nearly free.** NaPTAN records the direction a bus leaves each stop. Resolve each row to the stop *on the side the timetable's running order implies*, then verify the bearing agrees. On Wisbech all 34 resolved rows agreed, and in six places NaPTAN's `near`/`opp` independently matched the operator's printed *Near*/*Opposite*. Neither would have survived a wrong order or a wrong side. **On a chain with exactly one source, a field that has to agree is worth more than a second reading of the same source.**
- **Resolve to nothing rather than guess.** Four of Wisbech's 38 rows name places NaPTAN has no stop for. They are in the audit with `atco: null` and are drawn as no tick. The line still runs down those streets, because the road matcher traces between the anchors either side — so the cost of an honest gap is four ticks on a sheet whose own footer says *"Stop positions are approximate"*.
- **Then check the drawn line against the timetable a third way.** Name the OSM road nearest each point of the rendered path and compare the sequence to the streets the timetable names. Wisbech's reproduced the operator's own order, and one stretch OSM calls *6th Avenue* is what the timetable calls *Sixth Avenue* — which is the only evidence that the two lowest-confidence rows land in the right place.
- **Cross-check the backfilled coordinates against `naptan.sqlite`.** `backfill_coords.js` falls back to bustimes stop pages, and bustimes' stop NAMES can be wrong in a way that matters: it calls Wisbech's Cromwell Retail Park pair *"Tesco Superstore"*, 400 m from the real Tesco, which would have put a second Tesco on the sheet. Coordinates agreed to 8.1 m; names did not. Take names from NaPTAN's `CommonName`, and only for stops no other route already relies on.

### Two config levers a hand-authored circular will need

Both were measured on the artefact, not reasoned:

- **`match_cfg.json` `viaChain: {"<route>": "intown"}`** when part of the loop is one-way. Route 68's eye-clinic spur is on the return leg only, and on the canonical chain that tick sat **349.6 m** off its own line; on the intown chain the worst tick is 13.6 m. The doubled-back line costs nothing measurable — complexity scores identically either way.
- **`intown_cfg.json` `circular`** must list a route that starts and ends at the same stop. Without it Wisbech's 68 had a loose end, `contEnd` went true, and the sheet would have drawn a *continues to…* arrow off a bus that goes nowhere.

### What the operator's own page says beats what a newspaper said

Route 68's register entry recorded *"booking is offered but optional"* from a 2022 newspaper piece about a booking app. The operator's current page says *"Journeys for a Monday need to be booked on a Friday"* and *"Return time to be booked at the time of you booking, you are unable to arrange this with the driver"* — and the contract changed hands twice in between. **A community route's terms of use change with its contract, so date every claim about them and re-read the operator's page at each rebuild.** The Services-panel line carries the booking number as a result.
