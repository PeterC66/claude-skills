# Stage 6 — Verify (independent / "antagonistic" pass)

The reliability gate. S6 audits the latest S1–S5 outputs **two ways at once**: an **independent blind red-team re-derivation** of the town's services (a separate sub-agent that never saw our stored data) diffed against our pipeline, **plus** structural / geographic **sanity checks** that don't need the red-team. It writes `verification.json` + `verification.docx` and **fails the build (exit 1) on any HARD finding**. See SKILL.md for the stage model, the manifest, and `stage.js`. `%SK%` = the skill's `assets` folder; `$S6` = the run folder from `stage.js new S6`.

### How independent it actually is (state this honestly; don't oversell a PASS)
The pass is **procedurally blind** (the agent never sees our data, re-derives from scratch), **source-checked** (a second source is required), runs on a **different model** than the orchestrator (step 4 below), and its **primary source is NOT bustimes.org** (the prompt now requires a non-bustimes primary; bustimes may only be used to cross-check, never as the sole or first source — see the prompt). That closes two of the three correlated-error risks this section used to flag as open. What's still true:
- **Shared substrate family.** The red-team is a *different* model but still a Claude model, so architecture-level blind spots (not model-specific ones) can still correlate — a reasoning trap novel to the whole family, rather than one instance's quirk, could still survive.
- The diff and the HARD/SOFT thresholds are **our** code, not an outside standard.

So report a PASS as **"no contradiction found by a blind, second-sourced, different- primary-source, different-model re-check"** — stronger than before, still **not** "independently proven correct". For genuinely independent assurance you'd need a non-Claude checker. Keep the user's expectations calibrated to this in any summary.

S6 is **dated, not versioned** — it verifies whatever the manifest currently points at; re-run it whenever S1–S3 data changes. It changes no drawn output, so it never bumps an image version.

## When to run it
- After a major build (new/changed services, new town) — before relying on the data.
- Whenever the user asks "is this data right / trustworthy?" or to re-verify a town.
- Old towns (March, pre-S6 St Ives manifests) just work: `stage.js` lazily backfills the missing `S6` slot on first touch.

## The two design decisions (LOCKED — do not re-litigate)
1. **Rigour = full blind red-team agent, on a different model, with a non-bustimes primary source.** Spawn a *separate* sub-agent that re-derives S1 from scratch — each service's operator, termini at **both** ends, operating days, and whether it actually serves the town — with **no sight** of our stored `verified-services.json` / `routes.json` / geometry. It returns structured JSON; we diff. (Not self-consistency only; not a mere re-read of our own files.) Two extra constraints beyond the original design, added 2026-08-04 to convert the honesty caveat below from a permanent disclaimer into an actual improvement:
   - **Model:** pass `model:` in the `Agent` call and set it to a **different** Claude model than the one currently orchestrating the build (see step 4). Never Haiku — this pass needs real judgement (operator identity, day-trap reading), not mechanical extraction.
   - **Primary source is NOT bustimes.org.** The prompt below requires the red-team's first/primary source to be something other than bustimes (operator site, Traveline, BODS, council pages); bustimes may only be used as a cross-check, never the sole or first source for a service. This is what removes the "shared primary source" correlated-error risk, not just the "different agent instance" one.
2. **On mismatch = block hard / flag soft.** A finding is **HARD** (blocks the build loudly) only if the displayed leaflet would be *wrong or undrawable*; everything else is **SOFT** (logged for review, never blocks).

## Procedure
1. `$S6 = stage.js new S6` (dated dir, no version). `cd "$S6"`.
2. **Pull the inputs to diff against:** `stage.js pull S1`, `pull S2`, `pull S3` into `$S6`. (They join the run dir alongside the outputs, same as S4/S5.) **Then copy `corridors_report.json` in from the latest S4 if that run wrote one** — it is an S4 output, no `pull` brings it, and the ladder checks below read it from `$S6`. A rollout leaves it there for free, so this only bites a hand-run S6, and it bites SILENTLY: on 2026-09-06 Ramsey's re-run came back 2 soft against its predecessor's 3, and the missing finding was a `weak-corridor-bundle` that had not cleared — the check had simply been handed nothing. An absent file is also the correct normal case for a town setting neither `internalCorridors` nor `corridorPalette`, which is why nothing can flag it, so **the way to tell the two apart is the town's own `routes.json`, not the file listing.** Same shape as *the check that goes quiet on a missing input* throughout this file: a PASS that means "nothing was compared" reads exactly like a PASS that means "nothing is wrong". **Diff the new findings against the run you are superseding, always** — a report that got quieter is the one to distrust, and that diff is what caught this one.
3. **Ask whether this town already owns a red-team answer.** Run `node "%SK%\redteam_source.js"` from `$S6`. It reads every `redteam.json` this build has ever bought and decides: **REUSE** (it copies the answer into `$S6` and you skip step 4 entirely) or **BUY** (spawn the agent). **It names the resolved `--build` path on every run** (2026-08-29, OA-141) and **refuses (exit 2) when the folder is ambiguous** — when its default `../..` hop and the nearest enclosing `manifest.json` above `--into` name different maps. Run from the documented cwd the two agree and nothing changes; run from a PLACE's own root they do not, and it used to answer about the parent town in silence. `--foreign-build` lifts the refusal on purpose — see *Running S6 on a PLACE*, item 4. **Since 2026-09-01 (OA-166) it reuses when no SERVICE FACT the answer is about has moved, and not when the inputs merely happen to have been re-pulled.** It fingerprints route, operator, days, termini and headsigns per service, out of the S1 run that was current when the answer was derived and out of the S1 run that is current now, preferring `gtfs-services.json` and falling back to `verified-services.json`; registration windows, frequency samples and our own labelling are deliberately outside the fingerprint, and S2 is outside it altogether because geometry is not a service fact. The old rule was a pull TIMESTAMP, which is a proxy, and it bought three ~100k-token answers it did not need — measured on the real folders, Wisbech's July and 29 August S1 runs carry the identical fingerprint `ef6c6e78a0ff`, which is the reuse that had to be argued by hand in a commit note. When neither services file is readable on both sides it prints `CANNOT TELL`, says which rule it fell back to, and applies the old timestamp test — an absent fingerprint never reads as "unchanged". The answer must also be inside a 60-day window; it exits 0 for reuse, 10 for buy, and 10 is the normal outcome for a town whose data has just been re-pulled, not an error. The reasoning behind both conditions — in particular why blindness does not decay with age but accuracy about the world does — is written at the head of the script. On the estate as it stood on 2026-08-27 this reused 9 of the 18 builds that hold an answer. **If you reuse, say so in the S6 commit note** so the run records whose research it rests on.
4. **Pick a different model, then spawn the blind red-team agent** — only when step 3 said BUY. `Agent` (`subagent_type: general-purpose`) with the *exact prompt below*, substituting the town, and an explicit `model:` override that differs from whatever model is currently running this build: orchestrating as **Sonnet** → red-team on **Opus**; orchestrating as **Opus** → red-team on **Sonnet**. (If the orchestrator is something else, pick whichever of Sonnet/Opus it *isn't*.) It must NOT be given any of our data — only the town name, and the absolute path to `$S6`. **The prompt's last paragraph makes the agent write `redteam.json` itself and reply with one line**, so nothing to save by hand; if you are working from an older copy of the prompt that returns the JSON inline, save it verbatim as `redteam.json` in `$S6`. (HTML entities like `&amp;` / `P&amp;R` are fine — the engine unescapes them on load.)
   - If the agent returns prose around the JSON, keep only the JSON object.
   - It is acceptable to run the engine **without** `redteam.json` (sanity-only mode, `redteamPresent:false`) for a quick structural check, but a real verification pass needs the red-team.
5. **Run the diff/sanity engine:** `node "%SK%\verify_report.js"` (reads `$S6`; set `VERIFY_DIR` to point elsewhere). It writes `verification.json`, prints a console summary, and exits **1** on any HARD finding, **3** if it refused because the S1 is an unreviewed draft (see below), **2** on a missing input, else 0.
6. **Render the report:** `python3 "%SK%\gen_verification.py" verification.json` → `verification.docx` (mirrors `gen_disagreements.py`; red banner + HARD rows if blocked, green banner if PASS).
7. **Act on findings — and a finding about a SERVICE has a named destination** (buses-data OA-273, 2026-09-08; the full rule is [What happens to a claim](#what-happens-to-a-claim-added-2026-09-08-oa-273) below):
   - **HARD** → the build is not trustworthy. Fix the upstream stage (re-run S1/S2/S3 as needed) and re-verify. Do **not** ship a leaflet with an open HARD finding.
   - **SOFT about the artwork** (terminus, direction, days, colour, corridor) → record it for the user / a follow-up; **do not** silently edit a reproduced baseline (per the skill's "record open issues, don't fix" rule). Genuine data corrections go through a new S1/S2/S3 run + a version bump, not an in-place edit.
   - **SOFT about a SERVICE — a `missing-service`, `serves-town` or `serves-town-conflict` finding — is a CLAIM, and a claim is not finished until it has a HOME.** Before the run is committed, every claim on the report must be one of: already declared in the map's own `notOnLeaflet[]` or `redteamRejected[]`; already answered by the parent town's file; or written into `service-facts.json` at the buses root — as `queued` with the question, if nobody can answer it now. **Never in an open action's prose.** `tools/check-s6-claims.mjs`, run from the buses root, says which claims still have none; `status.js` and the `bus-work` worklist run it for you. Diff the new claims against the run you are superseding, exactly as for the findings themselves.
8. `stage.js commit S6 "$S6" --outputs redteam.json,verification.json,verification.docx --based-on "S1=…;S2=…;S3=…;S4=…" --note "<headline: N hard / N soft, key flags>"`.

## The exact blind red-team agent prompt
Spawn a `general-purpose` agent with this (replace **`<TOWN, COUNTY>`**, **`<ABSOLUTE PATH TO $S6>`** and the two "NOT the …" disambiguators; keep everything else verbatim — the strict-JSON shape is what `verify_report.js` parses).

**The final paragraph is not optional and is not decoration.** It makes the agent write the file itself. Letting a 5–10k-token JSON blob travel back through the orchestrator's context and then re-typing it into a file pays for the same content twice, once reading and once writing; across seven towns on 2026-08-26 that alone was roughly **100k tokens of pure duplication**. It used to be written here as advice under "Cost" and was therefore forgotten; it is now part of the prompt so it cannot be.

> You are an INDEPENDENT verification agent. Your job is to re-derive, from scratch and with NO prior assumptions, the complete set of bus services that serve the town of **<TOWN, COUNTY>** (NOT <the wrong same-named place>). You have NOT been given anyone else's answer; do not trust any number you cannot confirm from a live source. Treat this as a red-team audit: assume a previous analyst may have made mistakes, and find the ground truth.
>
> **What to determine** — for EVERY bus service that actually picks up/sets down passengers in the town, determine: (1) **route** — the public number/letter as branded; (2) **operator** — be precise about WHICH operator; (3) **termini** — the two end points as a two-element array; (4) **days** — plain words ("Mon-Sat", "Mon & Fri", "Daily", "limited / pre-book", …); (5) **servesTown** — true if it genuinely stops within the town, false if it only passes nearby. Also list separately any service the bustimes locality page associates with the town that does NOT actually serve it (with the reason).
>
> **How (use at least TWO independent sources) — bustimes.org is NOT your primary source.** Start from a **non-bustimes** source to establish which services serve the town in the first place: the relevant council's bus pages, Traveline, Bus Open Data (BODS), or operators' own network/timetable pages for the area. Only THEN use bustimes.org (`https://bustimes.org/localities/<slug>` and each service's page) as a **cross-check** — to fill in stop-level detail, catch anything your primary source missed, or resolve an ambiguity — never as the source you start from or the one you trust by default. Every service still needs a second, different source confirming it (operator's own site/timetable, Traveline, BODS, council pages — bustimes counts as one of these only if it was not also your primary). Where sources disagree, say so in `notes`, and note in `sources` which one you treated as primary for that service. Watch operating-days traps (a "Mon-Fri" heading can hide a separate Saturday timetable = Mon-Sat) and operator identity (a number can be run by different operators in different areas).
>
> **Output — STRICT JSON only.** Return ONLY a single fenced ```json code block, no prose, exactly this shape: ```json { "town":"…", "derivedAt":"<ISO date>", "sourcesConsulted":["<url>"], "services":[ {"route":"301","operator":"Dews Coaches","termini":["Ramsey","St Ives"], "days":"Mon-Sat","servesTown":true,"confidence":"high|medium|low", "sources":["bustimes","operator-site|traveline|bods|council"],"notes":"…"} ], "excluded":[ {"route":"101","operator":"…","servesTown":false,"reason":"…"} ] } ``` Include EVERY serving service in `services` and EVERY non-serving/expired one you considered in `excluded`. If you cannot confirm a field, give your best value, lower `confidence`, and explain in `notes` — never omit a field. No comments inside the JSON; it must parse with a strict parser. Be thorough and skeptical — the whole point is that you arrive at the answer independently.
>
> **Where a route number is shared or branded, say which is which.** If two different operators run the same number in this area, list them as two separate entries and make `operator` unambiguous on each — that pairing is done on the operator, so a vague name merges two real routes into one. If the operator brands the route (`46 (Lynx)`, `ZIP2 (Ely Zipper 2)`, `102 (Flightline)`), put the plain number in `route` and the brand in `notes`; a brand inside `route` used to create a phantom second service. **And `route` names exactly ONE route — never a slashed list.** Write `18` and `18A` as two entries, or one entry for the one that runs with the variant in `notes`; `18/18A`, `67 / 67B` and `LGW / LHR / OXF` are all real answers we have received, and each one keyed on a name no town carries. The reader now splits them, but a three-route entry is still heard by only the first of the three — on 2026-09-06 an exclusion written `LGW / LHR / OXF (The Airline)` went unread for four days and then reached only the LGW.
>
> **Write the file yourself. Do NOT return the JSON in your reply.** Save it to `<ABSOLUTE PATH TO $S6>/redteam.json` and reply with ONE line only: the town name and the number of services you found.

## What the engine checks, and how it classifies

### Structural / geographic sanity (no red-team needed)
| Check | Severity | Catches |
|---|---|---|
| Every **displayed** route has full-chain data in `routes_full_atco.json` | **HARD** | a drawn route that would be a stub / undrawable |
| Every **drawn** ATCO (in `routes_intown_atco.json`) has a coord in `atco2ll.json` | **HARD** | orphan stop with no coordinate |
| `routes_full` termini align with S1 declared termini (locality-token match at chain ends) | **HARD** if *neither* terminus matches; **SOFT** if one matches, one is just a naming variant | chain that ends somewhere else entirely vs. "Cambridge"→`CITY` naming |
| **Terminus coverage** — every displayed route lands in checked / unavailable / skipped, and `summary.terminusCoverage.accountsForAll` asserts the three sum to `displayed` | one **SOFT** `terminus-unavailable` per build, naming every route and its reason | a check with nothing to compare against reporting once per route as though it had looked |
| **Direction**: the drawn edge stop's bearing from the anchor vs. the terminus bearing | **HARD** > 90° apart (drawn the wrong way); **SOFT** 55–90° (arm worth a look) | a route drawn leaving town toward the wrong side |
| **Counts plausible**: 0 drawn stops, > 80 drawn, or full chain < 2 | **HARD**; **SOFT** at 45–80 drawn | nothing to draw / accidentally drawing the whole chain |
| **Complexity-ladder remedies** — read from S4's `corridors_report.json`, when the town has `internalCorridors` / `corridorPalette` | all **SOFT** | see below |

**Why the ladder checks are SOFT.** They are judgement calls a human signed off, not data errors — but each one is a way the *map* can state something false, which is what S6 is for. Absent file (the normal case) ⇒ no findings.

| Finding | What it means |
|---|---|
| `weak-corridor-bundle` | a family's member co-runs with it over < 60% of its route. **The row says two different things depending on the family, and the check reads which from `routes.json`, not from the report** (OA-249). For a PLAIN family (`internalCorridors` entry written as a bare array) the rest draws as a second same-coloured line going somewhere else, which is a defect: **drop that family**. For a STYLED family (written as `{routes, style}` — OA-176 4.24) every member keeps its own colour and the unshared stretch draws alone exactly as it would with no family at all, so the row is the SIZE OF THE SHARED STRETCH and not a fault: read it, and ask only whether the family still earns its place. The `evidence.style` field says which you are looking at |
| `colour-clash` | with `corridorPalette` in force, one hue is used by two unrelated corridor groups — a reader reads one colour as one corridor, so this asserts a corridor that does not exist |
| `palette-exhausted` | more than ~12 distinct colours are drawn; colour no longer identifies a line at all |

### Red-team diff (needs `redteam.json`)
| Diff | Severity | Notes |
|---|---|---|
| Red-team says a service we **include/draw** does **NOT** serve the town | **HARD if the sheet draws it, SOFT if no sheet does** | **SEVERITY FOLLOWS THE SHEET, NOT THE FACT** (Peter's decision, 2026-09-06, buses-data OA-004 q5). Three states, and the row says which one you have. **Drawn → HARD**: a reader is being shown a bus the red team says does not serve the town, and the message reads *"we include it and draw it"*. **Not drawn, but our data says `servesTown: true` → SOFT**: still raised and still a real curation lead, but it no longer blocks, because nothing a reader can see is wrong; the message says so in terms, quoting the in-town stop count and the absence from `routeOrder` and the palette. **Neither drawn nor claimed → nothing.** Until 2026-09-06 both of the first two said *"but we include it"* and both were HARD; that sentence stood in the backlog for a fortnight as a claim that two published sheets drew a closed-door school service (OA-262 item 1). Same rule as the X46 adjudication: exclude by default only where being wrong strands a passenger. **The two rejection arms below keep HARD deliberately** — an expired `redteamRejected` and R-1b are about the state of an adjudication, not about what the sheet draws |
| Red-team termini match **NEITHER** of our termini for a route | **HARD** | independent terminus contradiction |
| No end of our drawn chain carries a NaPTAN locality code | one **SOFT** `terminus-unavailable` for the build | nothing was compared; the old wording claimed a disagreement about an empty list |
| Operator differs | **SOFT** | name/label only (the 5A "Stephensons vs Stagecoach" question lands here) |
| Termini differ on **one** end / naming | **SOFT** | "Hinchingbrooke" vs "Huntingdon / Hinchingbrooke" |
| Operating days genuinely differ | **SOFT** `days` | ours "Daily" against their "Mon-Sat" — a difference of fact |
| Their days are ours plus a qualification | **SOFT** `days-qualified` | "Mon-Fri" vs "Mon-Fri (not bank holidays)" — decide whether the qualification belongs on the sheet |
| Our days read `"?"` | **SOFT** `days-unknown` | a gap on our side, not a disagreement |
| Their days are ours plus the word "only", or a plural day name | *nothing* | "Sat" vs "Sat only", "Thu" vs "Thursdays only" — `normDays` folds both away |
| Red-team finds a town service **absent** from our set | **SOFT** `missing-service` | inclusion candidate — and on a **borrowed** answer the row says so and names the lender, because a town answer is a superset of a place's services |
| Red-team writes a **second entry** for a route we already carry | **SOFT** `operator` | the pairing is one-to-one, so the second entry is a disagreement about who runs it — not a missing service. Ely Co-op's answer named route 9 twice, Stagecoach East and A2B, and the leftover used to arrive as an inclusion candidate for a route the sheet draws (OA-274, 2026-09-09) |
| Red-team lists a **sub-service** we fold into a parent (`variants[].subServices`) | **SOFT** `sub-service` | informational; aliased to the parent so it isn't noise (301S/301V/301X → 301) |
| We mark a route **not** serving town (`notOnLeaflet`) but red-team finds it **does** | **SOFT** `serves-town-conflict` | re-examine (e.g. seasonal weekend service) |
| Red-team finds a route the town has **already ruled off** in one of its four exclusion fields | **SOFT** `known-off` | the row carries the town's own recorded reason — a decision to confirm, not news |
| An exclusion field declares a route the sheet actually **draws** | **HARD** `known-off` | the declaration is false, or it is silencing a finding about a route that is on the sheet |
| An exclusion entry names a **class** rather than a route (`{"group": "…"}`) | **SOFT** `known-off` | nothing can match a route against it, so every service it means is still a candidate |
| We have a route the red-team didn't confirm | **SOFT** `not-confirmed` | the red-team may simply have missed it |

Classification is deliberately **cautious about HARD**: terminus/direction checks only go HARD when the contradiction is unambiguous (no token overlap at all / > 90°), so naming artifacts (a terminus coded under a parent locality, a route that leaves town on a different bearing than the straight line to its destination) stay SOFT and never falsely block a good build.

## What survives in git, and what does not (added 2026-08-22; redteam.json tracked 2026-08-27)
`buses-data`'s `.gitignore` ignores `Areas/**/S6-verify/**` and `Places/**/S6-verify/**`, re-including `README.md`, `manifest.json`, `*.docx` — **and, since 2026-08-27, `redteam.json`**. `verification.json` is still not tracked, and should not be: our own code rebuilds it for free from inputs git already holds.

`redteam.json` is the one file in an S6 run that cannot be rebuilt at any price short of re-buying the research. Until that change, seventeen of them existed on disk and **none was in git**, while `prune_runs.py` listed `S6-verify` in `SINGLE_KEEP` and so kept only the newest run per town — run estate-wide it named **nine S6 folders for deletion, seven of which held an answer**. On the order of 1.7 million tokens of purchased research, one `--apply` from gone, with the SyncBack mirror as the only other copy. `S6-verify` is now in `NEVER_PRUNE`.

`verification.docx` still carries a run's verdict into git, which is why step 6 is not optional: an S6 whose report was never rendered leaves nothing behind but a manifest row.

If a run needs a prose note — a place run where the HARD count needs interpreting, say — **name it `README.md`**. That is the keep-rule the ignore file already has (`!Areas/**/README.md`), so the note is preserved without forcing anything past the ignore rules or changing repo policy. Check with `git check-ignore -v <path>` rather than assuming.

## A service that is deliberately not drawn — `routes.json notShown[]` (added 2026-08-28, OA-049)

A service can be real, correct and deliberately undrawn. Both St Neots place sheets carry routes **112 and 193** — the Ivel Sprinter, an East Beds community bus outside the BODS region we pull — as Services-panel rows with no line on the map, because there is no chain to draw and there never will be from this data. The sheets already say so in words: `services_panel.js` appends *"not shown on this map"* to the row, and `routes.json` has carried `notShownNote` / `notShownNoteShort` to change those words since that convention landed.

S6 could not tell that from a route whose geometry has genuinely gone missing, so it called both HARD `no-full-chain`. On current data that one category was the **entire** distance between two BLOCKED places and two clean ones — 2 hard apiece and nothing else. A check that blocks on a decision somebody made on purpose is a check that stops being believed.

**The fix is a declaration, not a smarter check.** Add the route to `routes.json`:

```json
"notShown": ["112", "193"]
```

Inferring it — *"no chain and no palette entry, so it must be on purpose"* — was considered and rejected: it would make a genuinely broken route indistinguishable from an intended one, which is the fault this check exists to catch. Somebody has to write the route down.

**And a declaration that can only ever quieten a finding is a mute button, so this one is checked in both directions.** A declared route with no chain is a SOFT `declared-not-shown` (reported, never silent). A route the sheet actually **draws** — two or more stops in `routes_intown_atco.json` — is a **HARD** `declared-not-shown`, because that is how the key would be abused to silence a finding about a route that is on the sheet. A declared route the sheet does not carry at all is a stale entry and reads SOFT. All five behaviours are in `npm run test:prove-s6` (case 8), including an assertion that the artefact is still real against the *undeclared* config — so the case cannot quietly pass on a place that no longer carries either route.

**It changes no bytes.** No generator reads the key; that was proved by regenerating all five committed sheets of both places with and without it and comparing line for line, fresh against fresh through the identical path. So adopting it is a new dated **S3** run and no S4/S5 rebuild — which is what the two places' 2026-08-28 S3 runs record.

## A route the town has already ruled off — the four exclusion fields, read at last (added 2026-09-06, OA-259)

`notShown[]` above is about a route the sheet CARRIES with no line on the map. This is the other shape: a route the sheet does not carry at all, and somebody has decided it should not — a school contract, a seasonal excursion coach, a service that turned out to call at no stop in the town. That decision lives in `verified-services.json`, and eight town files write it four different ways: `notOnLeaflet[]`, `verifiedNotDisplayed[]` (High Wycombe, 18 entries), `notDisplayed[]` (St Neots, Beaconsfield) and `excluded[]` (Ramsey). `gtfs_refresh_report.py` read three of them and `verify_report.js` read **one**, and only where `servesTown` was `false`.

**So the commonest case had nowhere to go.** A service that genuinely serves the town and that we deliberately do not carry is invisible written truthfully — the route falls through to the `missing-service` arm and comes back as *absent from our verified set, inclusion candidate* — and writing `servesTown: false` to silence it is a lie that earns a recurring `serves-town-conflict` instead. **Huntingdon's blind red team named the same seven routes on both its runs**, 2026-08-04 and 2026-08-26, at 89k–137k tokens an answer, and no adjudication anybody wrote could have stopped the eighth.

**No new key.** Unlike `notShown[]` and `redteamRejected[]`, this fix adds nothing for a town to write: the towns had already written it, four different ways, and the reader was the thing missing.

**And since the evening of the same day there is only one field to write.** `notOnLeaflet[]` is canonical; `verifiedNotDisplayed[]`, `notDisplayed[]` and `excluded[]` are READ-ONLY ALIASES — parsed for ever, so an S6 run against a 2026-07 S1 still says what it always said, and written by nothing, which `check-exclusion-fields.mjs` enforces from buses-data's own CI over the latest S1 run of each map. Superseded runs are deliberately left alone: an older run is a dated record, and rewriting one to satisfy a gate about the present would argue with the reason the aliases are read at all. The five files using an alias were migrated the same day, each proved to give an identical reader answer before and after, so the gate is green because the estate is clean rather than because it is lenient. Every entry needs a `route` and should carry a `reason` (`note` is accepted; High Wycombe's one-word `reason` plus a `detail` is joined). `servesTown: false` in `notOnLeaflet` is deliberately NOT folded in — it keeps its louder `serves-town-conflict`.

**It is a RE-EVAL, not a silence**, worded the way the monthly refresh already words its own rows: the finding still appears, carrying the town's own sentence, so the next reader confirms a decision instead of re-deriving it from the feed. An exclusion nobody re-reads is how a school service that has become a real public service stays off a sheet for ever.

**And it is checked in the direction that could make it a mute button.** A declared route the sheet actually DRAWS — two or more stops in `routes_intown_atco.json` — is a **HARD** `known-off`, and the red team is not consulted: the drawn set alone settles it. The stale arm `notShown[]` carries is deliberately absent here, because "the sheet does not carry it" is the whole point of these fields and an equivalent arm would fire on all 18 of High Wycombe's entries every run, saying only that the town meant what it wrote.

All of it is in `npm run test:prove-s6` (case 14, seventeen checks): each of the four fields quiet on the finding and loud with the town's words, a declaration over a drawn route HARD, `servesTown: false` keeping its louder finding, a `{group: …}` entry reported and silencing nothing, and the control that declaring an unrelated route silences nothing at all. The fixture route is **discovered from the baseline run** rather than typed, so the case cannot quietly stop testing anything the day Wisbech's leads change.

**The rule is written twice and joined once.** `assets/known_off.js` is the JavaScript half and `known_off_routes()` in `assets/gtfs_refresh_report.py` the Python; they cannot share a runtime, so `npm run test:prove-known-off-parity` feeds one fixture through both — every edge case, plus every real town file — and fails when the route sets differ. It found a genuine disagreement on its first run: the Python iterated a dict's KEYS where the JS checked `isArray`, so a town writing `"notDisplayed": {…}` instead of `[{…}]` invented routes called `route` and `reason`.

**It changes no bytes.** `verify_report.js` is not in `engine_version.js`'s `ENGINE_FILES` and no generator requires `known_off.js`, so no town's engine stamp moves and no `ci-reference` is touched.

## A red-team claim that was checked and is wrong — `routes.json redteamRejected[]` (added 2026-08-28)

The blind red team is the most valuable input this stage has and it is **not an oracle**. Its answer comes from public web sources, so it cannot see a BODS calendar that opened yesterday, and it reasons about a town by its name rather than by NaPTAN's locality tree. Both of those faults produced the same false HARD twice on **St Neots route 69**: the red team called the route's "Eynesbury Tesco" stop a data-extraction artefact and excluded the route, when NaPTAN gives `0500HEYNE001` CommonName *Tesco*, LocalityName *Eynesbury*, **ParentLocalityName "St Neots"** — Eynesbury is part of St Neots, so a stop there is a stop in the town — and BODS carries 69 calling there Mon–Fri from 20 August 2026, a calendar that opened the day before that red team ran. That is also why 69 is absent from the prefix-only `gtfs-services.json` and present in the `--near` pull.

Peter adjudicated it on 2026-08-22, wrote the evidence into S1's `verified-services.json`, and S6 went on reporting HARD — because there was nowhere to put the answer. **A known-wrong finding that cannot be recorded is the most dangerous kind of red**: it is re-litigated every run, it blocks delivery on a settled question, and the pressure it creates is to waive the town or mute the check, which is how a real finding eventually stops being read.

**The fix is a declaration, not a smarter check** — same reasoning as [`notShown[]`](#a-service-that-is-deliberately-not-drawn--routesjson-notshown-added-2026-08-28-oa-049) above. Add it to `routes.json`:

```json
"redteamRejected": [
  {
    "route": "69",
    "claim": "serves-town",
    "decidedOn": "2026-08-22",
    "decidedBy": "Peter",
    "why": "NaPTAN gives 0500HEYNE001 ParentLocalityName \"St Neots\"; BODS carries 69 there from 20 Aug 2026. Do not re-open on a red-team exclusion alone.",
    "evidence": "Development Docs/route-66-and-69-evidence_2026-08-22.md",
    "recheckBy": "2027-05-20"
  }
]
```

`route`, `decidedOn`, `decidedBy` and `why` are required; `evidence` and `recheckBy` are optional. `claim` is currently documentation — `serves-town` is the only claim honoured.

**It never goes silent, and it is checked in every direction that could make it a mute button.**

| Situation | What S6 says |
|---|---|
| The claim is made and the entry is well-formed | **SOFT** `redteam-rejected`, printing the date, the decider, the reason, the evidence path and the route's in-town stop count — the adjudication is in every report, not hidden by it |
| The entry is missing `decidedOn`, `decidedBy` or `why` | It silences **nothing**. The original **HARD** `serves-town` fires as before, and a SOFT names the missing field. An undated, unexplained rejection is precisely the mute button this exists to avoid being |
| `recheckBy` has passed | The entry **stops silencing** and the **HARD** returns, naming the expiry — the rule `scripts/s6-waivers.json` applies to a deferral, and for the same reason |
| Our own drawn data gives the route **no** in-town stops | **HARD** `redteam-rejected` — the red team may have become right and the entry would be hiding it |
| This red team makes no such claim about the route | **SOFT** stale — it is silencing nothing this run |
| The sheet does not carry the route at all | **SOFT** stale |

All of these are in `npm run test:prove-s6` (case 6, ten checks), and the harness **undeclares the key itself** before asserting the artefact is real — because `stage()` seeds from the town's latest S3, which is exactly where the fix lands, so a case that merely read the config would be testing the fixed state against itself from the day it shipped. That is the failure shape *the fix invalidates its own control*, and it cost this harness four consecutive red pushes the last time.

**It changes no bytes.** No generator reads the key. St Neots adopted it as a new dated **S3** run with no S4/S5 rebuild, and all four of its byte gates still PASS against a `ci-reference` built from the previous S3; `rollout.js` reports the town UP-TO-DATE. If you do rebuild, note that the `build N.N · date` stamp is written by `rollout.js` on the way out and **not** by the generators — a hand-run `node gen_internal.js` comes out 137 bytes short on every sheet, with no stamp at all.

## What happens to a claim (added 2026-09-08, OA-273)

A **claim** is what the blind red team says about a SERVICE rather than about the artwork: it names a bus serving the town that our verified set does not carry (`missing-service`), it denies one we carry (`serves-town`), or our own file says a route does not serve and it says it does (`serves-town-conflict`). Each one cost part of an 89k–137k-token answer. Until this section existed, step 7 said a SOFT finding was "recorded for the user / a follow-up" and named no place, so a claim's outcome went wherever the nearest session put it — for a fortnight that was the prose of buses-data OA-004, which became a backlog inside a backlog. Measured on 2026-09-08: **100 claims on the latest S6 of 20 maps, and nothing counted the ones nobody had looked at.** 72 of the 100 were one fact repeated on a place after its parent town had already decided it.

**Two files, two sentences.** A map's own field says what THIS SHEET does; the register says what is TRUE.

| The sentence | Where it is written | Read by |
|---|---|---|
| *We know about this route and deliberately do not draw it* | a town's latest S1 `notOnLeaflet[]`; a place's latest S3 `notOnLeaflet[]` | S6 (`known-off`), the refresh report, `check-s6-claims.mjs` |
| *The red team claimed this and we checked; it is wrong* | the map's latest S3 `redteamRejected[]` | S6 (`redteam-rejected`), `check-s6-claims.mjs` |
| *This is what is true about this service, who decided, when, on what evidence, and when to look again* — or *this is the question, and nobody has answered it yet* | `service-facts.json` at the buses root, one entry per (route, operator, scope), `status: decided` or `queued` | `check-s6-claims.mjs`, `status.js`, the `bus-work` worklist |

**The order of homes, which is also the order to try them in.** A claim is covered by the map's own `notOnLeaflet[]` (a `servesTown:false` entry counts, though `known_off.js` leaves it out for S6's louder arm); by its own `redteamRejected[]`; by a `missing-service` naming a route the map's own verified set carries (a pairing failure, cleared by the next run); by its **parent town's** file, carrying the route or declaring it off; or by a register entry whose scope names the map, its parent, or `*`; or, LAST, by the map's own `badgeLabels`. **A parent town's decision reaches its places** — that is OA-004 decision 4, *the FACT is central, the DRAWING is local*, as a mechanism, and it is what makes 100 claims into 20. A standalone place has no parent and must answer for itself.

**The last home is a spelling, and it is the one you will meet without recognising it.** A blind red team reads the SHEET, so its claim is keyed on the badge we PRINT; every file we own is keyed on what the operator REGISTERED. `badgeLabels` in a map's `routes.json` is the join — `{"61EY": "61"}` at St Neots, `{"excel": "A", "46L": "46"}` at Wisbech — and shortening a badge is a normal deliberate thing this engine does, so the mismatch is **guaranteed** for every route that carries one rather than being a rare accident. Since 2026-09-11 `check-s6-claims.mjs` reads that map and reports such a claim as **ALIASED**, naming the registered key, instead of UNCOVERED; the same join stops a decided entry reading as a SILENCE. SF-014 is why: it sat `queued` for eleven days saying *"neither the place nor the St Neots town file carries a 61"*, and both carried it all along, as `61EY`, badged "61", in `routeOrder`, `panelOrder` and the town's `services[]`. **It is tried last, after every direct test, because a printed label can also be a live registered key on the same map** — Wisbech prints "46" for `46L` and carries a genuine `46` — so a claim about the real route must meet it as itself and never be re-pointed. When you write the register entry anyway, put the registered key in `aliases[]`: the ALIASED row names it, and an explicit alias does not depend on a config line surviving the next S3 run.

**What to write, in order.** (1) The register entry, always — `queued` with the `question` and the OA-004 `default` that would apply is enough to give the claim a home, and it is the honest state for a claim nobody can answer today. (2) If the answer is known, the decision in the same entry: `decidedOn`, `decidedBy` (Peter, or *a session applying OA-004 decision n*), `outcome` (`include` | `off` | `nothing`), `reason`, `evidence[]`, `recheckBy`. (3) Then the map's own field, because **a decided entry whose scope names a map that is SILENT about the route is red** — the register must never be a way to silence a claim without the sheet learning the answer. `include` for a service with no fixed stops (demand-responsive, door-to-door) means a Services-panel or map-notes line at the next rebuild, and the map declares it in `notOnLeaflet[]` until then with that instruction in the note. (4) Nothing is rebuilt or rendered for a decision; a decision that changes a drawing goes through a new S1/S3 run and a version bump like any other data change.

**Who decides.** **All five OA-004 decisions are made** (Peter; 2, 3, 4 and 5 on 2026-09-08, decision 1 the same day). A session may apply a decided default itself and say so in `decidedBy`; a claim no decided default covers stays `queued`; on a town with a local adviser it becomes a row in `local-decisions.json` (decision 3). OA-004 is retired and its record is buses-data `Development Docs/s6-claims-process_2026-09-08.md`.

**Decision 1 — PUBLICATION sets the default, not the commercial relationship.** The axis is *can a stranger read this sheet*, and it decides **urgency**, never which way a default points: decision 2's two directions apply to every map whatever its state. A claim on a public sheet is worked now; a claim on a sheet nobody outside the project can see may sit `queued` without the same pressure. The reasoning is that the risk is borne by the person at the stop, who cannot tell whether we have a contract with anybody — and there was no live customer to distinguish from a sample in any case, every portal organisation being a `(demo)` row.

**Two traps in reading that axis, and neither is in the register.** *Published is not public*: the portal makes a map reachable only when a `published_version_id` exists **and** the customer is `active` **and** `map.public_listed` is on, all three enforced in SQL, so `status: published` alone answers the wrong question. And **a sheet can be public with nothing in any database saying so** — the Ramsey sheet that drew CORR-001 and the St Neots v8.0 in a Love's Farm bus shelter (buses-data OA-261) both reached the public with no customer record at all. **A printed sheet is public the day it goes up.** So this is a question about the world, answered from the portal state *and* from whether a copy has been handed over or posted; it is deliberately not a field the checker reads, because a checker that read `public_listed` alone would have called both of those sheets private.

**Why the checker runs in two halves.** `verification.json` is gitignored, so `actions/checkout` produces a tree with no S6 report and a coverage check there would be green for ever. The coverage half therefore runs on the laptop — `status.js` and the worklist; the worklist passes `--require-reports`, so a run that finds no report is red rather than quiet, while the board reports *nothing to gate here* for a tree with no register and no report, because it also runs over every harness fixture and CI checkout — and CI runs `--register-only`, whose step name says what it did not look at. Both halves are falsified by `tools/prove-red-s6-claims.mjs`. The Peter-facing version of all this is buses-data's *README - How to handle what S6 finds*.

## Files S6 owns
`redteam.json` (the blind agent's JSON), `verification.json` (classified findings + summary), `verification.docx` (the rendered reliability report).

## Running S6 on a PLACE, not a town (added 2026-08-08 — St Neots Tesco Extra, first-ever place S6 run)
This engine was built for towns and reads `verified-services.json` as a **required** input — places don't have one (their S1 output is `gtfs-services.json`, a different shape, no `servesTown` flag). Before this, S6 had literally never been run on any place. Two things to know:

0. **A place can now say "we know about this route and deliberately do not draw it" — declare it in the place's S3 `routes.json` as `notOnLeaflet[]`** (Peter's decision, 2026-09-06, buses-data OA-262 item 3). Until then a place had nowhere to record it, so an adjudication made once came back as an inclusion candidate on every later run: 86 `missing-service` findings across nine places on their latest stored S6, of which 53 are a borrowed answer's superset and already labelled, and **33 are on places that BOUGHT their own red-team answer**, where the repetition costs 89k–137k tokens a time. It is the **same field a town writes**, not a fifth convention — same name, same shape, read by the same `known_off.js`, reported in the same words, and `check-exclusion-fields.mjs` covers places for free as a result. `place_verified_services.js` carries it from `routes.json` into the `verified-services.json` it builds. **It is declared in S3 and not S1** because a place's S1 is regenerated from BODS on every pull and would overwrite it. **It is NOT `notShown[]`**, which is a different sentence and unchanged: `notShown[]` means *on the panel with no line drawn*, `notOnLeaflet[]` means *off the sheet altogether* — and every route in a place's `notShown[]` is also in its `routeOrder`, which is how the two were told apart.

  **And a place's declaration now beats its own inference** (OA-274 fault 2, 2026-09-09). Every entry in the `services[]` this adapter builds is written `servesTown: true`, because its whole input is *routes with a stop inside the walkshed* — stop presence, which is an inference. A `notOnLeaflet[]` entry carrying an explicit **`servesTown: false`** is a decision somebody made and wrote down, so the adapter now writes that onto the matching `services[]` row. Until it did, the two disagreed silently: the declaration reached `known_off.js` while the inferred `true` stayed in `services[]`, so `verify_report.js`'s `if (isDisplayed || vs.servesTown)` guard kept firing and Ely Co-op's AJ2 — a school service with no BODS calendar, no stop near the Co-op and 0 in-town stops in our drawn data, adjudicated as register entry SF-003 — came back on every run. **Only an explicit `false` does this**: the commoner declaration is a route that really does call here and is simply not drawn (Ely Co-op's TIGERONDEMAND), and writing `false` for those would assert something nobody decided. `notServe` and the `serves-town-conflict` arm are built from `notOnLeaflet[]` directly and are untouched, so the [louder arm this field deliberately keeps](#a-route-the-town-has-already-ruled-off--the-four-exclusion-fields-read-at-last-added-2026-09-06-oa-259) still speaks.

1. **Generate the required input first.** Run `node "%PSK%\place_verified_services.js"` (from `make-place-bus-leaflet/assets`) in the S6 dir, after pulling S1 — it adapts `gtfs-services.json` into a `verified-services.json` the engine can read, treating every entry as `servesTown:true` (read as "calls at the place"), since P1's `--near` radius already filtered to stops inside the walkshed.

2. **A place's terminus checks no longer false-positive HARD (fixed 2026-08-22), so a place's HARD count is now readable.** It was not before: St Neots Town Centre came back BLOCKED with 13 hard on 2026-08-21 of which ten were pure artefact, and Tesco Extra's 6 hard were *all* artefact. Those same runs now read 3 hard and 0 hard, with every removed finding re-stated honestly as a SOFT. What changed, and why this is not just a muted check:

   - `place_verified_services.js` now resolves termini through `routes.json`'s curated `destinations[]` where an entry names the route, falls back to the raw GTFS headsign otherwise, and **stamps `terminiSource`** (`destinations` or `gtfs-headsign`) on each service. A town's file has no such field, so towns take none of the branches below.
   - **S-4 (declared terminus vs drawn chain) is downgraded to SOFT for a place, deliberately, because for a place it is structurally circular and asserts nothing.** Both sides come from the same BODS pull — `routes_full_atco.json`'s direction `name` IS the headsign pair — so any scheme resolving a headsign via the drawn chain would pass by construction. The finding now says the check is *unavailable*, which is true, rather than inventing a pass for it.
   - **The red-team terminus check carries the weight for a place, and was rewritten to work.** Instead of comparing our headsign against the red-team's settlement name (which can never match), it asks whether each red-team settlement is a **locality at the ends of our drawn chain**. The red-team is sourced blind, independently of BODS, so this is a real assertion — and it was proven to go HARD on demand by feeding it a terminus our chain does not reach.
   - Where a red-team terminus is unmatched *and* a chain end carries no NaPTAN locality code (a cross-border route — St Neots' 905 ends at Bedford `020035035`), nothing was actually compared, so it is SOFT, not HARD.
   - `naptan_localities.json` (new, in `make-bus-leaflet/assets/`) maps the few locality CODES the 3-character prefix rule cannot reach. Checked against every chain-end locality in the built estate — 27 distinct codes — **`CITY` (Cambridge) was the only irregular one**, confirming the note at the foot of this file. A code with no entry is unverifiable, never a mismatch, so a missing entry cannot manufacture a false HARD. Adding `CITY` also cleared five long-standing false SOFTs on Huntingdon, St Ives and St Neots.
   - **The hand file became the FALLBACK on 2026-08-31 (OA-038): the check now reads the DfT stop register first.** Two gazetteers were built on 2026-08-22 by sessions that did not know about each other — this one-entry hand file, and `_gtfs/naptan.sqlite`, which carries a `LocalityName` and a `ParentLocalityName` for all 127,658 stops and independently settled the route 69 question by giving Eynesbury a parent locality of St Neots. `verify_report.js` now builds its code→names map from the register where one is on disk, consults the hand file after it, and behaves exactly as before when there is none. **The join is on OUR OWN token, not on `NptgLocalityCode`** — that column holds the national code (`E0043711`) and the code this check compares is the four-letter mnemonic `localityToken()` slices out of an ATCO code, so a lookup on it returns nothing at all; the map is keyed by running `localityToken()` over the register's own `ATCOCode` column, which makes the join exact by construction. Measured across all 17 maps' newest S6 runs, before and after: **five terminus SOFTs removed, none added, no hard count and no exit code changed** — Huntingdon X3, March 33A, St Neots 150, and route A on both St Ives and St Ives Bus Station, the last of which is the item `OA-004` in the buses-data backlog named. That direction is structural rather than lucky: `nameMatchesLocality` returns a boolean and a *false* is what raises a finding, so a new source of *true* can only ever subtract.
   - **`_gtfs/*.sqlite` is gitignored, so CI has no register and this path is inert there.** A finding can therefore legitimately appear in CI and not on the laptop. It is also why section 13 of `tools/prove-s6-checks.js` **builds its own two-row register** and points `VERIFY_NAPTAN` at it rather than reading the real one: a case that needed the 38 MB file would be green for ever on the one machine that has it and silently skipped everywhere else. The pair is one run and one invented terminus with the register as the only variable — resolving it removes the finding, not resolving it leaves the finding standing — and a fourth check asserts the never-adds claim by diffing the two runs rather than reasoning about them. **And the runner cannot open a register either: CI is on Node 20, where `require('node:sqlite')` throws `ERR_UNKNOWN_BUILTIN_MODULE`** — the module arrived in Node 22 and this laptop is on 24. The first push took the whole harness down after twelve sections had passed, which is how this was learnt rather than foreseen. Section 13 now resolves the module defensively and SPLITS: the two register arms are printed as **NOT RUN** by name when it is absent and counted as neither pass nor failure, and the no-register arm runs everywhere — which is the honest arrangement, because that arm is the FALLBACK PATH and the fallback is exactly what CI executes in `verify_report.js`. `verify_report.js` itself needs no such split: its `require` is already inside a `try`, so a Node without the module simply behaves as it did before 2026-08-31.

3. **What a place's remaining HARDs mean — and as of 2026-08-28 there are none.** On the St Neots Town Centre run the three survivors were all genuine and all on the open-actions list: two `no-full-chain` HARDs on routes 112/193, carried deliberately as "not shown" panel rows, and one direction question on route 66. All three have since been answered rather than muted — the 112/193 pair by the `notShown[]` declaration described above (OA-049), the direction one by the paragraph below. **Both places now read 0 hard** (Town Centre 17 soft, Tesco Extra 14 soft) on their 2026-08-28 runs. **That last sentence used to read "two independent checks pointing at one route is real signal", and it was wrong** — see "The four noise sources" above. The direction check cannot run on a place at all (no `intown_cfg.json`, so no in-town prefix, so no buffer stops, ever), so the corroboration was one real check plus one structurally incapable of disagreeing. The real one was the red-team terminus comparison, which put 66's red-team terminus (Fenstanton) nowhere near our chain ends (HUNT, STNS); it has since been answered in the data — this place now carries curated `destinations[]`, the red team's other terminus (St Neots) matches a chain end, and route 66 reads SOFT on current inputs.

Everything else (red-team diff, direction/count sanity, the ladder checks) behaves normally and is genuinely informative for a place — treat SOFT findings (esp. `missing-service`) as real curation leads, same as for a town.

4. **A place may BORROW its parent town's red-team answer, and every HARD it produces is then restated as a SOFT** (decided by Peter 2026-08-29, OA-141/OA-140). A place draws a subset of its town's services and the town usually already owns a recent blind answer, so seven of the ten unverified place maps cost nothing instead of ~700k tokens. The independence argument survives whole — the red team never saw our data either way, and blindness does not decay by being read twice. What does not survive is the SCOPE: a town answer is about *services serving the town* where a place asks *services calling at these stops*, so it can be legitimately silent about a service reaching the place but not the centre. Evidence, then, and not a verdict.

   Run this **from the place's new S6 run dir**, after `stage.js pull S1 S2 S3`. Both paths are real; the only thing that changes per place is the `--build` value, which names the parent town:

   ```bash
   node "C:/u3a St Ives/.claude/skills/make-bus-leaflet/assets/redteam_source.js" --build "C:/u3a St Ives/Using AI/Buses/Areas/Beaconsfield" --foreign-build
   ```

   Without `--foreign-build` a cross-map answer is **refused** (exit 2) rather than quietly taken — which is the OA-141 failure it was written for: run from a place's own ROOT, `redteam_source.js` used to resolve `--build` two levels up onto the parent town, print `redteam_source — Beaconsfield` for a place called Beaconsfield Waitrose, answer REUSE and copy the town's answer in, with nothing in the output saying so. It now names the resolved `--build` path on every run. The copy it places is stamped `_borrowedFrom`; the answer in its own build is never touched; `verify_report.js` reads the stamp and does the downgrading, keeping every finding in full with the reason appended. `summary.borrowedRedteam` and `summary.downgradedFromHard` record it in the file, because the console banner that qualified a PASS does not outlive it. **The three standalone Co-ops — Ely and both Godmanchesters — have no parent town in the tree at all and still need a bought answer.**

5. **THE BORROW WAS EXERCISED SEVEN TIMES ON 2026-08-29 and here is what it actually did** (OA-140). St Ives Bus Station, all three High Wycombe places, both Beaconsfield places and St Neots Co-op were verified in one afternoon, borrowing from four towns. All seven PASSED at 0 hard, and the whole round cost no red-team tokens against an estimate of roughly a million. **Five of the seven downgraded NOTHING** — `summary.downgradedFromHard` is empty — so those PASSes do not lean on the borrow in any way, which is worth saying because the mechanism's whole risk is that it quietly props up a verdict. The two Beaconsfield sheets each downgraded exactly one finding and **it is the same finding**: route 624, which the red team calls a closed-door school/works service not open to the public and which both sheets include. So the first thing the downgrade ever fired on was a real question rather than an artefact. **When a borrowed run downgrades something, expect it to be one question across several sheets, not one per sheet** — the sheets share a town, so they share its data faults.

6. **A PLACE'S SOFT COUNT WAS 80% CHECKER, AND ON 2026-08-29 THAT WAS FIXED.** The seven runs of that afternoon produced soft counts from 11 to 113 and 283 of the 353 carried no information. All three sources are now handled in `verify_report.js`, each paired with a proof in `npm run test:prove-s6` (cases 10–12) that the same check still fires on a genuine fault of its kind. Estate-wide, counted over all seventeen maps from their current S1/S2/S3, the soft total went from **567 to 338**. The old text is kept below each bullet as the record of what the fix is for.
   - **217 terminus findings compared against nothing — and 41 of them were on TOWNS.** Where no end of any direction of the drawn chain carries a NaPTAN locality code, the check has no right-hand side. It now reports itself unavailable **once per build**, in a grouped `terminus-unavailable` finding naming every route and its reason, with `summary.terminusCoverage` beside `directionCoverage`. The measurement that provoked it is the part worth keeping: **the terminus check has never once run on High Wycombe (0 of 34), Beaconsfield (0 of 7), or any of their five place maps** — 132 of the estate's 217 displayed routes, every Buckinghamshire map — because Buckinghamshire's ATCO codes are not in the `0500H<LLLL>nnn` style this check reads. It said so 34 times rather than once, in the language of a comparison, which is how a check that cannot run reads as a check that looked. Cambridgeshire maps have full coverage. *(The harmful wording was the red-team variant: "NEITHER red-team terminus … is a locality at the ends of our drawn chain", stating a disagreement about an empty list.)*
   - **118 `missing-service` leads, of which the borrowed answer's own breadth is most.** A town answer is a superset of a place's services, so every town route that does not call at the place reads as an inclusion candidate; High Wycombe Aldi draws 12 against a borrowed answer of 44. These are **not** filtered — St Neots Co-op's W9/W10 leads come out of this same path and are real (OA-050) — but the row now says the answer was borrowed, names the map it was bought for, and carries `evidence.supersetArtefactPossible`. A reader can sort a superset artefact from a lead without knowing OA-141 exists.
   - **102 `days` findings were four different things wearing one label.** 19 differed only in wording ("Sat" vs "Sat only", "Thu" vs "Thursdays only") and `normDays` now folds both the word *only* and plural day names away, so they raise nothing at all. The rest split three ways: `days` for a genuine difference of fact (34), `days-qualified` where the red team gives our days plus a qualification (34), `days-unknown` where our own value reads `"?"` (15). Only the first is a disagreement about which days a bus runs, and it was 1 row in 3.

7. **Both structural checks report their own coverage now** (2026-08-29, OA-048 and OA-156). `summary.directionCoverage` and `summary.terminusCoverage` each carry `checked / unavailable / skipped / displayed / pct` plus `accountsForAll`, which asserts the three buckets sum to `displayed`, and the console prints both fractions beside the verdict. A place always reads `0%` on direction and its `direction-unavailable` finding carries `allBlind: true` — by construction, not a fault, and Peter decided on 2026-08-29 that places stay out rather than get a check of their own shape. On TOWNS the direction check ran on **26 of 95** drawn routes, and on High Wycombe and March on none at all; the terminus check ran on **72 of 217** across the whole estate. `directionCoverage.unavailableWithChainContinuation` records how many of the declined routes have a full chain that runs on past the drawn window — **45 of 55** — which is the denominator any future attempt at that check has to be designed against.

   **Two instruments for closing that gap were built and measured on 2026-08-29, and NEITHER works** — the same outcome as OA-033's two levers, and recorded here so nobody rebuilds them. *(a) The chain-continuation fallback*: take the last drawn stop in chain order and compare its bearing from the anchor against the bearing to that arm's chain end. It reaches 44 of the 55, and it produces large angles on sheets that are correct — Beaconsfield's **X74** reads 137° because the route runs south of the town centre anchor along the A40 and then exits west toward High Wycombe, which the coordinates confirm is exactly what the sheet draws. *(b) The per-arm reduction of the existing check*: identify the edge stop's arm from chain order and compare against that arm's own end instead of the closest of all chain ends. St Ives **A** goes from 22° to 114° and **B** from 11° to 153°, because a busway stop appears in both directions and its presence in a stop list says nothing about which end it is heading to. The lesson under both: **the anchor-bearing instrument tolerates only the "closest end" leniency it already has.** A bus route is not a straight line, and a bearing taken 2–5 km out compared with one taken 15–25 km out has a legitimate spread wide enough to swallow the signal. A different instrument is needed, not a tighter version of this one.

## Cost — read this BEFORE spawning (added 2026-08-26, after a seven-town run blew a session limit)

**S6 is the most expensive stage in this skill by a wide margin, and the cost is all in the red team.** Measured across seven towns on 2026-08-26: **89k–137k tokens and 41–70 tool calls per town**, about **814,000 tokens for seven**. That is inherent — the prompt demands a from-scratch re-derivation from council pages, operator PDFs, tender notices and BODS, with bustimes only as a cross-check — and it is the whole value of the stage. Do **not** try to make it cheaper by weakening the prompt.

Do make the *orchestration* cheaper. Three rules, the first two learned by getting them wrong in one session:

1. **Spawn two or three towns at a time, never seven.** All seven at once hit the session limit: one agent finished, six were killed mid-research, and re-running those six from cold meant paying for roughly **thirteen agent-runs to get seven results**. The agents are independent, so batching loses nothing that matters and removes the all-or-nothing failure.
2. **Have the agent WRITE `redteam.json` itself — do not let the JSON travel back through the orchestrator's context.** This is now the last paragraph of the prompt above rather than advice here, because as advice here it was forgotten. Returning a 5–10k-token JSON blob and then re-typing it into a file pays for the same content twice, once reading and once writing. Across seven towns that alone was roughly **100k tokens of pure duplication**.
3. **Do not buy what this town already owns.** Step 2a's `redteam_source.js` is the cheapest of the three by a distance: it costs nothing to run and, on the estate as at 2026-08-27, answered REUSE for 9 of the 18 builds holding an answer. A red-team answer is independent because it never saw our data, and that does not decay — only its accuracy about the world does, which is why the rule turns on whether a service fact it is about has moved — route, operator, days, termini, headsigns — and on a 60-day backstop, rather than on freshness for its own sake. **If it says BUY and you can say why the change cannot have moved the answer, say it to the tool and not to a commit message**: `--reuse-anyway "<reason>"` prints every reason it would have bought for, requires a reason of its own, and stamps `_reuseOverride` into the copy it places in the run dir, so the override travels with the run. A guard this expensive to obey and this cheap to bypass gets bypassed silently otherwise, and it was — twice on its first day of being wrong, both times correctly.

A seven-town clear-the-board exercise is two or three sessions' work. Plan it that way rather than discovering it.

## The four noise sources, and what each one does now (fixed 2026-08-27, OA-129 Phase 2)

These four produced findings that looked like defects and were not. Until 2026-08-27 they were documented here as things a reader had to remember to discount; they are now handled in `verify_report.js`, and each fix is paired with a proof that the same check still fires on a genuine fault of its kind — `npm run test:prove-s6`, which went red on 12 of its 22 assertions against the pre-fix engine and now carries 63 across twelve cases. The old advice is kept below as the record of what each fix is for. **The general rule still stands: when a direction or terminus finding surprises you, look at `_latest/internal.jpg` before believing it.**

Estate-wide the four fixes take the stored runs from **34 HARD findings to 12**, and the twelve that remain are all genuine. One HARD was **added**, which matters more than the removals — see the last bullet.

- **Direction now requires at least TWO non-core buffer stops, and says so when it has fewer.** The code picks the edge stop from `seq.filter(a => !isCore(a))`, and its own comment explains at length why the farthest *drawn* stop is the wrong choice — but `const cands = edgeCands.length ? edgeCands : seq` then fell straight back to that rejected behaviour whenever a route had **no** buffer stop, comparing an in-town stop's bearing against the terminus, which asserts nothing. With exactly **one** the selector has no choice and returns it whichever way it points. All four direction HARDs across seven towns on 2026-08-26 (Huntingdon T1, March 32, Ramsey 32, Ramsey X31) came from routes below that threshold; the only two from routes with a genuine choice (St Ives 301, 5A) were SOFT and were real. Below the threshold the check now emits **one** SOFT `direction-unavailable` per town naming the routes — one per route would just be a different kind of noise, and Wisbech would have produced seven. At two or more it goes HARD exactly as before.
- **A route number is not a key, on either side.** Our own `verified-services.json` has carried a `key` field all along wherever the number repeats — Wisbech runs two route 46s (Stagecoach East to March, Lynx to King's Lynn) keyed `46` and `46L`, which is how the geometry and palette key them too — and this file was indexing on the number, so **the Lynx entry silently overwrote the Stagecoach one: route 46's drawn chain was checked against the LYNX termini, and 46L was never checked at all.** On the red team's side the agent writes what the operator brands, so `46 (Lynx)`, `ZIP2 (Ely Zipper 2)` and `102 (Flightline)` produced keys we do not hold and the same route appeared **twice**, once as `not-confirmed <ours>` and once as `missing-service <theirs>`. The two sides now pair on the bare number and are told apart by **operator**, which is the only thing that actually distinguishes them. **A brand is not the only thing a red team writes into `route`, and the second shape took a year to notice** (OA-262 item 2, 2026-09-06): it also writes a SLASHED VARIANT LIST — `18/18A`, `32/32A`, `36/36S`, `67 / 67B` — which the bracket-strip left untouched, so the key was one no town has ever carried. St Neots draws 18 and declares 18A a `subServices` variant **in the same file**, and its newest run said in one breath that `18/18A` was a missing service and that its own `18` was unconfirmed: one route, two findings, contradicting each other. Pairing now falls back to matching a slashed key on either side of the slash, in a **second pass**, so an exact match always outranks a near-miss and one `18/18A` cannot be handed to two different routes of ours. A slashed route we genuinely do not carry is still reported, under the name the red team wrote rather than half of it — which is the arm `prove-s6-checks.js` §15 holds in place, because widening a match silences findings and that is the direction this fix can fail in.
- **A chain that never leaves town cannot contradict a terminus beyond it.** Wisbech's `excel` holds only its 15 local stops, both ends inside Wisbech / Wisbech St Mary, while its declared termini are Peterborough and Norwich — so "neither declared terminus appears at the ends of its full chain" was true and said nothing about the sheet, whose `external[]` correctly draws two spokes. When every chain end is in the town's own locality the finding is now SOFT and says the chain is truncated, naming the `external[]` entry where the real destination is asserted. Extend that chain one stop past the town boundary and the identical data goes HARD again.
- **An exclusion of a same-numbered route run by SOMEONE ELSE is not about our route.** This one was found by the fix above rather than before it, and it cuts both ways. St Ives' red team excluded `5A (Peterborough)`, Stagecoach East, whose own `reason` says in terms that the St Ives 5A is *Stephensons* and that a different Stagecoach 5A had taken over the bustimes URL — pairing on the number alone turned the red team telling us we were right into "red-team says route 5A does NOT serve the town, but we draw it". Exclusions now pair on operator only, with no last-resort fallback. **But the same brand-stripping surfaced a real HARD that had been silently dropped for as long as it existed:** St Neots' red team excluded `69 (formerly 68)`, Stephensons of Essex — the same operator as our route 69 — saying that corridor does not reach St Neots at all. The old exact-key match never saw it because of the four words in brackets. That finding is now live and is **for Peter to judge, not this document**; note that a previous "route 69 withdrawn" alarm on this estate turned out to be a too-narrow prefix in `town_prefixes.json`, so check the sheet and the prefix before acting.

**A large SOFT count is still not a large defect count.** High Wycombe returns 95 soft, almost all of it the red team enumerating variants (1S, 32/32A, 36/36S, 130D, 130M, 300M) and school routes (604, 643, 644, 654, RGS01/02A/02B/02C) at a finer granularity than the map deliberately models. Read the category breakdown before quoting a number at anyone.

**The direction check has never once run on a PLACE, and one of this file's own claims rested on that.** A place has no `intown_cfg.json`, so there is no in-town ATCO prefix, so `isCore` can never be true and the buffer-stop set is empty for every route of every place — the check has only ever run in the fallback mode its own comment rejects. It now says so explicitly, once per place. This corrects something written below under "Running S6 on a PLACE": St Neots Town Centre's route 66 was described there as having "two independent checks pointing at one route", and it was one real check (the red-team terminus comparison, which still fires and can still be made to go HARD on demand) plus one that was structurally incapable of disagreeing with anything. The red-team half has since been answered in the data — that place now carries curated `destinations[]` and the red team's second terminus, St Neots, matches a chain end — so on current data route 66 reads SOFT, which is the outcome the finding was for.

## An uncurated S1 is now REFUSED, not merely unreadable (Ramsey; gate added 2026-08-27)

If a town's `verified-services.json` came from `draft_town.py` and was never replaced by a real S1 pass, its `termini` hold **stop names** from GTFS headsigns where every other town holds **settlement names**. Every terminus check then fails by construction — Ramsey returned **12 terminus HARDs on that basis alone**, seven structural and five from the red-team diff, and **the five are not independent corroboration, because both checks read the same field.** The sheet itself was fine throughout: its Services panel is built from `routes.json`, which was correct. Ramsey's own `DRAFT-REVIEW.md` had predicted every finding the run produced — including the missing community services and the untuned "to X" arrows — and had sat unread since 2026-08-04 while the map was live.

`verify_report.js` now **refuses to run** when `routes.json` carries `_bootstrap` or the build folder holds `DRAFT-REVIEW.md`. It exits **3** (distinct from 2, a missing input), writes nothing, names both tells, and says the S1 pass is owed first. Setting `VERIFY_ALLOW_UNCURATED=1` forces the run — for proving the gate, or to see what the other checks say — and in that mode the terminus findings are reported **SOFT**, each stating that it is an artefact of the draft, the verdict is `not-verified-uncurated-s1` rather than a pass, and the exit code is still 3. Ramsey under the override reads **0 hard, 19 soft**, and the console says NOT VERIFIED in as many words. Nothing gets a PASS out of this: the default path never runs at all.

**A refusal is the correct answer, not an obstacle to work around.** The whole point is that the S1 pass is cheaper than triaging a confident wrong report, and the draft review usually already names what the run would rediscover.

## Reusable notes
- The red-team agent can be flaky on operating-days precision but is **excellent at operator identity and serves-town** — the two things hardest to self-check. Trust it there; treat its `days` as a SOFT prompt to re-read the operator PDF.
- A SOFT `serves-town-conflict` is the highest-value soft finding — it means our own data may be wrong about whether a route serves the town. Surface it prominently.
- **The red team earns its cost mainly on services that have changed since our data was pulled.** In one run it independently established, from a Combined Authority briefing and a GOV.UK Find a Tender notice, that Ramsey's route 31 was withdrawn 31 Dec 2025 and replaced by X31 on 2 Jan 2026; that Stagecoach's 33 no longer reaches March; that Wisbech's 68 returned to FACT on 1 June 2026; and that Huntingdon gained X1 "Blue Arrow" on 26 Jan 2026. None of that is visible in a BODS snapshot.
- **`missing-service` is where the real content gaps are, and it is SOFT.** Community and demand-responsive services are the systematic blind spot — BODS does not carry them, so an auto-drafted S1 can never contain them. One run found Rural Hoppa RH2/RH5 (Ramsey), RH3 and VL14 (Huntingdon), FACT's route 68 (Wisbech) and a Town Council community bus (Beaconsfield). Treat these as the highest-value output of the stage even though nothing blocks on them.
- **S6 audits data, not drawing.** Nothing in this stage can see a label printed under a badge. Ramsey's live sheet draws the 301 badge over the words "to St Ives" and the 305 badge over "to Huntingdon", and the run that found 14 HARDs was silent about it. If S6 is the first time anyone has looked at a town in weeks, look at the sheet too.
- The locality-token terminus heuristic (place-name first-4-letters ≈ ATCO locality code) is robust for matching but **not** for naming: Cambridge stops are coded `CITY`, Trumpington P&R is under Cambridge, etc., so expect a few benign SOFT terminus notes.
