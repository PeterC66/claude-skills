## Why these exist

Until 2026-08-25 this package's `test` script was `echo "Error: no test specified" && exit 1`, across 23,462 lines of JavaScript and Python. The `gate.js` byte gates are real and they are green, but they compare the engine's output against the engine's *own previous* output — they are a regression check, and they cannot tell you the previous output was right. This project has been bitten by exactly that: a verification harness once scored 7/7 on a map whose committed data **was** the bug's output. Every engine fault it has actually had was found by a person looking at a printed sheet.

So each test here is one of those faults, written down as a property. The comment above each one says which. Between them they cover the label placer's collision and `mustPlace` behaviour, the footer's measured wrap and its backing plate, the build-warning severities, the ratchet's arithmetic and its distance-to-target reporting, the text-quad geometry the collision metrics are built from, the engine hash, the byte-gate comparison helpers, and the icon recolouring.

**`seed_prev_s4.test.js` is a unit test because it cannot be a data one** (added 2026-08-29, OA-013). It pins the rule the rollout's dry run and its apply now share, and measured on the day, no map on the estate has an S4 input that differs from its stage copy — so the live tree would have reported the broken rule working just as loudly as the fixed one. Its first draft required `../assets/` directly and **both of its prove-red mutations survived**: a suite that resolves its own path never sees the harness's scratch copy, so it is green about code it never ran. Everything here goes through `_engine.js` for exactly that reason.

**`generator_load.test.js` asks the cheapest question in the estate, and it is the one nothing was asking** (added 2026-09-02, OA-224 Tier 4.1). *Does the file load?* On 2026-09-02 `gen_external_busway.js` — the second external template, selected by no town since 2026-08-03 — was given two calls to an undeclared `_from` by the Tier 3.4/3.5 extraction and threw `ReferenceError` before executing a line. It stayed that way for a day, through a re-vendor and a deploy to busmaps.uk, with `status.js` PASS, 98/98 sheet verdicts, 249/249 mutations, `prove-red-gates` 12/12 and CI green in all three repositories. **Not one of those gates was broken.** Every one asks *does the output still match*, and every one can only ask it of a generator some map actually runs — so the suite was silent about a file that could not execute. Worse, the one thing that DID touch it lied helpfully: `gate_lib.detectExternalStyle` probed each template against a town's committed sheet and fell back to `radial`, so *this template cannot be loaded* and *this town is not that style* were the same answer.

Three properties, and the population is DERIVED from `engine_version.js`'s lists rather than typed here, because a hand-written list rots the same way the thing it was watching did: every entry point loads without throwing; every generator exports `main()`, so its body is behind `require.main`; and requiring one **draws nothing**, checked by requiring it with the cwd set to an empty directory and asserting the directory is still empty. A fourth asserts the derived list against the generators actually on disk, which is the shape `gen_boarding.js` hid in for a month. Three mutations in `prove-red.js` prove it can fail, and the third exists because the first two are both caught by *loads without throwing*: a load-time side effect that throws nothing is the only thing the *draws NOTHING* assertion catches alone, and without it that assertion would never have been seen red. **The place half skips LOUDLY rather than vanishing** — a mutation run copies only the town engine, so `PLACE_SKILL_ASSETS` is absent there and the absence is announced; a silent `filter(existsSync)` is also how a DELETED generator would stop being checked without anyone noticing.

**`asset_load.test.js` asks that same question of the DIRECTORY, because the test above was asking it of seven files out of eighty** (added 2026-09-14, buses-data OA-344). `generator_load.test.js` derives its population from `engine_version.js`, which is the right source for the hash and the wrong one for *everything that ought to load*: on 2026-09-14 that was **7 of the 80 tracked `assets/*.js`**, and **29 of the other 73 could not have been asked at all** — with neither a `require.main` guard nor a `module.exports`, requiring one RAN it. The files outside the check were exactly the ones a person runs at a terminal rather than a gate runs for them: `rollout.js`, `status.js`, `verify_report.js`, `redteam_source.js`, `sync_ci_reference.js`, `render.js`. `rollout.js --apply` had already thrown for every town for a day by the busway mechanism, which is the same fault in the half of the engine the busway test could not reach.

**The measurement that found the 29 missed a thirtieth, and the reason is worth more than the number.** The population was computed by asking which files match neither `require.main === module` nor `module.exports` — and `font_metrics_build.js` matches the second **inside a template literal it writes to disk**, so it read as guarded while requiring it regenerated `assets/font_metrics.js`, a vendored file inside the hash closure. A regex over source text cannot tell code from a string that looks like code. The same literal is why the guard is a wrapper that does **not** re-indent the body: indenting would have changed the bytes of every file these scripts generate. That was falsified rather than assumed — the guarded builder rewrote `font_metrics.js` byte-identically, and `labeller_demo.js` wrote the same two SVGs and the same `routes.json`, hash for hash, on both sides of the change.

Four assertions, and the population is the DIRECTORY rather than any list: it is not empty (a misdirected `ENGINE_DIR` must read as a failure, not as eighty silent passes); it agrees with `git ls-files`, so an untracked scratch file cannot join it and a tracked file cannot leave it; every file loads, **prints nothing and writes nothing**, in ONE child process whose cwd is an empty directory; and every file exports something. The single child is not a shortcut — it checkpoints the name it is *about* to require to a file outside that directory, so a `process.exit()` at module scope is attributed to the file that did it instead of killing the run anonymously. The git half **skips loudly** under `ENGINE_DIR=<scratch>`, the same rule the place half of `generator_load.test.js` follows, and the child is given the package’s `node_modules` on `NODE_PATH` — **wherever that install actually is**, which since 2026-09-19 means the main checkout's when this one is a worktree and has none of its own — so that a scratch copy does not fail on `sharp` for a reason having nothing to do with the engine. `npm run test:prove-red-asset-load` breaks it **seven** ways — an undeclared identifier at module scope (the busway fault verbatim, planted in a file no map runs), a guard removed, a `process.exit(0)`, a file exporting nothing, an untracked `.js`, an engine file requiring an **undeclared module**, and a **declared dependency that resolves from nowhere** — and asserts the control green.

Population from the DIRECTORY listing, not from any list; classification by BEHAVIOUR, so a file that gains its guard changes group by itself and the entry excusing it goes red. ## Proving they can fail

A green check that has never been seen to go red proves nothing.

```bash
npm run test:prove-red
```

`tools/prove-red.js` copies `assets/` to a scratch directory, then breaks it on purpose — one deliberate one-line edit per property, each reverted before the next — 175 of them as at 2026-08-29, and again, read the count off the run — and runs the relevant suite against the mutated copy expecting it to **fail**. It prints a table of which test objected to which break, and exits 1 if any mutation SURVIVED. Nothing under `assets/` is touched: every file there is vendored into the portal and compared by `status.js`, so an edit in place would surface as portal drift the next morning.

**A survivor is almost always a hole in the suite — but check that it CAN differ before you write a test for it.** On 2026-08-27 a mutation deleting `badgeStack`'s one-element fast path survived because there was nothing to break: with one member `y0` collapses to `y` and `(n-1)/2*pitch` to zero, so the general loop draws identical bytes at every radius. It is an optimisation, not a branch, and the file's own comments were claiming a fork it does not have. An **equivalent mutant** like that gets replaced with an observable one, with a note in `prove-red.js` saying why it is absent, so nobody re-adds it — and the source comment gets corrected too. Two other survivors in that same run were genuine holes, so the default assumption still holds.

It has already earned its place. On its first run, dropping the file name out of the engine hash survived every assertion in `engine_version.test.js` — the tests checked that the hash moved when a file changed, and never that content could not migrate between two files unnoticed. That test exists now because the mutation run found it missing.

Add `--keep` to leave the scratch copy behind for inspection.

## A THIRD OUTCOME: the harness that did not run — added 2026-09-14, buses-data OA-353

**`prove-red.js` runs every suite against the unmutated copy before it mutates anything, and until 2026-09-14 the stop that guard produces was indistinguishable from an ordinary failure.** The guard is right — a mutation measured against a failing copy proves nothing — but its stop printed one line, `BASELINE FAILED: <suite> is red against an unmutated copy of the engine.`, and exited 1, which is the exit code of *a mutation SURVIVED*. On 2026-09-13 a place map's S3 moved, one estate-control test went red, and from that moment until the next day the answer to *can these 348 mutations fail?* was **nobody has asked**, while the unit suite went on reading 941 pass / 1 fail, which is an ordinary and unalarming shape. A harness needs *caught*, *survived* **and** *could not look*, or it measures itself.

**Three outcomes now have three exit codes**, and the reporting says the number that did not happen: `0` every mutation was caught; `1` the harness RAN and found a hole — a mutation survived, or an anchor is stale; `2` the harness DID NOT RUN. The stop is a block rather than a line — it says this is neither a failure nor a pass, prints `0 of 348 mutations ran, 0 caught, 0 survived, 0 anchors stale` beside a count that is normally in the hundreds, says how many of how many baseline suites are red, names each of them, and then prints each one's output. It lives in `tools/lib/baseline.js` rather than inside `prove-red.js` so that it can be driven with a stub runner in milliseconds instead of needing a repository that is genuinely broken.

**`node tools/prove-red.js --baseline-only` is the same question asked cheaply**: it runs the 48 baseline suites, prints `baseline green: 48 of 48 suites pass against an unmutated copy of assets/, 348 mutations ready to run.` and stops — seconds rather than the minute and a half the mutations take. It is worth running before a refactor, and it is the arm the harness drives end to end.

**`npm run test:prove-red-baseline` falsifies it, seven cases.** Five drive the verdict with a stub runner — a green baseline, one red suite, two red suites, a runner that answers nothing at all (which must read as red and never as green), and the two exit codes being different from each other and from zero. Two run `prove-red.js --baseline-only` end to end: green here, and **red on a scratch copy of the skill with one baseline suite deliberately broken**, because the five stub cases would all pass against a module `prove-red.js` had stopped requiring — *the subject you named yourself*. **Those last two divide one assertion and neither half is sufficient, which was measured rather than reasoned**: setting the did-not-run code back to `1` turns the exit-code case red and leaves the end-to-end case green, because that case compares the observed code to the declared constant and follows it wherever it goes.

| Command | Answers |

# Proving the S6 CHECKS can still fail — the third harness, added 2026-08-27

The other two falsify code that draws. This one falsifies code that **judges**, and it exists for a different reason from either.

On 2026-08-27 four of `verify_report.js`'s checks were rewritten because they were manufacturing findings that looked like defects and were not — across the stored runs the estate went from 34 HARD findings to 12. That is only good news if the checks can still find a real fault, and **the failure mode of fixing a noisy check is a check that no longer says anything at all, which looks exactly like success**: in both cases the report gets shorter. Neither of the other harnesses can see any of this. `prove-red.js` cannot require `verify_report.js` — it is a top-to-bottom script that reads a run directory and exits, the same reason the five generators are out of reach — and `prove-red-gates.js` compares drawn bytes, which a verification check never touches.

```bash
npm run test:prove-s6
```

`tools/prove-s6-checks.js` builds a run directory from real map data, optionally mutates **one input**, runs `verify_report.js` there, and asserts on the resulting `verification.json`. **Every case is a pair**: the artefact must be quiet, *and* a genuine fault of the same kind must still be found. So the direction check must stay silent on a one-buffer-stop route **and** still go HARD on a route reversed on purpose; a truncated chain must be SOFT **and** the identical data must go HARD once the chain is extended one stop past the town boundary; an exclusion naming a different operator must be ignored **and** the same exclusion carrying our own operator must block; and a route dropped from `routeOrder` must leave the coverage denominator **and** a service riding on another route's spoke must stay in it, because the obvious fix to the first breaks the second (section 21, OA-048). Every case is watched red against the pre-fix engine before it is believed, which is what establishes that the assertions are load-bearing rather than decorative. **The harness prints its own assertion count on its closing line; read it from a run rather than from here** — the total typed in this paragraph until 2026-09-19 said 22 while the harness was asserting well over a hundred, which is what a number maintained by remembering to change it always ends up saying.

**It seeds from the tracked S1/S2/S3 runs plus `redteam.json`, never from an S6 run folder.** Copying a stored S6 run is shorter and was the first attempt, but `S4/S5/S6` folders are gitignored: `git ls-files` over one returns `README.md`, `verification.docx` and (since 2026-08-27) `redteam.json`, and nothing else. A harness written that way runs only on the laptop that already has the data. Seeding from the tracked stages is also what a real S6 does — `stage.js pull S1 S2 S3` — and for a place it runs `place_verified_services.js` from the sibling skill first, exactly as the documented place procedure does.

**Because it seeds from `latest`, the inputs can move under the fixtures, and that is deliberate.** Every case that depends on a property of the data asserts that property and throws `fixture assumption broken` rather than quietly passing over data that no longer exhibits the thing being proved. That guard has already earned itself twice: once when route 303's chain ends turned out to span too widely for a reflection to express a reversal, and once when St Neots Town Centre's route 66 stopped being a HARD **because the data had been fixed** — the place gained curated `destinations[]`. Asserting the historic finding would have left this harness a monument to a resolved defect; it now proves the check can be *made* to fire instead.

Add `--keep` to leave the temp directories on disk, and `--buses "<path>"` if the data repo is elsewhere. It runs in `gates.yml` alongside the other two, ahead of the board.

## Prove the build-warning severities can go red

The three harnesses above falsify code that draws and code that judges a finished run. This one falsifies the thing that decides whether a build may **ship at all** — `build_log.js`, which sorts every generator message into WARN or BLOCKING and which `rollout.js` and `rollout_places.js` stop on.

```bash
npm run test:prove-red-build-log
```

`tools/prove-red-build-log.js` breaks each of the nine severity rules on purpose and requires the break to be caught. **Every case carries a NEAR-MISS** — a message that looks like the one being caught and must stay WARN — because a rule that fires on everything is as useless as one that fires on nothing, and only the near-miss separates them. It then replays the nine messages a real build writes every day and requires all nine to stay WARN, and it asserts its own case COUNT, because a harness that has quietly stopped running some of its cases reports a clean sweep either way. It needs no other repository, so it runs in CI as its own step and a cross-repo checkout failure cannot take it down.

## Where a test's scratch directory goes — one root, since 2026-08-31

**Never call `fs.mkdtempSync(path.join(os.tmpdir(), '<prefix>-'))` again.** Use `require('../assets/scratch').scratchDir('<label>')`, which puts the directory under `<tmp>/busmaps-scratch/` and removes it when the process exits.

The reason is a measurement (OA-201). On 2026-08-31 the OS temp folder on this laptop held **68,078** scratch directories under 47 unrelated prefixes, and one `npm test` run added **139** of them — `quality_metrics_ink`'s `sheet()` helper alone had left roughly 34,000, because it makes a directory per call and never removes one. The backlog row that raised it had counted 3,191 (the portal's `cbm-*`) and named the Windows SQLite-handle `EPERM` as the cause, which is true of those and of 4.7% of the total; the other 95% did not attempt cleanup at all. After the migration the same `npm test` run leaks **0**, and so does every falsification harness in `tools/`.

Three things about the helper that matter when you use it:

- **The exit sweep is belt and braces, not a replacement for your teardown.** A long suite that removes its own directory frees the disk while it runs rather than at the end of it, so keep doing that — `removeScratch(dir)` never throws, which is the point of it.
- **A tool whose `--keep` means "look at this afterwards" must call `keepScratch()`**, or the sweep takes the evidence away. Every `--keep` in `tools/` now does; `BUSMAPS_SCRATCH_KEEP=1` does the same from outside the process.
- **It does not fix the `EPERM`.** A directory holding a file the process still has open cannot be unlinked on Windows and will still be left behind — but it is left behind *inside one named root*, where `npm run sweep:scratch` can take it later. That command is a dry run until you add `--apply`, it will not touch anything younger than `--older-than` hours (default 6, because several sessions run here at once), and outside the root it knows only a **closed** list of the pre-migration prefixes, taken from `git show` of the old tree rather than typed from memory.

## The rule all of these harnesses are built on: assert the CAUSE, not the colour

**"It went red" and "it went red for this reason" are different claims, and only the second is one a mutation test is entitled to make.** Four of the attribution harness's five cases would have gone red together if the gate merely threw at startup, and a colour-only harness would have scored all four as catches — a confident green about a gate that had stopped working entirely. Both harnesses therefore read the run's output: the board prints its JSON *before* setting the exit code, so a red run is still parseable and the specific town can be checked; the gate's message is matched by regex. Both report a third verdict, `RED, WRONG CAUSE`, distinct from `caught` and `SURVIVED`. It is the same fault the withdrawn lane-mirror detector shipped with — green on a two-run comparison while the field it reported was backwards.

**And the mirror of it on the GREEN side: a case whose subject the run never found is green too.** OA-057's contract case says a place short of every completeness key must not turn the board red — which a board that never enumerated the place satisfies perfectly, and an enumeration silently walking past a map is this repository's most-repeated bug. The case carries an `also` assertion naming what the run must have SEEN: the place present, judged short of all four keys, exit 0 anyway. It was watched report `VACUOUS` with the place removed from the scratch tree.

## Two rules the 2026-08-28 round taught, which apply to every suite here

**A fixture rejected by the wrong rule certifies nothing.** The test written to prove that a *fork* is not a lane mirror passed from the day it was written — and it was passing because a minimum-separation floor rejected the fixture, not because the symmetry test it was written for did. The symmetry test never ran on any fixture at all. Nothing in a green suite can show that; what showed it was a mutation that **deleted the symmetry test and changed no verdict**. The underlying fault was in the measure, not the test: the comparison window was 6 mm and the thing it compares across is tens of millimetres wide, so the probe stopped short of its own discriminator. Size a window from the phenomenon, then print the intermediate values and check the near-miss is rejected for the reason you think.

**Aim a mutation at a term where the two rules actually differ.** The mutation for "a stadium badge is measured as a disc again" was first pointed at the *x* term — and a stadium's `rx` **is** its `max(rx, ry)`, so both rules agree exactly along x and the mutation was a no-op that survived looking like a hole in the suite. It only bites on the *y* term. A surviving mutation is a claim about the suite; check it is not a claim about the mutation.

**A harness that compares two runs cannot tell you either run is right.** `prove-lane-mirror.js` was green on every sheet while the field it was reporting was backwards. Only the artwork settles a question about the artwork — which is what this project has said since the legend-burying finding and the fixed exit device, and it has now been true a third time. Before trusting a new visual measure, render the ONE site it names, at 300 dpi, and look at it. It cost half an hour and it overturned a day's number.

**When a measure is disproved, remove the field — do not soften the name.** `laneMirrors` is gone rather than renamed, and there is an assertion in `quality_metrics_ink.test.js` that the key is absent, so it cannot drift back without somebody deleting a test that explains why. `laneCrossings` stays, because two ribbons crossing at a shallow angle is exactly what that geometry measures and it was never the thing in doubt.

**And the general one, again.** The 15 assertions written for the two new measures passed 15/15 on their first run, and the mutation run then found **three** real holes in them. A new suite asserts what its author believed.

**It found two faults on its first run, both in `status.js`, and neither was in the mutation table.** They came from reading the gate closely enough to write the harness:

- The derived-sheet rows guarded on `routesJson.internalSchematic && exists(<sheet>.svg)`. So a map whose config **asks** for a schematic and whose SVG had gone printed `-`, the same benign dash as a map that never had one. That is the precise trap `judgeNoSheet()` was written for on internal/external/boarding, still open on the other two sheet types.
- Worse: `r.schematic` and `r.diagram` appeared **nowhere** in the `bad` set that computes the exit code. Both columns were computed, printed, and then discarded — a town whose schematic came back DIFF showed DIFF on the board and exited 0, so CI passed. Eight towns draw a schematic and four draw a diagram, so twelve sheet-gates had been decorative for their whole lives.

Both are fixed and both were proven to fire by deleting a real schematic from a scratch copy of Huntingdon and watching the row go `-` → `MISSING` and the exit code go 0 → 1. Both start green on the real estate, so nothing changed colour and nobody learns to ignore a red.

## Adding a test

Load the module through `test/_engine.js`, not with a direct `require('../assets/…')`:

```js
const { Labeller } = require('./_engine.js').load('labeller.js');
```

That indirection is what lets `prove-red.js` point a suite at a mutated copy via the `ENGINE_DIR` environment variable. Unset — which is how `npm test` and CI run — it resolves to the real `assets/`.

Then add a mutation for it to the `MUTATIONS` table in `tools/prove-red.js`: the file, the exact text to replace, what to replace it with, and the suite that should object. The runner checks that the text it is replacing appears **exactly once**, so an anchor that has drifted from the engine is reported as stale rather than silently doing nothing.

**The first one landed on 2026-08-26, by a different route than expected.** `lane_normals.js` is not an extraction — nothing was carved out of `gen_internal.js`. **And on 2026-08-27 that module's unit tests proved the point in the other direction.** `lane_normals.test.js` exercised `orientSegments(segs, lateral, chain)` with chain pairs in the third argument, which is the module's documented contract — while the only real caller, `gen_internal.js`, concatenated them into the second and passed `[]` as the third. Twelve green assertions over the interface nobody used. Nothing was wrong with the drawn output, but the conflict count the module reports was a mixture of two populations, which made it useless as the basis for a build warning and was only found by going to write that warning. **A unit test proves the module; only a caller proves the wiring.** See [[feedback_assert_through_the_real_interface]].

So the cheaper route into that boundary is: when a generator fault needs new logic, write the new logic as a module rather than as more lines in the script. The re-vendor is owed either way, and this way the fault arrives with a test.

**And once a module exists, do not test it evenly — measure which branches the committed maps actually take, and test the zeroes and the ones.** `npm run gate:branch-coverage -- tools/<spec>.js` instruments a scratch copy of the engine and runs every map; where every map takes a branch, the byte gate already covers it and a unit test only repeats it. Done that way the suites here are deliberately lopsided: `services_panel.test.js` is nineteen assertions aimed almost entirely at branches **no map draws**, including `design.panelCols`, a whole Services-panel layout, and the entire `design.panelScale` opt-out; `feature_labels.test.js` is twenty-one aimed mostly at four guards whose every fault path is dark, because each guard was written after a shipped sheet went wrong and a fixed board trips nothing. The inventory of what is dark no longer lives in a backlog row: since OA-136 closed on 2026-08-27, every dark path is noted **at its own site in the engine**, marked `DARK, measured`, so `grep -rn "DARK, measured" assets/` is the register. One item was retired — `cross()` in `svg_primitives.js`, which had no caller anywhere — and the rest are kept as live features a config key selects. The specs that measured them are `tools/branch-coverage.*.js`, one per extracted module; re-run the spec rather than trusting a number, and remember a zero means "no map in the run that was done took it".

**And read a zero twice before believing it.** Dark means "no map in THIS RUN took it", and the run is a choice. `north_arrow.js`'s `angle` branch reported zero and is taken by twelve committed sheets — the probe renders `internal.svg` only, and the schematic and diagram generators inject that key before re-running the generator. Separately, three of `feature_labels.js`'s guard marks were first anchored on the NEXT guard's `if`, i.e. after the `return` they were meant to observe, so those rows could not have been anything but zero. Both look exactly like a finished answer.

Extracting helpers from the generators, one at a time, each with its test and its re-vendor, is the next step. It is logged in `Development Docs/open-actions.md` rather than left in this file.

**Each probe's four-line bootstrap is SLICED out of the real generator it stands in for**, never retyped. `engine_paths.test.js` asserts every entry point spells that search identically and that no other engine file carries the literal; a copy of it written into a test would be one more spelling, in a file that test does not read, going stale the first time the search changed. ## Prove the `_latest` mirror picks the newest RENDER and not the newest NAME — added 2026-09-16

`refresh_latest_render_choice.test.js` covers the fallback under `refresh_latest.js`'s `latestS5()`: the manifest is asked first and always has been, and what had never been asked of anything is which run gets picked when the manifest cannot answer. Until 2026-09-16 that was `readdirSync(...).sort()` and the last element — a text sort over names of the form `v<N.N>_<date>_<hhmm>`, in which `v1.9` sorts after `v1.19` and `v2.9` after `v2.32`. It is the same instrument that delivered two of the first customer's four sheets from renders a fortnight old (buses-data OA-368), and `_latest` is the folder a person opens and the folder `Collected_latests` is assembled from.

**The fixture is the estate's own fault rather than an invented one.** The two run names in the first case are St Neots Co-op's real folders, the pair delivered wrongly on 15 September 2026; the stray `_latest` sitting INSIDE an `S5-render` in the third case is St Neots Town Centre's, found by the same sweep. Measured that day over the 23 map folders, a text sort names the wrong run in 26 of the 40 versioned stage listings and in 0 of the 80 unversioned ones — which is what says the trap is the version prefix rather than sorting, because on a `date_hhmm` name a text sort *is* a chronological sort.

**What makes this worth a suite rather than a fixed line is where the fault is invisible.** Four maps get the right answer today only because `prune_runs.py` has deleted their low-numbered runs, and four more only because a MAJOR bump has kept their minors in single digits — High Wycombe is two builds from breaking. So the correctness of that listing is currently a property of the retention policy, which nobody designed as a guarantee and nobody would think to preserve; a green run on this laptop tomorrow would say nothing. Both mutations in `prove-red.js` are therefore written against the code as it stood: the text sort restored, and the not-a-run filter dropped so that a folder which is not a run at all becomes a candidate for the mirror.

**The CONTROL is the manifest answering**, because a fix to a fallback that quietly took over from the thing above it would pass every other case here and be a different bug. It is green under both mutations, which is what makes the three reds mean something.

## A suite that is never green where the work happens — added 2026-09-19, buses-data OA-344

Since buses-data OA-341 every engine change is made in a **git worktree**. At the same commit, `npm test` read **981 tests, 974 pass, 1 fail, 7 skipped** in a worktree and **981 pass, 0 skipped** in the installed checkout, and `tools/prove-red-asset-load.js` could not run in a worktree at all: its CONTROL failed, so **four of its six cases reported NOT RED**. The harness that exists to prove this check can go red was itself dead in the place the check is relied on.

**Both causes were the same shape and neither was in the engine.** A worktree has no `node_modules` — nothing is junctioned in, deliberately — and it sits at a different depth on disk. So `asset_load.test.js` put a non-existent directory on the child's `NODE_PATH`, which node ignores without a word, and the census died on the first of the four files that require `sharp`, reporting `contact_sheet.js failed while being loaded`: a sentence about the ENGINE for a condition that is a property of the CHECKOUT. And `_buses.js` walked up four levels for the buses-data estate, landing on `C:\u3a St Ives\.claude\Using AI\Buses` instead of `C:\u3a St Ives\Using AI\Buses`, so seven tests skipped — five of them the falsification controls for `collect-maps.ps1`.

**The skip half is the one worth keeping, because `_buses.js` was already doing its job.** Its whole header is about a test that silently returns when its subject is absent being green for the wrong reason, and it fixed that by making the absence a **visible** skip — which is the only reason the number could be read at all. What was wrong was not the reporting. It was that the estate **was not absent**: it was on the same disk, one directory up from where the walk looked. A correct report of a wrong question is still a green nobody reads.

**`_worktree.js` is the one statement of the answer**, used by both. `git rev-parse --git-common-dir` names the main checkout of **this** repository — not whichever other tree happens to be on the disk, which is the quiet fallback `_buses.js` rightly forbids — and the twin directory is taken at the same path relative to the repository root, so it survives either tree being moved or renamed, and returns `null` rather than guessing when git cannot answer. `BUSES_DIR` stays authoritative and short-circuits the search entirely.

**The two new mutations are the two halves of that tolerance and neither stands for the other.** Any change that lets a dependency live somewhere else risks starting to EXCUSE a file requiring something the package never declared — the busway fault this suite is for. Case 6 is that fault as a missing **module** rather than case 1's missing identifier, and it must still name the file; case 7 declares a dependency that resolves from nowhere and requires the failure to name the **dependency**, which is what says the check is consulted at all rather than being a block that happens never to fire. **Both discriminate on every machine.** A case that only reddens in a worktree would be green for ever on the laptop where `npm test` is usually run — the same trap `build_s4.test.js` fell into one section above.

**Afterwards both trees report the identical set of tests and zero skips**, and the only difference in the two runs is the new helper file itself, which `node --test` counts because every file under `test/` is a test file. Nothing under `assets/` was touched: `computeEngineVersion()` reads `8104ef1a5d` and `computePlaceEngineVersion()` `d319f5a711` either side, so no map goes stale, nothing is re-vendored and no deploy is owed.

**What this did NOT fix, and it is the same walk.** `tools/prove-red.js`, `tools/lane-census.js`, `tools/prove-known-off-parity.js` and several `assets/` scripts each resolve the buses-data estate their own way. They were left alone deliberately: the `assets/` ones are inside the engine hash closure, where there is no such thing as a free edit, so a tidy-up there is an estate re-stamp rather than a tidy-up.

## The mutation that wrote a real file into the checkout — fixed 2026-09-19, buses-data OA-001

`prove-red-python.py` runs every suite with `cwd=TESTS`, and one of its 255 mutations makes `gen_disagreements.py`'s default output a **bare filename**. A bare filename resolves against the cwd, so that mutant wrote a real 37 KB `disagreements.docx` into `make-bus-leaflet/test/python/` on every harness run — caught, red, verdict correct, and the file still there afterwards. OA-001 recorded the litter on 2026-09-18, blamed the fixture in `test_gen_disagreements.py`, and left it for a pull request of its own.

**It was never the fixture, and the answer had been in the twin suite since the twin was written.** `test_gen_verification.py`'s `test_the_default_output_lands_beside_the_json_it_was_given` runs from a THIRD directory — neither the run folder nor the repository — under a comment that says exactly why: standing in the run folder makes the mutant PASS, standing in the checkout makes it litter the test folder, *"Both were observed before this line"*. `gen_disagreements.py` carries the same default-output line and the same mutation; its case never copied the four lines that stand somewhere else. This is the *module with a TWIN* shape the Python half met twice before: the two files are read as a pair and changed one at a time.

**The fix is those four lines and one assertion.** The case now `chdir`s into its own scratch directory for the duration, restores the cwd through `addCleanup`, and asserts the written document's directory **equals** the run folder rather than only that the path ends with it — an equality the bare-filename mutant fails outright instead of failing by the accident that the expected file is missing.

**Reproduced before it was fixed, with the harness's own mechanism rather than a model of it.** A script that copies `assets/`, applies that one mutation's `find`/`to` verbatim, and runs the suite with the same `ENGINE_DIR`, `PYTHONPATH` and `cwd=TESTS` that `run_suite()` sets: **suite exit 1, and `disagreements.docx` 37,310 bytes in the test folder**, untracked and unignored. The same script against the fixed suite: **suite exit 1, and no file**. The exit code is the control — a fix that stopped the litter by stopping the mutation being caught would be a worse bug than the litter.

**Then the whole harness, and the tree afterwards is the acceptance test.** `prove-red-python.py` reads **255 mutations, all caught, control green**, and `git status --porcelain` names nothing but the edited suite; before the fix the same folder gained the docx. `run.py` reads **772 tests, OK**, unchanged either side, because a case was sharpened rather than added.

**Exactly two mutations in the file resolve a path against the cwd and now both are guarded.** Grepping the harness for the shape rather than trusting the two the eye had already seen: `verification.docx` and `disagreements.docx`, one line each, no third. That is the whole population, so nothing else in this harness can write into the checkout by this route.

**Why no gate could ever have caught it.** The litter appears only in a working tree — `actions/checkout` produces a tree in which every file is tracked, so an untracked sibling is invisible to CI for ever, which is the class of subject buses-data's `CLAUDE.md` says to ask about before putting a check anywhere near it. What sees it is the buses-data pre-commit hook's warning about an untracked file in a folder a commit is already writing to, and a person reading `git status`. Nothing under `assets/` was touched, so no map goes stale, nothing is re-vendored and no deploy is owed.
