# Document stamping and formatting

Every bus-system document shows **which version it is and when it last changed**, right there on the page when you read it or print it — and that stays true without anyone remembering to update it. A second, hand-run tool keeps the Markdown itself tidy.

## What you will see

At the top of a Markdown document, just under the title:

> **v1.4** · updated 27 July 2026

On every slide of a deck, small and grey in the top-right corner:

> v1.4 · 27 July 2026

Versions start at **v1.0**. Each ordinary edit moves the second number (v1.0 → v1.1 → v1.2). A rewrite can be pushed to v2.0 on request. The date is the day the content actually changed.

## What keeps it up to date

A hook that runs automatically at the end of every Claude session turn. It notices any in-scope document that changed — however it changed, whether typed by hand, edited by Claude, or rebuilt by a script — and updates that document's stamp. Documents that did not change are not touched at all, so nothing gets a spurious new date and no file is rewritten needlessly.

There is nothing to remember and nothing to run.

**Generated files are deliberately left alone.** The bus-leaflet stage folders already record their own version and date in the folder name (`S4-generate/v1.3_2026-07-19_0517`), the audit and verification reports stamp themselves as they are written, and the portal's finished map sheets are checked byte-for-byte against a reference — stamping any of those would do damage rather than good.

**Documents written by a SCRIPT are left alone, and they say so themselves.** A generated report and a version stamp fight each other — the hook adds a stamp, the next run of the generator overwrites the file and deletes it, the hook puts it back, and the file churns in every diff while its "version" describes nothing. Two coverage reports did that for weeks. Rather than list them by name, the stamper skips any document whose head carries a `<!-- generated by … -->` line, so the next generated report is protected by its own author saying it is generated, on the day it is written, instead of by somebody remembering to edit a policy file in a different repository.

**The pre-commit hook honours that exclusion too, from 2026-08-31, and did not before.** `check_committed_stamps.py --staged` applied the policy's exclusions on the HEAD path and not on the index path, so the hook demanded a stamp for documents this tool refuses to stamp. It went unseen for two days because the only way to reach it is to EDIT an archived document, and archiving is normally a pure `git mv` that changes no content — it fired the first time a round repointed the links inside the files it was archiving. **An unsatisfiable refusal is worse than no check**, because the only way past it is `--no-verify`. **CI had the same hole and the local fix did not reach it**: it audits by named path, and a named repo was audited with no exclusions at all because the policy config travels with the policy roots and a CI checkout is at a path no root has. Policy roots now carry `checkoutDirNames` — what the same repository is called when it is checked out somewhere else — and a repo that matches nothing is still audited fully and now says so on its summary line.

**Archived and duplicated documents are left alone too.** `Development Docs\_archive` holds superseded plans kept as a record, so there is nothing for a version stamp to describe. And anything inside a git worktree is skipped, because a worktree is a second copy of the whole repo — without that exclusion, 49 of what looked like 141 documents were duplicates of the other 92, and generated reports were getting stamped there that the policy excludes everywhere else.

## Keeping the Markdown tidy

Markdown paragraphs are written as one continuous line each, however long. Line breaks separate headings, paragraphs, list items and table rows — they are never used to wrap a long sentence onto the next line.

That looks like a fussy preference and isn't. Wrapping is invisible when you read the document, but it wrecks the record of what changed: alter one word early in a paragraph and every line after it shifts, so a one-word correction shows up looking like a rewritten section, and a real change hides in the noise.

Unlike the stamping, nothing does this automatically. When a document needs unwrapping, there is a tool that does it:

```bash
python scripts/reflow_md.py --apply "<the document or folder>"
```

Run it without `--apply` first and it tells you what it would change without touching anything. It refuses to write a file unless the words come out identical — only the line breaks may move — so it cannot quietly eat a sentence. It leaves code blocks, tables and the metadata block at the top of a file exactly as they are, and it skips generated output and other people's files.

It cannot put wrapping back. There is no undo beyond your own version control.

## Things worth knowing

- **A deck's exported PDF does not update itself.** When a deck gets a new stamp, any PDF you exported from it earlier still shows the old one. Re-export from PowerPoint when it matters.
- **The stamp does not mean "reviewed".** It means the file's content changed on that date. The runbooks separately carry a `Last reviewed` line, which is a human judgement and is left alone.
- **Adding a document** to one of the three folders picks it up automatically at v1.0.
- **The stamp cannot tell you that other documents still describe this one correctly.** It watches one file at a time. When a document is deliberately shortened — as the open-actions list was in August 2026, from a long history down to a short list of what is still outstanding — anything that pointed at the part now removed goes on pointing, and goes on looking fine. The link opens, the file is there, and the thing it promised has gone. Five such pointers were found and corrected on 22 August 2026. So if you follow a reference and the promised detail is not there, the record probably was not lost: it moved, and the pointer was not updated. Say so and it can be traced back through the file's history.
- **`--backfill` used to walk other documents' dates backwards.** It dates a *new* document from git, which is right — "updated" should say when the file was actually last written, not when the backfill happened to run. But it applied that to every file it stamped, and an already-stamped file only reaches the stamping code because its content just changed, so its git date is the *previous* commit. Backfilling one new README on 21 August 2026 re-dated four documents edited that same morning to the 20th, silently and in the one line a reader actually looks at. Fixed the same day — the git date is now used only where no stamp is present — but if you ever see a visible date move backwards, that is the shape of the bug.

## For whoever maintains this

The tools are `scripts/docstamp.py` (stamping, hook-driven), `scripts/reflow_md.py` (Markdown paragraphs, hand-run) and `scripts/check_committed_stamps.py` (audits what is in `HEAD`, not on disk); scope lives in `stamp-policy.json` and all three honour it; `SKILL.md` has the commands, the design, and the gotchas. To check the current state of everything:

```bash
python scripts/docstamp.py --check
python scripts/check_committed_stamps.py
```

Run both from `~/.claude/skills/stamp-docs`. Neither takes an argument: the roots come from `stamp-policy.json`. **Since 2026-08-27 the second one also runs in CI**, from `buses-data`'s `.github/workflows/gates.yml`, which checks this repository out as a fourth checkout and passes the two pushed roots explicitly. So a docstamp that is wrong in `main` is now caught by a machine rather than by somebody happening to run the checker — which is how the last three were found. The third policy root, `community-bus-maps-ops`, is never pushed and is deliberately left out of the CI invocation.

**If you edit a stamped document and commit in the same turn, run `python scripts/docstamp.py --all` first** and commit the stamp with the content. The stamping hook runs at the *end* of the turn, so otherwise it leaves a stamp-only change behind for you to ship separately.

One lesson worth keeping, from 18 August 2026: `check_committed_stamps.py` reported 16 portal documents as having stale committed stamps, with per-file hashes, and that claim sat in `SKILL.md` as a known problem for a day. All 16 were fine — the tool was mishandling a byte-order mark and every BOM-carrying file failed. Acting on it would have meant 16 needless version bumps in a public repo. **Reproduce one failing case by hand before acting on a batch a tool reports.**
